## 代码定位

- `bindings/csharp/Store.cs` 的普通 Read 调用原生 `fqdb_store_get`，后者产生原生持有的字节副本。`bindings/csharp/FengquDB.cs` 随后创建托管 `byte[]`、Marshal.Copy，再跨界释放原生缓冲。因此比 C++ 直接使用原生返回缓冲多一次托管分配和一次复制，并有运行时边界成本。
- `StorePreparedKey.GetInto` 一次性复用键对象，直接把数据写进调用方固定的目标数组，不创建中间返回缓冲。它仍复制字节，不能称作零拷贝。
- C# GetMany 每次创建 StorePins、键描述数组和 GCHandle 列表，逐条固定/解除固定输入数组；结果逐条 Marshal.PtrToStructure 并创建 `byte[]`。减少数据库调用次数没有消除这些逐条工作。
- Python 普通调用有 ctypes 参数与结果对象、句柄租约，以及返回 Python bytes 的复制；固定缓冲接口已减少参数重建，但 Python 循环和 FFI 仍在。本轮未重新测量 Python/Java 吞吐。
- Java 的 byte[] 路径涉及 JNI 数组处理；已有 direct ByteBuffer 读取路径能避免部分数组中转，不能据此声称所有 JNI 成本消失。

Protobuf 的 C# 业务样例通过 Google.Protobuf 托管运行时解析消息；它不代表每次解析都跨界调用 C++。跨界调用整条消息或一组数据时，固定成本更容易摊薄。数据库热读只需约百纳秒时，同样的固定成本在比例上会显得更大。

## 后续优化顺序

1. 让常用安全接口便于复用调用方缓冲和键，避免把便利 API 的重复分配留给调用方猜测。
2. 增加准备批量键和复用整块结果缓冲/偏移描述，减少每批的固定操作、结构转换和逐条结果分配。
3. 为确实不需要独立副本的使用者设计有明确生命周期的只读借用接口；保留独立返回数组的所有权契约。
4. Python 对大量小记录应让更多循环在原生批量操作中完成；Java 优先复用 direct 缓冲。逐条动态语言调用不能保证等同 C++ 循环。

验收须使用相同返回所有权、相同读取或批量语义，另测分配字节、GC、完整业务解析和多线程场景；不能拿 C++ 仅取字节与 C# 读取加 DTO 解析直接比较。SYNC 写入也不能套用热读的衰减比例。本次短测存在 JIT/GC 和系统波动，解析与读取后解析结果不能直接相减分摊成本，也不外推到 Unity IL2CPP 或手机。
