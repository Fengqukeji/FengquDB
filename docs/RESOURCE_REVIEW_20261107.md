# 实际资源故障与默认日志压力（2026-11-07）

本批新增可重复执行的 Linux 生产 API 资源探针、Docker 驱动器和跨平台日志保留压力脚本。测试方法与运行方式见 [实际资源故障验证](RESOURCE_VALIDATION.md)。没有修改引擎、序列化与减法裁剪实现。

## 构建与隔离

`tools/store_resource_probe.cpp` 链接正式 Release 共享核心，只包含公开 C/C++ 头文件。核心编译定义为 FQDB_BUILD，没有 FQDB_TESTING；探针也没有测试宏或故障注入调用。CMake 的 FQDB_BUILD_RESOURCE_PROBE 默认 OFF，只在显式启用时构建 Linux 探针，不安装到 SDK。Windows 常规配置确认默认 OFF。

Docker 固定本机 Ubuntu 26.04 镜像的实际 ID，容器根只读、关闭网络、移除 capabilities，仅挂载专用 `/data`。各场景实际使用 2 核；内存为普通场景 512 MiB、强杀/恢复 256 MiB、OOM 96 MiB，内存与 memory-swap 同值。镜像 ID、实际 HostConfig、退出状态及源码/产物哈希均保存在 `build/store-resource-20261107/run-final/report.json`，每个容器另有 inspect JSON。

## 实际资源故障结果

| 场景 | 结果 |
| --- | --- |
| 16 MiB 文件系统追加写满 | 实际 ENOSPC=28，提交返回 COMMIT_UNKNOWN，原实例拒绝继续写；111 笔已确认事务全部恢复，截去 92205 字节不完整尾部，释放预留空间后可继续 SYNC 提交、校验及检查点 |
| 整理候选遇到写满 | 剩余空间填到 64 KiB 后返回 IO_ERROR；CURRENT 和已发布版本不变，旧快照有效，仅剩原三个库文件；释放空间后原 writer 可写，整理与完整备份重试成功 |
| 实际地址空间耗尽 | RLIMIT_AS=42508288 B，保留 126 个 256 KiB 压力块后，C ABI 暂存大值返回 NO_MEMORY；先前暂存的 guard 未发布，失败事务不能提交，释放压力后新事务成功 |
| 96 MiB 内核 OOM | Docker OOMKilled=true、退出 137；宿主收到 95 笔确认，恢复保留全部 95 笔，重放 95 笔事务后可继续写、检查点及重开 |
| 外部 SIGKILL 第 1 轮 | 退出 137、非 OOM；确认 25 笔，恢复 25 笔 |
| 外部 SIGKILL 第 2 轮 | 退出 137、非 OOM；确认 28 笔，恢复 28 笔 |
| 外部 SIGKILL 第 3 轮 | 退出 137、非 OOM；确认 36 笔，恢复 37 笔，额外一笔完整但尚未收到确认的事务符合原有结果不确定语义 |

每笔事务包含 Protobuf 载荷、镜像记录和递增 head；强杀场景每个载荷约 4 MiB。恢复逐条精确核对确认前缀与所有恢复出的完整尾部，检查不存在下一事务的孤立记录，再校验、新提交、检查点和关闭重开。所有已确认事务保留，没有半事务可见。

最终完整运行包含 11 次容器执行，全部按预期通过，`run-final/report.json` 的 ok=true，运行期间源码清单未变。本批没有新增的引擎修复需求。首轮在强杀场景开始前，探针的 8 MiB 事务预算不足以容纳 4 MiB Protobuf 值的保守暂存预留；现已将探针预算调整为 16 MiB，并显式验证每次确认对应 durable_version。这是测试配置修正，首轮失败及已通过场景保存在 `run/`，没有改写成成功记录。

最终运行的自有容器/卷全部清理。首轮失败资源在调查后再次检查标签和停止状态，再按精确名称清理，证据为 `run/cleanup-after-investigation.json`。宿主日志和报告仍保留。

## 默认日志压力结果

测试使用真实 Store PutIfChanged 调用，将成功提交记录阈值临时设为 0，但未改变轮转/保留大小和天数。默认 8 MiB 轮转与 64 MiB 总量确实被跨越，首个生成的日志文件自动回收：

| 指标 | Windows | Linux（WSL，DrvFS 上的独立测试目录） |
| --- | ---: | ---: |
| 重复未变值调用 | 135168 | 136192 |
| 最终写入日志计数 | 135172 | 136196 |
| 存量文件数 | 8 | 8 |
| 存量总字节 | 58699326 | 58937555 |
| 存量有效 JSONL 行 | 118275 | 119234 |
| 丢弃 / I/O 错误 / 回调错误 | 0 / 0 / 0 | 0 / 0 / 0 |
| 队列条数高水位 | 648 / 4096 | 773 / 4096 |
| 队列字节高水位 | 756864 / 2097152 | 900545 / 2097152 |

两端均验证：单文件不超过 8 MiB、总量不超过 64 MiB，写入计数大于存量行数，说明实际生成的早期日志已经回收；8 天前的自有旧格式文件被默认 7 天策略移除，无关日志保留。逐行解析全部存量 JSONL，未出现私密业务键值；只读诊断仍可查询，业务数据库关闭重开及后续写入正常。重复未变值没有使业务 WAL 增长。

证据分别为 `build/store-resource-20261107/windows-retention/report.json` 和 `linux-retention/report.json`，原始存量日志均在对应 log 目录。这里验证的是有限压力下的计数一致性与默认上限，不是实际运行 7 天，也不代表已测试 UINT64_MAX 等数值边界。

## 结论与剩余范围

实际 ENOSPC、可恢复分配失败、内核 OOM、外部强杀和默认日志保留压力均已获得运行证据。tmpfs 写满不模拟磁盘掉电，进程强杀不会切断内核及设备缓存，仍不构成真实硬件断电或长期生产验收。

本批引擎 DLL 未改变，开发 DLL 的 SHA256 仍为 `1ec3cbd02a709e983b4cc00a55a280a27c8e6a8f1b7103ba2616c201b245e44e`；原发布 DLL 仍为 `3411f07db33140f7b7fc1a479d36c51b862460295680194462489a39d07ee9c9`，未打包或替换 SDK。由于引擎代码未变，验证集中在新增探针、两个平台的实际日志模块和常规 CMake 配置，未机械重复上一批的完整回归及性能基准。
