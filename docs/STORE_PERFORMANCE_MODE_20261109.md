# 性能模式服务器业务复测（2026-11-09）

本轮默认性能模式已按内存原子发布后确认实现；此前热点计数、转账等待周期的退化已消除。24个业务条件各3轮、共72个样本，全字段与逐户余额校验、独立进程重开校验全部完成。其他数据库直接引用历史实测，没有重跑。

## 测试口径

沿用上轮镜像、Linux原生命名卷、2 vCPU（CPU 0/2）、4 GiB内存及无额外swap；4096档案、十字段DTO、固定种子、Zipf(0.99)，简介128/4096 B，实际初始化Protobuf205/4173 B。业务轨迹、编码解码与校验保持原标准。每调用线程只有一笔在途；数据库一个业务写线程。每轮计划1秒，每64操作检查时间；计入冲突重试、线程收尾和最终显式可靠sync，结束时version等于durable_version。每个样本核对后删除本次自有夹具，避免72轮文件缓存累积。

性能模式的同步返回／异步凭据完成表示内存成功；P50/P95/P99是该调用响应，不能作为逐笔刷盘延迟。吞吐列虽包含最终sync，也不代表此前每笔返回时已可靠。可靠模式和force_reliable仍先刷盘后成功。100 ms是调度目标，磁盘阻塞时可能超过；不能承诺严格只丢100 ms。

历史SYNC是逐笔可靠参考，历史BUFFERED比较用于观察不逐笔刷盘的成绩；其具体持久化策略也不完全相同（例如Redis everysec）。结果差异同时包含嵌入式／服务进程、网络、索引、缓存、编码和驱动成本，不能全归因于Protobuf。历史数据非同期测量，表内倍数为有界实测参考。

## 收益与剩余差距

15个含写条件相对历史可靠FQDB吞吐为5.38～11.58倍。热点计数、转账已不再等待100 ms周期才发布内存结果。4 KiB／8调用线程整存41,737次/秒，为历史可靠模式8.43倍、历史手动BUFFERED的1.36倍。与历史SQLite普通表、MySQL、Redis、MySQL+Redis的SYNC写成绩相比，本矩阵的含写条件均更高；两者逐笔成功保证不同，不能解释为同可靠性胜出。

纯读约为旧FQDB的0.95～1.05倍。部分差异处于几个百分点，短测不能证明这类差异在长期稳态下稳定存在。4 KiB／8线程整存三轮范围36,856～42,612，跨度约14%，因此不用最好一次代替中位数。

相对旧FQDB手动BUFFERED，单调用线程含写条件仍只有0.12～0.20倍吞吐。当前同步性能写每笔都跨线程入队并等待内存执行，旧BUFFERED可以在调用线程直接完成；当前还有后台可靠刷盘，旧BUFFERED依赖显式sync。因此“去掉逐笔落盘等待”并不等于“整个接口已达到内存执行极限”。具体成本占比没有做CPU采样剖析，不能将全部差距武断归因于某一步。8调用线程含写条件除4 KiB整存外，相对旧BUFFERED也还有差距。此处如实保留，未擅自改成调用线程执行或扩大在途窗口改变本轮标准。
