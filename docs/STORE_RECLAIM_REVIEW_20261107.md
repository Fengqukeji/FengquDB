# 原位稀疏回收隔离原型审查

本方案仍在 `build/reclaim-lab-20261107/` 隔离验证，**没有合入主工程，也没有发布 SDK**。向量检索、全文检索和 RAG/Wiki 按用户要求以后单独设计；本批只处理通用存储的持续空间回收。

主工程 114 文件基线的哈希仍一致，开发 DLL 为 790016 字节、SHA256 `5d72256e4fb998c189edb2dff9b21235b9cd9a4277de9c37cf5e443be438c4b3`；旧 0.3.2 发布 DLL 仍为 281088 字节、SHA256 `3411f07db33140f7b7fc1a479d36c51b862460295680194462489a39d07ee9c9`。本批没有更改完整私有二进制缓冲的减法裁剪、公开 C ABI 或语言绑定。

## 为什么换路线

此前的全库复制即使减少逐键反查和小帧写出，仍未能追上高并发持续写入，见 [后台整理审查](STORE_MAINTENANCE_REVIEW_20261107.md)。本原型不移动存活值，不改变它们的偏移；只找出旧文件中不再被引用的完整块，然后释放其物理分配。标记和扫描位置可以跨时间或 I/O 切片续做，避免每轮超时后从头复制。

Linux 使用 `fallocate(PUNCH_HOLE | KEEP_SIZE)`；Windows 使用稀疏文件及零区间控制。查询实际分配区间，跳过已有空洞。平台或文件系统不支持时继续采用原有换代复制；落后历史水位需要保留旧 WAL 时也走复制路径。较长旧读者等待后允许回退复制，复制本身的持续追赶限制仍存在。

## 数据与读者保护

- 先把当前增量元数据折叠为持久根，预付两次完整 seal 与 superblock 的写额度；两个根都成功同步后才允许回收。根写入开始后失败会封锁写者并要求重开。
- 原型新增 `FQROOT05` superblock，记录历史边界 seal 的偏移和结束位置。WAL 和逻辑 features 仍用既有编码；打开时校验边界 CRC、类型、版本和结束位置。旧程序不能识别 Root5，不能用其打开这份实验数据。
- 标记冻结索引页、普通值和补丁依赖，只回收截止位置前未标记的完整块。后续写入追加在截止位置后；补丁保守保留完整原始 base 与 recipe，**尚未对被减掉的 raw span 做物理裁剪**。
- 读者保护随不可变 View 持有。文件代际保留此前所有仍存活的读者时期记录；新任务会清掉已退出的弱引用，保留旧任务留下的活读者。保护记录受写者 scratch 与 pin 预算约束。
- 时间或 I/O 切片耗尽保留标记、页内位置和扫描位置；取消、关闭、切代际等路径明确释放任务。关闭不需要后台任务反向持有 Core。
- 历史读取从持久边界之后开始，避免扫描旧空洞。全备仍输出独立的紧凑文件；持久历史水位和未确认订阅阻止丢弃所需 WAL。

## 审查中实际修正的问题

1. 原来的 `pending=true` 再清除 `cancelled` 可能覆盖并发取消。现在以一个原子状态表达空闲、运行和取消，取消与启动只有一个状态转换。
2. 文件统计可能遇到后台刚删除的旧代际。比较工具容忍 `ENOENT`，其他查询错误仍报错；同时保留逻辑长度和实际分配量，每约 250 ms 采样一次分配及匿名/文件缓存内存。
3. 最初只记住上一轮 reader epoch。取消任务后重开第二轮可能漏掉第一轮仍存活的快照。新增用例在修复前实际失败：`replacement reclaim forgot an earlier reader epoch`。现在由 Generation 持续持有有界弱引用集合，任务取消不清除保护。失败源码、EXE、哈希和日志保留在 `source-epoch-repro/`、`epoch-repro-report.json`、`epoch-repro-test.exe`、`windows-epoch-repro.log`。

第一轮 worker 源码位于 `source-worker/`，带上述第三项缺陷，不能作为可合入版本。修复后的完整 116 文件位于 `source-epochs/`，由 `epochs-source-manifest.json` 固定；`epochs-proposal.patch` 保存相对主工程的差异。二者不能混用。

## 当前验证

修复后的隔离副本通过 Windows 原生 CTest **20/20**、Linux ASan/UBSan 含泄漏检测 **20/20**。这两个集合包含新增回收用例，未启用诊断适配器和 JNI；不等于三语言或移动平台已经重新验收。原始日志为 `windows-epochs-test.log`、`worker-asan-epochs-test.log`，Linux 源码清单、资源配置和二进制哈希见 `worker-asan-epochs-report.json`。

回收用例覆盖旧快照冷读、补丁祖先、I/O 切片续做、双根额度不足与未发布元数据尾回滚、启动/等待写者时取消、punch 故障重试、切代际冲突、后台多轮覆盖写入、停止及重配置、旧读者复制回退、重复取消后旧读者保护、任一根损坏回退、根写入/同步故障封锁与重开、全备/增量恢复、历史订阅，以及第一次 seal、双 seal、标记结束和 punch 后的子进程退出恢复。

Windows 修复后两轮 4 名写者、4 KiB 值覆盖的模型用例，逻辑长度约 42 MB，实际分配回落到 720896 字节并完成 3 次回收。它是有限波次的功能用例，不能代替持续吞吐或长期空间验收。

修复后的回收、后台功能、历史订阅三个 TSan 程序也通过，记录为 `worker-tsan-epochs-report.json`；分别在 17、10、12 次 main 前地址布局失败后进入并通过。只对明确未进入 main 的此类失败重试，未跳过已进入测试的错误。崩溃子进程在 TSan 下跳过，由 Windows 和 ASan 集合覆盖。

## 第一轮及修复后持续写入诊断

该组观察到单条更新吞吐约回退 50.1%，批量约回退 4.8%；单条 P99 也变差，不能作为提速优化合入。最后 20 秒的候选物理分配分别在约 77～153 MB、166～386 MB 间回落，而基线继续增长；候选计时内存峰值约 1.78/1.62 GB，基线均触及 4 GiB。这说明原位回收在该负载下取得局部空间进展，同时引入了尚待定位的成本。

修复后的两项继续完成 15/29 次回收，最后 20 秒分配量分别在约 76～155 MB、157～369 MB 间回落，结束为约 119/241 MB；计时内存峰值约 1.71/1.57 GB。单条写入相对前面基线样本约回退 53.4%，批量约回退 4.2%；单条尾延迟仍明显变差。受测 60 秒取得回收进展，不能由此宣称多年稳态已验证，更不能把不同写入总量下的结束大小比当作同工作量的压缩倍数。

第一轮 worker 存在已复现的旧读者缺陷，不可采用；修复后源码的性能仍未达到合入要求。原始记录为 `worker-steady256-report.json`、`worker-epochs256-report.json`、逐项报告和 `worker-evidence-summary.json`。修复后核心 SO SHA256 为 `29bbcfda50fe329b3a27a597a53ac2a5c0411804826bf2dd136aadd1fecbcd9f`；镜像及匹配基线由 `worker-epochs-images.json` 固定，比较源码由 `epochs-candidate-benchmark-manifest.json` 固定，核心文件与 `source-epochs/` 相同。比较工具核验源码和镜像，自有容器与卷均在所有权检查后清理。

## 仍未解决的边界

物理空洞回收不会降低逻辑偏移或文件长度。高吞吐持续服务仍可能触及具体文件系统的文件长度上限；当前没有逻辑地址回卷或分段复用，不能宣称长期空间已完全有界。后续成本计时、后台开关和 perf 对照已排除“只因标记或同步耗时”的简单解释，发现原写者交接的停车/唤醒成本；三状态锁改善纯写，但混合吞吐与批量尾延迟未达到采用条件，详见 [写者交接审查](STORE_WRITER_REVIEW_20261107.md)。回收候选仍未合入，仍需扩大切片/异常模型、较大载荷与持续稳态验证，并确定实验磁盘格式的兼容策略。

后续新增保留单调地址的分段物理文件层原型，两平台完成独立随机模型、跨段并发、故障和强杀验证；尚未与双根/可达性标记连接，不能当作上述逻辑文件边界已解决。最长段名、持久发布、脏句柄保护及接入条件见 [分段文件层审查](STORE_SEGMENT_REVIEW_20261107.md)。

另一份后续隔离副本现已将分段文件层与双根、WAL 恢复、可达性回收及整代际清理连接，并完成真实数据库故障和并发模型；两平台 21/21 与 TSan 六程序通过。它还没有合入主库，长期物理文件数量、标记内存与正式吞吐仍待验收；源码身份、首次失败和清理修复见 [分段 Store 接入审查](STORE_SEGMENT_INTEGRATION_20261107.md)。

旧快照或持久历史水位长期不释放时，需要保留相应数据；回退复制在高写入下仍可能超时。实际资源不足、默认日志压力、五语言成本、包体与导出、Android/iOS 和最终五方案比较仍按 [长期验收记录](GOAL_ACCEPTANCE_20261107.md) 继续，不能用本批原型取代最终验收。
