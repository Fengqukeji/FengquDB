## 单例优先的 SYNC 选型

用户要求收缩验证范围后，120 样本矩阵在完成 24 个样本时主动停止，未完成部分不作为成功证据。随后只使用 256 B、SYNC、单条完整修改、128 线程这一例，比较组大小和唤醒方式；每项两秒、预热 0.2 秒，两轮顺序反转，共 8 个短样本。每次测量都做完整业务值比对及独立进程重开。2 CPU、4 GiB、无 swap；所有编译结束后才计时。

| 配置 | 两轮吞吐，条/秒 | 两轮抽样 P99，微秒 |
| --- | --- | --- |
| 改前核心，共享唤醒，组上限 64 | 41797 / 42287 | 3740 / 4000 |
| 候选，逐等待者唤醒，组上限 128 | 64484 / 63084 | 3288 / 4826 |
| 候选，共享唤醒，组上限 64 | 39680 / 41183 | 3422 / 3428 |
| 候选，共享唤醒，组上限 128 | 65547 / 66608 | 3342 / 3966 |

选择共享唤醒、默认组上限 128，允许配置 1–256；撤回逐等待者条件变量。相对于改前，这个例子的吞吐中位数提高约 57%。固定 64 的结果没有显示代码本身的吞吐收益，主要收益来自更充分地摊薄同步，而不是去掉校验或刷盘。单线程无法合组，这项策略不解决每次独立 fsync 的物理等待。

这只是方案筛选证据，不是完整并发曲线、多载荷验收或“全面超过 Redis”的结论。此次没有续跑大矩阵或重测 Redis。正式基准增加显式 `--fq-group-max`，仍默认 64；新比较必须注明配置，不改写原结果。

WAL 的缓存 CRC 复用及有界 16 KiB 写出合并仍是工作区候选的一部分；这个 256 B 单例不能证明其对其他载荷的性能收益。完整私有二进制缓冲及减法裁剪保持不变，WAL 输出缓冲不改变值的私有编辑方式。

## 可靠性和证据边界

此前 Linux 标识诊断复现过全零 UUID 重复，已将随机源改为操作系统 API：Windows BCryptGenRandom、Linux getrandom，其他 POSIX/Android 使用 urandom；零标识或读取失败拒绝。连续 20 万个标识和原生回归通过，未将根因擅自归结为特定硬件。

删除旧引擎及随机源修复后的两平台 21 项原生测试、Linux 21 项 ASan/UBSan 与三语言接入记录保存在本目录。SYNC 候选先完成两平台相关原生复验、Linux 21 项 ASan/UBSan、安装消费者和语言接入；本次撤回逐等待者唤醒后仅补直接相关的并发及故障检查，不重复整个矩阵。各阶段源码与测试范围分别记录，不能将旧阶段全量测试当作最后源码的全量结果。

首次候选测试中的故障注入依赖原来的写调用次数，新写出方式使第三次注入不再触发；正式测试改为更大的 WAL，并覆盖每次写失败和同步失败。Windows 高并发屏障测试改为显式线程，避免 std::async 线程池阻塞爬升造成排队超时。原始失败日志保留，修正后单独记录复验。

证据均位于 `build/store-only-20261108/`：

- `sync-pilot-report.json`：本次单例 8 个原始样本。
- `sync-matrix-stop.json`、`sync-ab-report.json`：停止决定与 24 个已完成矩阵样本，矩阵整体未完成。
- `profile2-report.json`：26 个吞吐诊断及热读分量；首次 perf 过滤时钟不一致，空报告不用于热点归因。
- `profile3-report.json`：显式指定 monotonic 时钟后的 6 个有效 CPU 采样；4 KiB 修改与批量写入的 CRC 分别占用户态样本约 37% 和 44%，不是全部墙钟时间。
- `store-only-source-v3.json` / `v5.json` / `v6.json`：随机源修复、初始 SYNC 候选及唤醒撤回后的源码身份。
- `windows-sync-tests.log`、`windows-sync2-tests.json`、`linux-sync2-report.json`：首轮原生失败、定向复验及候选 sanitizer/接入。
