# 单线程逐次刷盘：最小机制筛选

本轮只研究一个单线程、256 B 值完整修改的例子。实际 Store 先完成 128 次 SYNC 更新、版本/持久水位核对、校验及关闭重开读取，约 844 次/秒。随后使用包含 256 B 值的 512 B 文件记录筛选 I/O 路径；文件层吞吐不能当作数据库吞吐。

使用同一 Docker Linux 原生卷、2 CPU、1 GiB、无 swap；每种方式两轮、每轮 128 次。普通追加和候选都每笔同步，不用合组或延迟持久化。没有数据库重编译、sanitizer、大矩阵或其他并行性能任务。

| 文件层路径 | 两轮次/秒 | 结论 |
| --- | --- | --- |
| 持续追加、每笔 fsync | 942 / 893 | 基线 |
| 持续追加、每笔 pwritev RWF_DSYNC | 918 / 900 | 单纯替换同步 API 没有明显收益 |
| 预先写实初始化 64 KiB、每笔 fsync | 1825 / 1852 | 不再逐笔扩展文件及转换未初始化范围，约两倍吞吐 |
| 预初始化、每笔额外写轮换尾位置槽、fsync | 1615 / 1651 | 加入有效尾位置的写入开销后，仍比基线高约 78% |

初始化包含实际写零和同步，不仅调用 fallocate；本次将文件及目录初始化时间一并计入，最后一项相对基线仍高约 77%。所有记录全字节、两个尾位置槽均用新文件描述符验证。普通追加的 pwrite 平均约 9–10 微秒，随后 fsync 平均约 1052–1110 微秒。

选择继续研究预初始化空间和显式有效日志边界。此次没有修改核心源码，当前 Store 文件格式尚不能直接使用预填零尾部。尾位置槽实验只衡量额外写入成本，没有证明一套完整恢复协议：实际集成必须定义预留区域、提交边界、尾部撕裂写与真实损坏的区别，以及容量补充的顺序。不能通过忽略坏 CRC、静默丢弃完整坏记录或省略同步来取得收益。

这轮完成机制筛选，不宣称数据库已提高 78%，也没有 Windows、硬件掉电或全场景结论。下一步应限定为一个隔离格式候选和同一个数据库例子，先确认真实端到端收益，再扩大必要验证。

可复现脚本和原始结果：`build/single-sync-min-20261108/` 下的 `probe.py`、`tail-probe.py`、`report.json`、`tail-report.json` 和 `decision.json`。两个自有容器和卷均在验证成功后核对所有权并清理。
