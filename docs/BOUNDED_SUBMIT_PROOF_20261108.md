# 大值争用代办提交：最小验证

> 后续状态：用户授权后，最终定向方案已合入主引擎。本文“尚未合入”描述保留为原型验证时的历史状态；当前采用与验证见 [合入记录](BOUNDED_SUBMIT_MERGE_20261108.md)。

本轮按要求只研究提交代办和等待策略，没有引入流水线或分片。最终隔离原型在所测的 4 KiB 简介档案、8 线程完整保存中提升 **26.6%**，抽样 P99 从约 **6.22 ms 降至 0.57 ms**；小数据读多写少基本持平。2 秒单线程整存中位数约低 3.9%，逐轮有升有降且波动较大，不能宣称单线程已经完全无回退。

**尚未合入主引擎。** 这是方案有效性的最小证据，不是全场景采用或生产可靠性认证。主工程 56 个受保护输入逐一哈希未变，发布包未替换。原有完整私有二进制缓冲和减法裁剪没有改动。

## 最终原型的实际范围

原型位于 `build/bounded-submit-20261108/candidate/`；相对基线只改变 `src/paged/core.hpp`、`src/paged/group.hpp`，并新增 `src/paged/buffered_submit.hpp`。

- 仅针对 BUFFERED、普通事务中的一条完整 put，暂存值至少 4096 字节。按实际暂存操作及字节数判断，不识别基准名称或业务 schema。4 KiB 是本轮原型入口，不是已测定的全局最佳阈值。
- 大值写入也先尝试原来的直接路径，只有确有写入锁竞争或已有代办者时才进入队列。没有固定凑批等待，也没有新增常驻写线程。
- 当前调用线程可以在继续持有写者时，顺手代办已经排队的大值请求。每笔仍有独立日志记录、冲突检查、版本、发布和完成结果，没有把几笔独立事务改成一笔原子事务，也没有延后至整组才发布。
- 连续代办最多为配置组上限与 64 的较小值，同时在累计日志字节达到 256 KiB 或连续处理约 200 微秒后停止接下一笔。这些检查发生在事务之间；单笔不可拆分事务仍可能超过字节或时间门槛。
- 等待者使用各自的完成条件变量；只通知已完成的请求或下一位代办者。队列成员状态、完成通知和退出由同一队列互斥保护，防止调用栈请求在通知过程中销毁。
- 排队中的请求可以取消或超时；出队后必须等处理完成，保证输入、事务和日志事件对象存活。代办者取消或超时后交接给后继请求。
- SYNC、线程内 I/O 额度、小日志增量、删除、多键批量和原子条件接口继续使用原提交路线。若增量修改因已有深度限制被物化为一条完整大值 put，则按物化后的实际操作判断。

队列快路使用活跃/待入队状态握手：竞争者在队列互斥下先登记待入队状态再链接请求，无争用代办者可以通过原子状态释放领导权。这避免无争用写入每次获取队列锁，也避免检查空队列与入队之间丢失后继请求。

思路参考 [RocksDB WriteThread 设计](https://github.com/meta/rocksdb/blob/main/docs/components/write_flow/02_write_thread.md)、[LevelDB 写入队列](https://github.com/google/leveldb/blob/main/db/db_impl.cc) 和 [Folly 代办临界区说明](https://github.com/meta/folly/blob/main/folly/synchronization/DistributedMutex.h)，没有引入这些库作为依赖。本轮没有采用持续自旋策略。

## 最小性能对照

复用上一轮相同业务程序：完整编码保存生成相同十字段 C++ 档案，并完整编码后覆盖；B 为约 95% 完整读取、5% 修订字段更新。4096 条记录，固定种子、相同访问轨迹，每项装载及预热在计时外，结果按独立模型核对全部字段并独立进程重开校验。

Linux Docker，CPU 0、2 两个指定 vCPU、4 GiB、无额外 swap。所有构建和安全验证均与性能计时分开。两个核心来自相同源码基线、相同编译配置；重新构建的基线 SHA256 与原正式比较所用生产库完全一致。

## 探索中保留的负结果

1. 所有 BUFFERED 请求都代办，逐笔发布：8 线程大值保存改善约四成，但小数据混合吞吐下降约 17%，未采用。
2. 去掉无争用时的队列锁、计时和条件变量构造：混合回退仍约 13%，表明不能仅归因于固定快路开销，未采用。
3. 将范围限制为单条大值完整写入：目标写入改善，小数据混合接近原实现，但较长单线程样本波动明显，继续保留。
4. 最终版再增加“实际无争用则直接提交”，只在确有争用时使用代办，得到上表结果。

没有通过只挑最好一轮、隐藏回退或把各版不同条件数字混合成一份成绩来选方案。早期二进制和源码 ZIP、逐轮报告保留在同一证据目录，最终结果只汇总 v4。

## 针对性安全检查

单个控制探针在同一份候选源码上通过 ASan、UBSan 和泄漏检查，包含：同键写冲突及旧快照、代办数量上限为 1 的交接、排队取消、排队超时、代办者取消后的后继接替、存活请求写入以及同步后重新打开读取。它不代表 TSan、真实断电或完整故障矩阵通过。

安全探针首次编译因测试 lambda 的匿名枚举/状态类型推导不一致而失败，没有执行到数据库；显式标注返回类型后通过。失败源码 `control_probe-attempt1.cpp`、编译输出和原始失败报告均保留，未改写为成功。所有自建容器和卷均按各自所有权标签核对后移除；失败编译资源的清理另记为 `failure-cleanup.json`。

本轮未覆盖 Windows/移动平台、TSan、长时间持续写入、64 KiB 记录、跨语言接入及新队列的完整故障注入。尚未证明已消除全部并发回退，最终原型仍有待决定是否采用，不直接替换主引擎。
