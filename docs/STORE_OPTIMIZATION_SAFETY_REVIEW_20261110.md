# 三项优化的代码风险与四平台边界（2026-11-10）

这是接入前审查记录。后续已按受限方案接入主引擎，实际实现及验证结果见[接入记录](STORE_SAFE_OPTIMIZATIONS_MERGE_20261110.md)。

范围：仅静态阅读现有引擎及上一轮隔离原型，不编译、不跑性能或功能测试、不改生产引擎。结合用户允许低风险优化接入的补充要求，评估副作用和安全实施范围。本记录提供实现判断，不是上线或四平台验收结论。

## 结论

| 项目 | 正确性风险判断 | 对其他操作的潜在影响 | 建议 |
|---|---|---|---|
| 复用已验证旧引用，预留WAL头部容量 | 低，依赖现有提交验证顺序不变 | 临时容量和分配失败时点可变化；不保证所有键长或批量都提速 | 可作为小范围公共路径改动 |
| 复用已解析索引规则 | 缓存身份校验可行；原型的长期内存计费尚不完整 | 每线程新增保留内存；交替查询多个索引可能反复失效，多付TLS及引用计数开销 | 补齐计费、可选准入和生命周期，再接入 |
| 私有缓冲转入值缓存 | 单命令可控；不能直接放开为任意事务 | 可能破坏共享写集、借用I/O；容量膨胀会改变缓存淘汰行为 | 先覆盖内部独占的自动事务，包括带索引路径；其他事务复制回退 |

三项概念上可以共存，但不能把实验开关的存在视为安全实现，也不能由静态审查断言所有负载提速。前两项不改变日志字节；第三项也应只改变内存所有权，不改变WAL、发布及可靠提交协议。

## 1. 共用写路径

`Transaction::stage`与初次patch都从`depend`保留原引用；提交先验证Generation、功能标志及读依赖的版本，再进入`append_writes`。单命令在写者租约下取得当前引用。因此数量统计可复用`Write::original`，无需再次`old->find`。

条件是保留全部冲突验证，且用`original.version == 0`判断真正不存在。删除标记的offset为0但version非0；不能把`deleted()`、到期或空值当作不存在，否则会改变entries、keys及live_bytes统计。导入恢复也通过普通stage记录依赖，不能因skip_indexes绕过引用验证。

为头部Writer预留容量只改变临时字符串分配，不改变字段顺序、长度、CRC或文件格式。不能借此扩大每笔事务的长期预留，也不能把字符串capacity写进日志。OOM仍应在WAL追加前沿现有错误路径退出。

## 2. 索引规则复用

隔离原型先取得schema并记录事务依赖，再通过弱引用锁住上次的准确schema对象，比较对象身份后复用解析结果。锁住的旧对象在比较期间不会释放，因此不是只缓存裸地址；删除重建同名索引、旧快照和不同数据库不能仅凭名称或全库版本判定命中。

需要补齐以下边界：

- 持久保留的规则字符串、parts及缓存元数据纳入有上限的预算。原型只有每线程一个、schema不超过4096字节的限制，没有将规则长期内存计入库预算；线程很多或缓存关闭时，这点尤其需要明确。
- 缓存填充或预算准入失败时使用本次已解析规则，不把可选缓存失败升级为查询失败，也不为缓存而再次复制或解析。
- 缓存只接受已提交、不可变的schema。内部事务若存在私有catalog写入，直接解析；不能把“shared_ptr<const Data>类型”当成底层暂存数据绝不会原地修改的证明。
- 保留逐次schema获取、可见性及依赖记录。不能跳过TTL、索引ready状态、范围边界或查询字段解析。
- `Core::rules_cache`现用于写线程，不能为省分配就在查询线程无同步读写它；其生命周期、同步及所匹配的快照必须另外设计。

此项不需要改普通按键读、批读或值对象布局。不应给每个普通Data增加索引规则指针，避免把仅查询所需的成本摊到所有值上。交替多个索引或不同快照时，一项缓存可能反复失效，因此理论上存在性能负担；不以代码审查代替实测结论。

代码依据：[查询入口](../src/paged/query.hpp)、[规则结构](../src/paged/index_schema.hpp)、[现有写线程规则缓存](../src/paged/features.hpp)、[现有读取TLS](../src/store.cpp)。

## 3. 缓冲转移为什么不能只放开类型判断

`WriteRoot`为持久共享树。保存点和事务游标可以共享同一个WriteNode，而节点内只有一个指向StagedData的shared_ptr。即使数据的use_count为1，也可能有多个逻辑读者通过这个节点访问它。此时把字符串搬空，会影响提交前建立、提交后仍存活的游标；若它并发读取，还会形成数据竞争。仅检查root是否独占也不够，编辑后新根仍可能共享旧子树。

此外：

- 预制批次保留同一StagedData，后续可再次应用。不能把批次输入搬空；数据指针独占检查只能作为已有所有权证明之后的第二道保护。
- StagedData携带事务Charge。不能直接把整个StagedData强持有进值缓存，否则命令或事务结束后仍保留事务预算。应使用新的缓存Data，只转移其中的Bytes存储，重新设置CRC并按实际capacity计费。
- WAL对较大值可保留owner交给DeferredIO。append完成不等于磁盘已不再引用原地址。初次扩展保留原型的小值限制，不为搬移增加Sync或等待屏障；不满足借用安全条件就复制。
- 减法裁剪可以让逻辑值变小而capacity很大。原实现复制为较紧凑的缓存值；直接搬移会把大容量一起保留，导致更高缓存占用、更多淘汰和其他读取变慢。容量明显膨胀时继续紧凑复制；短字符串也未必有堆缓冲可搬。
- 新缓存对象必须在搬移前分配成功。搬移后的缓存准入失败仍属于可选缓存失败；日志已接收的数据及可见性不得依赖缓存成功。追加前的正常失败不能留下已被搬空、却还允许调用者继续使用的事务。

代码依据：[写树及独占路径说明](../src/paged/write_index.hpp)、[游标保留写集](../src/paged/cursor.hpp)、[预制批次](../src/paged/operations.hpp)、[暂存计费与裁剪](../src/paged/budget.hpp)、[借用WAL载荷](../src/paged/wal.hpp)、[延迟I/O所有者](../src/paged/deferred_io.hpp)、[缓存准入与淘汰](../src/paged/cache.hpp)。

## 4. 带索引事务的可行实施范围

可行，而且不需要把索引写入伪装成无索引路径。优先覆盖以下已有请求：

- `AtomicUpdate`内部创建的普通业务自动事务，包含带索引的put、patch、比较交换等；它们返回标量结果，不把私有写树交给调用者。历史pin管理等维护操作不因共用这个类型就自动获得搬移资格。
- `FieldUpdates`内部创建的字段加减事务，包含多键转账；仍对每个值执行独占、借用及容量检查。
- 同一原则可覆盖由异步put请求在写线程内新建的事务；不能因请求是异步的，就把从用户事务转移来的写集一并当成独占。

这些请求由明确的内部上下文授予“可消费私有缓存缓冲”的资格，不能仅靠transaction指针存在、没有保存点或不是只读来猜测。普通显式事务、已有游标、可复用批次及维护/导入请求默认不授予资格，继续复制。将来若覆盖它们，需要单独证明整条写树和所有外借者的生命周期。

顺序保持为：完成索引计算、唯一约束及冲突验证 → 编码、校验并接收完整WAL → 释放已不再使用的WAL小载荷引用 → 对获准且确实独占的完整私有值转移缓冲 → 按原协议发布/可靠确认。索引维护暂时持有的original写树和next_bytes必须已离开作用域。缓存成本、CRC、准入、旧版本淘汰和复制回退集中封装，避免各接口各写一份。

这样可让带索引自动写入和索引查询在同一数据库中分别受益，不改保存点、快照、批次共享和公开句柄的承诺。代码层面属于可控的局部所有权改动，仍涉及数据一致性，不能宣称无需验证即可发布。

## 5. Windows、Linux、Android、iOS硬约束

- 保持C++17和现有C ABI。内存始终在原生库内部申请、转移与释放，不跨C#/Java/Python或Unity运行时转移allocator所有权。
- 只使用标准std::string、shared_ptr及既有同步机制。MSVC STL、libstdc++和libc++的短字符串容量、增长和移动后状态不同；不硬编码15/22字节，不假定move一定零复制、不复用移动前的指针，也不memcpy整个含string/atomic的对象。
- 引用计数不是线程锁。资格证明、写者互斥和发布顺序须在ARM弱内存序下同样成立，不依赖x86的观察结果或添加无同步裸指针捷径。
- 不引入平台独占系统调用、特定SIMD指令、特定页大小或固定指针宽度；所有计费使用实际capacity及已检查的长度。日志继续按现有明确编码生成，不持久化宿主结构体内存布局。
- 不修改平台I/O层、预留空间恢复、性能/可靠模式、force_reliable及50 ms / 1 MiB默认设置，不为这三项新增忙等或周期任务。
- Android共享库已有16 KiB链接对齐设置，静态iOS产物仍须在宿主链接阶段满足目标要求；这些设置本身不能替代目标平台验收。

当前`.github/workflows/build.yml`仅列Windows与Ubuntu任务，没有Android/iOS目标任务。因此本次只能得出标准C++设计可移植的判断，不能声称四平台已验证。后续实际接入的相关验证应覆盖Windows/MSVC、Linux工具链、Android NDK/libc++ ARM64、Apple Clang/libc++ iOS设备及模拟器目标；Unity使用场景另核对IL2CPP的C ABI与句柄释放。用户本轮要求先分析，本次未执行这些构建或测试。
