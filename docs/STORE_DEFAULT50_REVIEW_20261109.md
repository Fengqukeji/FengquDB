# 默认 50 ms / 1 MiB 与空闲写线程验证（2026-11-09）

当前默认值已改为性能模式、50 ms / 1 MiB。原生 C 默认、C++、C#、Java、Python 配置对象和 Python configure_write 默认参数均同步，业务基准默认周期也改为 50 ms。当前接口和入门文档已更新；历史报告保留当时测量值并标注当前规格入口。

## 保存与还原

- 新库和没有 WRITE 配置文件的目录采用新默认值。
- 已有保存配置按原值加载，包括过去显式选择的 100 ms，不会在升级时覆盖业务设置。
- reset 或 C API 传 NULL 会恢复并保存 50 ms / 1 MiB；重开继续为 50 ms。
- 可靠模式与单次强制可靠写入仍等待可靠同步后成功。

## 空闲不空刷盘

生产逻辑已有该行为，本次保留条件，仅加入测试构建专用观测计数器：

1. 写线程按首次实际请求启动，空库没有写线程或周期定时器。
2. 待刷逻辑字节非零时，才检查周期/阈值并安排同步。
3. 队列为空且待刷字节为零时，使用无截止时间的条件等待；有新请求才唤醒。空闲阶段不进行短暂活跃等待。
4. 即使显式 sync 到达，可靠版本已追上当前版本时也会直接返回。

新增测试覆盖 Hybrid、分段与整理后的直接文件三种布局：先观察空库 200 ms，再进行两轮写入；每轮等最后数据可靠落盘后观察 250 ms（五个默认周期），确认写线程循环次数、空闲等待次数、数据文件 write/sync 计数均不增加，并检查下一轮写入仍正常唤醒、落盘。测试计数器只在 FQDB_TESTING 存在，不进入发布库。

## 验证范围

- Windows、Linux 各 3/3 相关原生测试通过：paged_write_policy、paged_committed_cache、paged_store_sdk。
- 两平台 C#、Java、Python 写策略与常规接口回归通过；覆盖各语言配置对象的默认值、reset 后重开、用户保存配置及强制可靠写入。
- 本次没有重跑全量性能矩阵及 sanitizer：生产变化为默认参数，等待/刷盘条件和 CRC/缓存计算路径未改。上一轮最终引擎已测显式 50 ms，对照见[整存、转账与周期测试](STORE_SAVE_TRANSFER_REVIEW_20261109.md)。

## 当前剩余短板

下表区分已测到的现象、代码定位和尚需覆盖的场景，没有重新使用旧 SQL/Redis 数据建立排名。

| 优先级 | 短板 | 当前证据与实际影响 | 后续方向 |
|---|---|---|---|
| 1 | 刷盘期间的写入尾延迟 | 写线程调用 sync_locked 时持有写者许可；上一轮 50 ms / 1 MiB、4 KiB / 8 线程整存的 P50 约 3.15 微秒，P99 约 2.69 毫秒。少数调用仍受正在进行的 I/O 阻挡。 | 定向量化刷盘阻塞；沿用用户此前要求，本次没有改变该机制。 |
| 2 | 普通值冷读的重复校验（后续已解决） | 已保留最终一次内容 CRC，校验与最小性能对照见[冷读与并发说明](STORE_COLD_READ_REVIEW_20261109.md)。 | 字段投影需要另外设计，普通完整值读取仍需要完整结果。 |
| 3 | 热点事务仍有冲突重试 | 上一轮显式 50 ms、4 KiB / 8 线程转账样本，额外重试/完成业务笔数中位数约 7.27%，约每 1000 笔多做 73 次尝试。 | 减少失败尝试的准备成本；若提供写线程内声明式多键原子命令，可另行避免部分业务重试，同时保留普通事务的快照语义。 |
| 4 | 长期/大值/移动端证据不足 | 最近吞吐对照主要为热缓存 128 B、4 KiB 与两项写入业务；不能据此判断当前 MiB 大值、超内存冷数据和大型原子批量的表现。Android/iOS 真机、真实断电及长期压力尚未完成。 | 每个领域先选一项短测试，发现问题后再扩展；这些是验证缺口，不把历史大值弱项直接当作当前结论。 |

完整保存仍输入并记录整份业务值，写磁盘量明显高于少量字段补丁。只改 8 字节时应优先使用已有 patch 接口；整存语义的透明多处差分需要独立验证，不能直接假定输入等于旧缓存。

后台在线维护已实现但默认关闭；持续更新时需要配置维护策略。长期写入下整理是否及时收敛、重启代价和实际设备空间峰值还需要压力验证。
