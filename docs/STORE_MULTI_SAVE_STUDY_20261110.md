# 多段差量整存最小原型（2026-11-10）

后续状态：公共差异内核与有界整存已接入主引擎，当前结果见 [接入报告](STORE_BINARY_DIFF_MERGE_20261110.md)。本报告保留早期隔离原型的测量与限制，下文“未合入”描述的是当时版本。

**写入量和尾延迟有明确收益，持续整存吞吐尚无稳定的大幅提升。** 4 KiB简介、8线程完整编码并保存，首版三轮约1秒对照的吞吐中位值从64,616升到124,269次/秒，约1.92倍；审查修正后的最终点测约提升52.0%，4秒点测仅提升1.6%。先前两个4秒对照分别提升5.1%和20.0%。写入量及P99在这些测量中均明显减少。原型保留在 `build/multi-save-20261110/candidate-source`，**没有合入主引擎**。

## 原型做了什么

业务仍传入完整新二进制，保持原接口及性能模式 **50 ms / 1 MiB**，每线程仅一笔同步调用在途，包含完整DTO编码、最终Sync、业务字段校验及独立进程重开。

仅对1～64 KiB的同长度覆盖尝试差量：复用现有受预算限制的值缓存中的完整旧值，确认引用、长度、CRC和文件配方标记一致后，完整比对新旧字节。相同的64字节块快速跳过，变化处识别为少数范围。最多8段，编码载荷不超过完整值的四分之一；冷缓存、长度变化、变化过多或已有差量深度达到8时直接完整写入。不会为了找差量额外读盘。

写入缓存中保留完整新值；日志记录基值引用、变化范围和新字节。恢复时在基值上直接覆盖变化范围，最终核对完整值CRC。没有反复拼接不变二进制块。已有单段减法裁剪保留，旧的共享值不会被修改。差量深度上限仍为8，因此热点反复保存也会定期完整写入。

为使纯写整存也能复用旧值，原型允许这些有界大小的完整写进入既有值缓存，沿用原预算和淘汰规则。因此另外设置“只缓存、不生成差量”对照，区分缓存和日志压缩的影响。

这是隔离研究格式：新增WAL操作种类5，并适配读取、恢复和回收引用遍历；没有修改主目录、公共接口或生产文件格式。**原型数据库文件不能交给当前生产引擎使用**。正式接入前还需要格式能力标记及完整兼容性/恢复审查。

## 测量口径

沿用上一轮原生服务器业务可执行文件及镜像，Linux原生命名卷、CPU 0/2、2 vCPU/4 GiB，4096份十字段档案，Zipf(0.99)、固定轨迹。业务简介4096字节，初始化Protobuf为4173字节。缓存预算显式配置512 MiB，后台维护仍为原专项的200 ms / 32 MiB / 32 MiB。

这个整存业务修改revision和bio尾字节，再编码整份档案；它不是每次将全部4 KiB替换成完全不同内容。更换大量字节的业务不应预期相同收益。所有组使用相同业务和配置，没有调整阈值、提前确认规则或最终持久化步骤；编译与测量没有并行运行，其他数据库没有重测。

先做四个约0.6秒样本，只有差量开启时出现明显收益：

| 方案 | 吞吐 次/秒 |
|---|---:|
| 当前生产库 | 49,636 |
| 同候选库关闭研究开关 | 63,728 |
| 同候选库只缓存旧值 | 54,462 |
| 同候选库缓存并生成多段差量 | 152,148 |

第一组波动较大，不能据此把15.2万当作稳定水平，也不能将换候选二进制后的差异全部归因于差量。随后才对生产、候选关闭、差量开启各做三轮约1秒交替顺序复测。

## 持续写入边界：收益收窄

考虑到日志、差量链及后台维护状态会随写入增长，再做两个约4秒对照，第二组反转执行顺序：

| 顺序 | 生产库 次/秒 | 多段差量 次/秒 | 吞吐增幅 | 生产P99 | 差量P99 |
|---|---:|---:|---:|---:|---:|
| 生产→差量 | 68,932 | 72,464 | +5.1% | 3.064 ms | 1.179 ms |
| 差量→生产 | 67,322 | 80,799 | +20.0% | 3.333 ms | 1.290 ms |

这两组仍然正确持久化，磁盘写入量均明显减少，但没有保持三轮短测约1.92倍的吞吐。持续场景的CPU用核从约0.74增加到1.13～1.19，按每次业务计算的CPU时间也增加；优化已不能仅用“刷盘次数减少多少”推算吞吐。

缓存比较、结果保留、差量链读取和后台维护都有可能参与成本，目前没有采样证据将收窄归因到某一个函数或锁。4秒只是比1秒更长的边界探针，不是长时间稳定性压测。下一步应针对持续负载定位等待及维护成本，再决定正式接入，不能宣称整存已稳定翻倍或已全面超越其他数据库。

证据：[持续对照](../build/multi-save-20261110/sustained-report.json)、[反转顺序](../build/multi-save-20261110/sustainedreverse-report.json)。

## 审查修正后的最终点测

审查发现，同一事务第二次单段patch回退成put后可能仍保留旧offset/remove；若进一步转成multi，这些旧字段必须清零，否则会生成恢复校验不接受的日志。已经修正，并通过先强制建立完整基值、再在同一事务做两次远距离patch的针对性检查。

首版源码/库及所有原始测量保留为attempt1；上面的三轮及两组4秒表对应首版。最终库重新构建、补充正确性探针后，只补测直接相关的1秒与4秒各一对，没有重新机械运行整套矩阵：

| 条件 | 生产库 | 最终原型 | 变化 |
|---|---:|---:|---:|
| 1秒吞吐 次/秒 | 59,904 | 91,066 | +52.0% |
| 1秒P99 | 3.364 ms | 1.292 ms | -61.6% |
| 4秒吞吐 次/秒 | 70,667 | 71,781 | +1.6% |
| 4秒P99 | 3.069 ms | 1.383 ms | -54.9% |
| 4秒cgroup写入字节/业务次 | 4,624 | 798 | -82.8% |
| 4秒CPU用核 | 0.737 | 1.122 | 增加 |

单次点测不能证明稳定的52%收益，4秒的1.6%也可能处于波动范围；吞吐收益收窄的问题仍在。修正针对日志语义边界，不应将两版短测差异直接归因于这一处修正。最终候选库SHA256为 `fe9a09b0a91b768a1848e0d862ba790056c58c0a043ff894eaace34bf16b7731`。

证据：[最终点测](../build/multi-save-20261110/finalcheck-report.json)、[最终边界探针](../build/multi-save-20261110/probeedge-report.json)。

## 正确性、审查和交付范围

原型检查覆盖普通及分段布局、多处修改、差量深度回退、完整替换、长度变化、相同值覆盖、禁用缓存后的冷重开及进程立即退出后的恢复；逐条扫描历史日志并无缓存还原，核对最终CRC。补充固定种子的随机1～12处修改，覆盖事务写入及多键、旧共享值不变、数据库verify、完整备份、整理及重开。

最终探针通过，基础探针实际扫描到48个多段记录。两版共21个业务测量样本的结果和独立进程重开校验通过，最终版本均已持久化，无重试。这里只做了Linux隔离原型验证，没有Windows/移动端验收、全量回归、Sanitizer资格验证或物理掉电试验，因此没有把实验代码合入生产。

首次构建的库成功，但探针误用了不存在的默认配置函数而编译失败；修正探针后复用同一库完成验证，失败报告保留。源码、候选差异、二进制哈希和容器/卷所有者核对清理见 [最终审计](../build/multi-save-20261110/final-audit.json)。主源码171文件哈希与本轮开始时完全一致。
