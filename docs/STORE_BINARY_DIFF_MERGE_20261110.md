# 公共二进制差异内核与整存接入（2026-11-10）

公共内核和受限多段差量已接入主引擎。完整写入汇合到提交入口后，机会性复用缓存旧二进制并生成差量日志；明确指定范围的patch继续使用已有减法裁剪。默认仍为**性能模式50 ms / 1 MiB**，可靠模式、单次强制可靠、原子发布和周期刷盘阻塞没有改变。

## 接入范围

| 路径 | 当前处理 |
|---|---|
| 单条put、事务put、原子批量及经事务提交的集合/索引值 | 在公共提交入口统一判断是否适合差量，不在各语言接口重复实现 |
| put_if_changed | 复用公共精确相等判断；相等时沿用原来的不提交语义 |
| 底层预留页空图像比较 | 复用公共精确相等判断，任一字节不同仍完整初始化 |
| 显式单段patch | 已知修改范围，直接裁剪/覆盖，不增加差异扫描 |
| 键排序、文件身份、CRC和格式校验 | 保留各自的语义；不以一个有预算的差量计划代替完整相等或顺序判断 |

`src/binary_diff.hpp`提供无分配的比较与差量计划，`src/paged/wal.hpp`负责缓存基值校验和一次性编码，`src/paged/core.hpp`统一接入。生产代码不保留实验环境变量、旧逐字节算法或实验切换分支。

## 为什么比较更快

旧原型已经会跳过相同64字节块。这次进一步按8字节机器字定位变化，避免对变化区域逐字节长循环；通过memcpy读取机器字，兼容不对齐地址和严格别名规则，不依赖特定SIMD指令集。

计划使用固定容量数组，最多8段。只接受同长度的1～64 KiB覆盖；编码载荷预算为完整值四分之一与1 KiB中的较小者，包含4字节段数、每段8字节描述及新字节。发现片段过多或预算不足立即返回完整写入方案，在确认可用之前不分配、不复制差量载荷。接受后只精修变化段的首尾，再一次性分配编码缓冲。

连续密集变化时会提前退出；变化少但位于尾部或遍布全文时，仍需要实际检查全部可能复用的字节。预算失败只表示选择完整写入，不能当作“值相同”。较保守的预算也可能错过一些可压缩更新，因此不承诺所有变化形态都更快。

## 缓存、日志和恢复

只有既有值缓存命中的旧值才参与比较，检查长度、CRC和配方标签；不会为了发现差量额外读盘。重复覆盖的有界大小值可进入既有预算缓存，首次插入不因这一优化填充读取缓存。缓存关闭、冷值、变长、变化密集、片段过多或差量链达到8层时完整写入。

内存仍保留完整私有二进制及不可变共享结果。完全相同的整存可复用原存储位置，仍按原put语义产生新版本；需要相同值不产生提交时继续使用put_if_changed。多次patch回退put后转为多段日志时，会清除旧单段offset/remove。

WAL新增内部操作种类5，记录基值引用和多个变化范围。读取及恢复在基值上直接覆盖变化段并检查完整结果CRC；回收遍历保留整个基值依赖链。备份/整理继续生成可独立读取的完整内容。请配套使用当前核心；历史实验文件和旧开发二进制不是新增日志格式的兼容承诺。

周期/字节触发仍统计真实逻辑WAL字节及帧开销。每笔日志变小后，同一阈值可能容纳更多业务操作；50 ms仍是调度目标，强制可靠仍同步此前完整前缀。

## 最终内核小测

同一个比较程序、GCC -O3、Linux固定CPU、热缓存旧值，包含缓存查找和成功时的差量编码。旧算法来自上一轮冻结原型；新算法来自最终主源码。两种实现各通过1800组随机修改的完整还原核对，另有正式2000组含不对齐视图的内核测试。

| 输入 | 原型旧算法 | 当前主内核 |
|---|---:|---:|
| 4173 B，两处稀疏变化 | 166.7 ns | 100.8 ns |
| 4173 B，整份变化后回退 | 818.5 ns | 157.7 ns |
| 64 KiB，两处稀疏变化 | 1432.4 ns | 1040.1 ns |
| 64 KiB，整份变化后回退 | 12219.4 ns | 160.1 ns |

64 KiB密集变化约快76倍，主要来自更早放弃。这个数字只属于比较/计划/编码的小测，不代表数据库整体快76倍，也不能代替移动芯片实测。

证据：[最终内核对照](../build/multi-save-main-20261110/microfinal2-report.json)。

## 最终主引擎整存对照

沿用服务器业务驱动及镜像、Linux原生命名卷、CPU 0/2、2 vCPU/4 GiB、4096份档案、固定Zipf轨迹和显式512 MiB缓存预算，后台维护保持200 ms / 32 MiB / 32 MiB。每调用线程仅一笔在途，包含业务编解码、最后Sync及独立进程重开验证。没有并行编译或其他性能测试，没有重跑竞品。

4 KiB简介、8线程完整保存，三轮约4秒，交替执行顺序：

| 指标，中位值 | 接入前主引擎 | 当前主引擎 |
|---|---:|---:|
| 吞吐，业务次/秒 | 70,284 | 93,067 |
| 三轮范围 | 66,292～72,050 | 78,250～102,526 |
| P99 | 3.073 ms | 1.191 ms |
| 每秒同步次数 | 286.8 | 56.4 |
| cgroup写入字节/业务次 | 4615 | 772 |
| 测量容器CPU用核 | 0.724 | 1.206 |
| 测量容器峰值内存 | 392.3 MiB | 246.6 MiB |

吞吐约提高32.4%，P99约降低61.2%，每次业务对应写入量约减少83.3%。CPU使用增加；容器内存包含文件缓存，cgroup字节不等于SSD内部物理写入量。这项业务每次编码完整档案，但实际只改revision和简介尾字节，不能推广到全部字节随机变化的业务。三轮4秒仍不等于长期压测。

另做两个单对约0.6秒边界：4 KiB/1线程95%读、5%小字段更新为1,495,110→1,522,180次/秒，P99为2.545→2.615 μs；128 B/8线程一次读32份为255,643→253,744批/秒，P99为20.780→23.475 μs。批读吞吐接近，P99有波动，不宣称全部指标都改善。

证据：[最终10样本](../build/multi-save-main-20261110/final2-report.json)。当前未重跑完整72样本或其他数据库，历史排名不能直接当作本次全量结论。

## 持续收益收窄的研究

隔离诊断在同一候选二进制上比较旧/新算法：开启既有后台维护时4秒吞吐波动明显；关闭维护时分别为141,787和143,178次/秒。它说明维护路径参与了成本，不能单靠比较算法推算整库吞吐。关闭维护仅是诊断，未作为生产配置或主排名使用。

另试差量链上限8、2、1，没有形成明确的综合改善；更浅的链带来更多完整写和更高P99，因此最终仍为8。没有改写后台维护策略、关闭维护或提高刷盘阈值来制造收益。具体维护步骤的耗时占比尚未做采样归因。

证据：[维护诊断](../build/multi-save-fast-20261110/diag-report.json)、[限深探针](../build/multi-save-fast-20261110/depth-report.json)。这些对应隔离源码，不混算到最终主引擎数字。
