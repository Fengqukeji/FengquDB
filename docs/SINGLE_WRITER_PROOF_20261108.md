# 单线程累计写入与可靠合批：最小验证

按用户要求，本轮使用**一个应用线程累计和执行全部写入，没有后台写线程**。4 KiB 简介档案完整保存，1 MiB / 100 ms 的三轮吞吐中位数为 **52,996.4 条/秒**，范围 49,242.4～54,473.4 条/秒。诊断采样也确认被测进程始终只有一个操作系统线程。

相比此前报告的 8 线程 5,822.97 条/秒，约为 9.10 倍；相比此前 64 线程自然合组的单次样本 27,216.6 条/秒，约为 1.95 倍。这是与历史结果的对照，尚未证明完整生产 SDK 能直接得到相同提升。

## 实际处理方式

同一个线程连续生成、编码并累计待确认写入。累计业务字节达到阈值，或本批等待时间到，立即顺序处理这一批；每笔写入保留独立 WAL、版本和结果，整批共享刷盘，刷盘成功后才计为可靠完成。不是将252笔改成只有一个版本的原子事务，也不把内存接收计为提交成功。

原型复用主引擎的 `CommitWaiter.prepare/cleanup` 和 `Core::drain_group`。私有事务在写者中按前一笔待发布视图创建，执行完整 put，日志借用结束后释放；这也支持一批内重复写同一个键，避免用共同旧快照制造额外冲突。每笔完成前核对版本已经进入 durable 水位。

32 KiB 约为8笔、64 KiB约16笔、256 KiB约63笔、1 MiB约252笔；笔数由实际编码大小决定。本轮沿用核心最多256笔的处理边界，没有扩大主引擎上限。若核心因自身索引边界拆组，所有额外刷盘也会计入。

这种入口允许同一线程先积攒多笔**未确认**请求，再统一取得可靠结果。现有逐条阻塞 `Commit()` 在返回前必须完成本笔，无法积攒尚未调用的下一笔。因此后续 SDK 需要批次提交或待确认请求入口，才能使用这种处理方式；本轮没有修改公共 API。

## 单线程向上扫描参数

相同4096条十字段档案、4 KiB简介，复用业务基准的 Protobuf 编码、固定种子和单线程 Zipf 轨迹。Linux Docker，两个指定 vCPU（0、2）、4 GiB、无额外 swap；被测程序只使用一个线程。每项计划1秒，按真实时间统计，序列化、请求准备、日志写入、刷盘及尾批都在计时内。

| 字节阈值 | 等待1 ms，条/秒 | 等待10 ms，条/秒 | 等待100 ms，条/秒 |
| --- | ---: | ---: | ---: |
| 64 KiB | 9,989 | 9,700 | 9,467 |
| 256 KiB | 26,691 | 25,739 | 25,790 |
| 1 MiB | 54,193 | 53,757 | 52,931 |

另保留两个控制：32 KiB / 50微秒约5,037条/秒；单线程逐笔可靠刷盘约1,468条/秒。第一次两例机制验证中，逐笔刷盘1,476条/秒，1 MiB / 100 ms为56,370条/秒；没有将这次最高值作为最终成绩。

这说明上一轮5,823条/秒没有代表单线程集中合批的能力。在本轮压力下，大阈值比32 KiB有效；等待时间从1 ms增到100 ms没有明显额外收益，因为1 MiB通常在1 ms以内就凑齐，先由字节条件触发。低频输入是否达到最长等待后及时处理，仍需要宿主事件循环或等待机制配合；本压力原型在收集循环中检查期限，停止时显式处理尾批，没有实现空闲时的独立定时器。

## 三轮复测

固定参数后正反顺序复测，每项计划2秒。

| 单线程配置 | 吞吐中位数，条/秒 | 三轮区间 | 抽样P99中位数 |
| --- | ---: | ---: | ---: |
| 32 KiB / 50微秒 | 4,974.07 | 4,953.91～5,009.53 | 3.65 ms |
| 1 MiB / 1 ms | 52,768.50 | 52,146.60～54,745.60 | 6.53 ms |
| 1 MiB / 100 ms | 52,996.40 | 49,242.40～54,473.40 | 6.94 ms |

另一个2秒逐笔刷盘控制为1,396.04条/秒，不混作三轮中位数。1 MiB两种时间配置的6个样本全部由字节条件触发，平均每次刷盘252笔。两种等待时间的吞吐差约0.43%，不足以证明100 ms更好。更大的批量提高吞吐，也使单笔可靠确认延迟上升；100 ms在低流量下仍可能成为实际等待时间。

## 核验与适用边界

本轮共25个单线程样本：2个机制验证、11个扫描/控制、10个复测/控制和2个诊断。全部通过全字段模型核验；再以独立进程、当前生产共享库读取同一目录和期望模型，验证格式兼容及重开结果。每个样本还核对业务完成数、独立事务数、版本增量和 durable 水位一致，以及事务/快照资源释放。没有省略中间写入或仅保留同键最终一笔来取得成绩。

两个诊断样本分别获得55次进程线程采样，最小值和最大值均为1；性能表不采用带探针的样本。I/O探针覆盖程序生命周期，包含初始化和检查点，不能将其累计耗时直接当作精确的计时阶段分解。

原型在 `build/sync-submit-research-20261108/single_writer.cpp`，以同一份主引擎源码静态链接，并从内部提交入口执行；后台维护关闭。之前多线程数字来自共享库外部接口及其维护配置，访问线程的分区方式也不同。因此本轮证明的是单线程累计与可靠合批的有效性，尚未完成公共接口接入、长期自动整理、取消/超时和故障注入验证，也不构成所有负载的性能保证。

主引擎82个受保护构建输入保持不变，实验未合入。源码、二进制、负结果和报告保留，所有本轮自建容器及卷核对所有权后移除。
