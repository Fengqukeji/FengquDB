# FengquDB 产品与技术规格

状态：1.0.0 使用分页 Store 引擎，全局 ABI 2。本文描述当前默认行为及产品边界；0.1/0.2 原型的实现与实验见 [历史索引](history/README.md)，不能当作当前接口契约。具体调用以 [Store API](STORE_API.md)、[写入策略](STORE_WRITE_POLICY.md) 和 [复杂查询](STORE_SELECT.md) 为准。

## 产品定义

FengquDB 是面向游戏、本地工具和嵌入式应用的轻量级、高性能、可恢复的原生 C++ 非关系数据库引擎，以可嵌入库文件交付。业务程序在自己的进程中调用统一 C ABI；提供 C++17 RAII 接口及 C# P/Invoke、Java JNI、Python ctypes 适配。库负责数据持久化、并发一致性、事务及基础索引，上层可独立构建 Wiki、RAG、项目 AI 索引等能力。

不要求安装数据库服务器、使用网络协议或维护单独的数据库进程。Java JNI 是语言适配库，不是另一套数据库实现。静态链接也应可选。

Protobuf 是编码格式，不是数据库算法，也不是压缩算法。它不会自动提供事务、索引、缓存、持久性、加密或检索。数据库文件无需所有字节都是一个 Protobuf message：文件框架、索引页面、页校验和对齐应以可恢复和高效访问为准；核心语义记录保持 wire 格式。

## 性能目标的专业表述

“极尽优化、尽量超越现有方案”是研发方向，不能写成“所有场景全面最快”的验收承诺。数据结构、读写比例、数据规模、排序扫描、内存占用和刷盘频率存在取舍。目标是在选定的嵌入式重点负载中形成可复现的性能优势，同时给出不占优势的负载。

重点负载：小值主键命中/未命中、热点混合读写、多记录原子更新、按前缀/范围扫描、按帧追加回放命令及定期状态快照。测试覆盖不同线程数、键/值大小、数据规模、热点分布和超内存数据集。

每份报告至少包括：每秒操作数、P50/P95/P99/必要时 P99.9 延迟、可靠提交延迟、CPU、常驻及峰值内存、数据库文件大小、写放大、恢复时间、发布包大小；注明硬件/文件系统/系统/编译器/版本/参数/随机种子/样本量。短小微基准不证明长时间生产表现。

Redis 比较应区分两类：

* 应用端到端延迟：进程内调用可节省 Redis 跨进程、协议与调度成本，可能明显更低；报告须说明比较包含这些成本。
* 数据结构与持久性：单独比较内存查找成本；写入严格匹配 Redis 持久化配置与事务语义。缓冲写入不能对比对方逐笔可靠刷盘。Redis 的数据类型、生态与服务端能力不等同于本项目范围。

SQLite、LMDB、LevelDB 等也要按匹配的同步保证、事务批量、读写线程和结果消费方式比较。不得从自测吞吐推导已经超过某个未实际参测的数据库。

## 内存与缓存架构

当前使用分页磁盘索引，页和值按需加载，适用于存活数据超过缓存的场景。缓存、增量元数据、事务、固定值/快照和查询工作内存分别受预算约束；这些不是宿主进程 RSS 的硬上限。默认缓存按需增长，超额按缓存和对象所有权规则淘汰或明确报错。

完整私有二进制缓冲和减法裁剪用于增量修改，整值保存可有界识别差量并保守回退；这些优化不改变事务原子性和持久化保证。显式全内存专用数据库尚未提供，性能模式仍会写 WAL 并周期同步。

生产缓存应有容量预算、命中/淘汰统计和快照固定内存统计。不可淘汰仍被快照/事务引用的数据；超出预算需明确背压或限制长事务。提交发布新版本时维护缓存可见性，回滚不泄露写入。序列化字节缓存属于底座；语言对象缓存通常属于应用，必要时通过提交版本失效。

## 并发与持久性边界

当前采用进程内并发读、串行提交，事务固定快照，验证点读/写集和已登记扫描范围。缺失键、删除版本和范围依赖参与冲突检测，支持读自己的修改、保存点和范围/索引查询。冲突后须重开事务、重读重算；不能将业务重试视为单线程程序错误。

性能模式由数据库专用写线程执行请求，内存原子发布后同步接口或异步凭据即可确认；周期到达或待刷 WAL 字节达到阈值时可靠同步。新库和没有 WRITE 配置的目录默认 50 ms / 1 MiB，已有配置继续加载，reset 恢复当前默认。没有待刷内容时休眠，不按周期空刷盘。50 ms 是调度目标，不是掉电损失的严格时间上限。

可靠模式和单次 force_reliable=true 均须等待事务及其依赖的此前完整提交前缀可靠同步成功。多个提交可共享刷盘，成功仍以各自的持久化水位为准。显式 BUFFERED 保留手动 sync 语义，独立于默认模式开关。

性能模式下，进程崩溃或断电可能丢失已经在内存确认的未同步后缀。后台同步失败封锁后续写入，保留故障状态；已有内存视图和外部业务副作用不会自动撤销。写入开始后的失败可能返回 COMMIT_UNKNOWN，重开后由应用按业务操作 ID 核对，不能盲目重试非幂等业务。关键付费操作应在强制可靠成功后再发送外部副作用。

恢复仅应用完整、校验通过的事务。未完成的日志尾部可截断；完整但校验失败的记录须报告损坏，不能悄悄删除并宣称恢复成功。设备损坏、磁盘满、权限变化、文件系统错误和真实断电需要独立测试。已成功执行系统刷盘不能证明设备没有虚报完成。

检查点/压缩整理必须具有原子切换与崩溃恢复方案，并保留快照/增量消费者所需的数据。备份不能直接复制一个正在写入的文件并假设一致。初期不支持多进程共享同一文件、网络文件系统、分布式事务或自动故障转移。

## 引擎分层与扩展

* 内核：平台文件 I/O、日志、校验、恢复、版本管理、事务、内存管理与基础键索引。
* 编码：有限 wire 编解码、版本化存储记录；业务 Protobuf schema 由应用/上层模块管理。
* 访问：C ABI、薄语言适配、批量与迭代接口；不暴露 C++ STL 布局给其他语言。
* 可选模块：字段二级索引、全文倒排、向量索引、文档解析、Embedding、RAG 检索与 Wiki 领域模型。各模块单独衡量体积与依赖，不强制进入核心。

RAG 检索质量和 Wiki 业务规则不属于存储引擎的性能保证。向量索引与全文索引需要定义提交后何时可查询：同事务强一致或明确异步水位。
