# 分段候选的吞吐、语言调用成本与包体审查

本轮完成隔离候选的实测，没有合入主工程或更新发布包。候选热读取吞吐接近当前核心，但单条、批量并发写入仍有回退，不能据稳定性检查通过就采用。向量检索、全文检索和 RAG/Wiki 仍留待以后设计。

证据目录：`build/segment-cost-lab-20261107/`。`summary.json` 汇总全部分组、三轮范围、抽样 P99、进程 RSS、文件逻辑/分配大小及后台状态。核心复用 SDK 批次已验证的二进制；主工程 114 文件、SDK 137 文件均重新核对 SHA256，保持不变。

## 原生吞吐

Linux Docker 固定两个物理核心对应的 CPU 0、2，4 GiB，无额外 swap，数据写入独占命名卷；计时期间不并行构建。三个方案使用同一 EXE、公开 C ABI 和相同配置：当前 Root4 核心、候选单文件布局、候选分段布局。每项预填 32768 条，8 个调用线程，预热 0.2 秒、计时 3 秒，三个轮次轮换方案顺序。

以下均为 **buffered 模式的记录/秒中位数**，不是每条强制刷盘的结果。批量每次 32 条；mixed95 是 95% 读、5% 写。每轮先执行完整字节模型核对和进程内重开，再由独立进程重开核对，72/72 项通过。4 KiB 分段用例预填后均至少三个数据文件，使用真实 64 MiB 段容量。

| 值大小 / 操作 | 当前核心 | 候选单文件 | 候选分段 | 分段相对当前 |
| --- | ---: | ---: | ---: | ---: |
| 256 B 复制读取 | 3,692,747 | 3,863,686 | 3,786,017 | +2.53% |
| 256 B 单条覆盖 | 61,772 | 51,082 | 44,898 | -27.32% |
| 256 B 批量覆盖 | 434,183 | 366,600 | 344,915 | -20.56% |
| 256 B mixed95 | 1,785,662 | 1,827,786 | 1,770,393 | -0.86% |
| 4 KiB 复制读取 | 2,059,561 | 2,107,765 | 2,072,534 | +0.63% |
| 4 KiB 单条覆盖 | 34,212 | 22,906 | 21,778 | -36.34% |
| 4 KiB 批量覆盖 | 128,363 | 118,013 | 110,760 | -13.71% |
| 4 KiB mixed95 | 644,208 | 670,110 | 628,005 | -2.52% |

尾延迟也有退化：4 KiB 单条覆盖的 P99 中位数为当前 4418 μs、候选单文件 14776 μs、分段 10381 μs；256 B mixed95 为 74.2、123.1、122.4 μs。另一些批量 P99 更好，全部原始值保留，不以其中一项代表全部负载。

候选单文件包含 Root5 回收及新的文件门面，并非只改变根格式的对照。4 KiB 单条覆盖中，候选三轮各完成一次后台回收，当前核心均为零；不能把累计回退全部归因于分段映射。相同候选的分段相对单文件吞吐仍低约 1.7%～12.1%，不同回收时序也须纳入后续定位。

本轮分段数据文件最大 **67174400 B**，名称最长 **30 字符**；短样本没有解决长期文件数量、逻辑偏移和标记内存的边界。RSS 和文件分配快照也不能直接当作节省比例，因为各方案在相同时间内完成的写入量不同。cgroup peak 为整个容器的累计峰值，含构建，不用于方案之间的内存比较。

## 语言调用成本

Windows 同机使用一套基准程序和最终 SDK 绑定，分别加载当前核心及其 JNI、候选单文件、候选分段。载荷为同一份 4176 B 业务 Protobuf 字节，每种语言 32 个热键；三轮交替语言与方案顺序，单条一百万次，批量每次 32 条。启动、样本写入、数据库校验与重开不计时；序列化和反序列化不在本轮测量内。

36 个程序合计 **126 组测量**，校验和、完整返回字节及另启 Python 进程重开均通过。Java 吞吐运行不启用 JNI 检查，相关生命周期与去符号包体验证另用 `-Xcheck:jni`。C# 与 Java 的被测应用分别为 .NET 10 和 Unity 附带 JDK 11；这些不是 Android/iOS 或 IL2CPP 的性能数据。

| 复用路径 | 当前核心次/秒 | 候选分段次/秒 | 变化 |
| --- | ---: | ---: | ---: |
| 原生准备键 / 目标缓冲 | 11,330,400 | 11,066,000 | -2.33% |
| Python 固定 bytearray | 902,534 | 902,840 | +0.03% |
| Java direct ByteBuffer | 7,458,312 | 7,533,711 | +1.01% |
| C# 准备键 / byte[] | 9,234,369 | 8,771,599 | -5.01% |

候选分段下，Python、Java、C# 的复用吞吐约为同语义原生的 8.2%、68.1%、79.3%，仍有语言和 FFI 成本。C# 准备键复用路径三种布局均测得每次 **0 B 托管分配**；普通复制读取每次 4200 B。分段下 Python 固定缓冲比同轮原 `get_into` 约快 33.3%，Java direct 比 byte[] 复用约快 40.1%。

C# 复用的当前核心三轮为 9.175～9.239 M/s，分段为 8.182～9.009 M/s，保留约 5% 的中位数回退，不认定全部只是噪声。Python 批量相对当前约 -3.0%，普通复制约 -0.24%；其他路径与范围见报告。新分段选项只影响打开并不构成运行零回退的证据。

这组热键始终位于首段，目的在于测语言边界和分配成本；它不证明冷值、多段随机读取、并发或写入的语言性能。先前 SDK 批次的真实多段语言检查提供正确性证据，不补作本轮性能数据。

## Linux 包体

保留完整原 ELF，仅在副本上执行 `strip --strip-unneeded`；此操作减少符号等磁盘内容，不改变运行代码。当前基线由同一镜像以 Release、IPO、诊断关闭配置重建；候选复用此前相同核心配置的 SDK 产物。

| 二进制 | 完整 ELF B | 副本去符号后 B |
| --- | ---: | ---: |
| 当前核心 | 919032 | 781840 |
| 候选核心 | 994656 | 843304 |
| 候选 JNI | 101624 | 85160 |

候选核心副本减少 151352 B，约 15.2%；与同样去符号的当前核心相比仍增加 61464 B，约 7.9%。候选 `.text` 比当前增加 56256 B，异常展开与异常表也有增长，不能只靠去符号消除累计代码增长。两核心导出均为 134 行，三个产物去符号前后导出名称完全一致；候选核心依赖 libstdc++、libgcc_s、libc 和动态加载器，没有引入 Protobuf 运行库。

去符号副本通过三种布局各一次准备、自检和独立重开，共九条运行命令；去符号 JNI 通过单文件、分段两次 Java 读写检查。它们仍是隔离产物，没有覆盖正式包或追加发布安装步骤。

## 失败记录与结论

`linux-native-report.json` 整体保留 false：其 72 项测量和重开全部成功，之后的副本自检漏做 prepare，因缺少预期模型中断。只补跑包体检查，没有重跑吞吐。`linux-package-report.json` 保留后续失败：三组导出比对及九条原生检查成功，但 Java 运行目录漏放 `libfengqudb.so` 标准别名，未进入业务程序；补齐别名后 `linux-package-final-report.json` 的两条 Java 命令成功。这两个问题属于本轮测试编排，不能算数据库故障，也不能把失败报告改写成全绿。

最终汇总、源码保护、原二进制哈希与自有容器清理状态见 `final-audit.json`。本批没有修改数据库核心、0.3.1 完整私有二进制缓冲或减法裁剪。后续两个文件层提案、54 项 Linux 对照和 54 组原生/C# 热路径复查见 [写入精简对照](STORE_SEGMENT_WRITE_REVIEW_20261107.md)；小值写入有所提升，4 KiB 批量与尾延迟仍有回退，均未采用。

仍须定位写入和 C# 复用变化，完成新格式实际磁盘/内存异常、长期资源边界、受影响功能组合及最终五方案比较。稳定性和部分热读结果不足以支持当前采用或普遍性能领先的结论。
