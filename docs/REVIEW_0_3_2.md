# 0.3.2 优化与代码审查

日期：2026-11-06。本轮在 0.3.1 基础上减少分配、查找和编码元数据，并审查缓存所有权、失败原子性、历史回收和 Protobuf 恢复边界。C ABI 仍为 1，文件格式和普通写入事件语义保持不变。

## 优化内容

- 普通 put 覆盖事务独占值时复用 ValueBytes 和字符串容量，完成后清除缓存 CRC。共享值必须先隔离；缩小到容量四分之一以下的大缓冲仍重新压紧。put、patch 共用独占判断和准备写集物化函数，避免两处安全条件漂移。
- 向非空事务合并准备批次时共享拥有的不可变值，避免再次复制整值。重复应用同一个准备对象直接复用；同值派生仍分配独立句柄，但共享原准备数据和编码缓存。普通提交仍增加版本和变更事件。同值判断本身需要比较值字节，不是整个接口 O(1)。
- 连续 patch 只有在显式检查期望版本，或首次构造增量日志时才查基础索引。独占暂存值的后续编辑不再重复走树；提交时仍执行原有冲突检查。结果预算在构造新值之前检查。
- 编码头按可证明的 varint 上限确定容量，从每操作 110 字节降至 51 字节，减少约 53.6%。仅写入和读取实际使用区间，移除整块重复清零；最大键 64 KiB、最大值 16 MiB 与增量偏移经过运行校验。该比例仅指分段编码头，不代表全库内存减少相同比例。
- 历史裁剪在发布锁内更新预算和摘链，批次释放移到锁外，缩短阻挡读者的临界区。没有改变历史窗口或活动游标固定数据的语义；未单独宣称该项有多少吞吐收益。
- 基准版本标签不再写死，支持选择缓存场景并约束标签为安全目录名，复用现有程序和校验逻辑。

## 审查修复的实际问题

官方 proto3 对全零 CheckpointSeal 的规范编码为零字节。0.3.1 同时要求载荷非空和三个字段显式存在，因而将一个合法的 88 字节空格式2检查点返回 CORRUPT(5)。修改前用 protoc 36.2 生成消息并复现，证据在 artifacts/review-before-0.3.2.json。

0.3.2 允许基线结束seal载荷为空，省略字段按零解释，仍核对实际条数、chunk数和CRC。普通空事务、空chunk、错误计数/CRC、截断字段和未完成基线仍拒绝。内置写出格式未改变，旧版本仍能读取本库导出的检查点。新回归用例覆盖打开空基线、随后追加、关闭重开，以及错误seal不修改原文件。

审查还核对了原地写入的可变分配来源、共享引用计数、准备对象生命周期、修改前预算、异常后字节/日志元数据、CRC失效、编码头长度以及历史批次在读者持有时的释放。未发现需要保留为已知未修复的功能缺陷；这不等同于证明所有输入和硬件故障均无缺陷。

## 针对性性能实测

同机 Windows 11、Ryzen 9 9950X3D，Release x64。使用相同 EXE 和 SQLite 3.54.1 DLL，按场景交替加载 0.3.1/0.3.2 Core；3轮中位数，固定 0x5555 亲和性，计时期间不编译。原生基数10万键、256字节，缓存场景基数1万键。全部输入预先生成、预热，所有最终键值关闭重开后验证。SQLite 使用 WAL FULL 或 NORMAL+最终检查点，可靠性与既有基准一致。

缓存写使用缓冲模式并计入最后 sync。private_full/private_patch 每笔对同一个100 KiB值连续修改100次，包括首次隔离、最终整值日志和提交；其余缓存场景每笔处理100个256字节值。merged_batch 先放入额外键再合并准备批次；repeat_batch 每笔应用同一批次两次；prepared_noop 派生与原值相同的准备批次。准备对象首次构造成本另外记录。

收益集中在重复数据处理：合并准备批次约13.6%、重复批次约53.5%、同值派生约17.6%、连续整值暂存约16.1%、连续patch约19.3%。单次准备派生约低1.2%，普通可靠批量短样本低约3.3%，缓冲单写首轮低约7.8%。所有低值均保留，没有挑选最佳值或宣称全路径加速。

对缓冲单写的负值，进一步用相同最终DLL、单个固定核心0x1、每轮10万次、交替5轮复查：0.3.1为238,773次/秒，0.3.2为235,903次/秒，约低1.2%；中位CPU时间0.40625→0.421875秒，受Windows约15.625ms时钟量化限制。原生单写中位延迟3.9→4.0微秒。不能将首轮7.8%直接视为稳定代码损耗，也不能断言1.2%已经是统计显著差异。

独立阶段探针：单条暂存0.149→0.153微秒，单条编码/CRC 0.124→0.106微秒，100条暂存21.64→21.50微秒，索引准备49.38→48.16微秒。没有发现与首轮墙钟负值同量级的阶段退化。阶段探针直接包含源文件，并不等同于实际DLL完整提交时间。可靠批量的约3.3%短样本低值尚未证明固定成因，不把它抹成零。

Windows Core DLL 280,064→281,088字节；Linux stripped SO 183,272→187,360字节。包体略有增加。全库驻留索引、活动快照和准备数据仍有原有成本，没有引入全库内存限额或超内存分页。

SDK：artifacts/release-0.3.2/windows-x64 与 linux-x64，各含 static 子前缀；0.3.1 SDK与基线保留，没有改动参考工作区、提交、推送或生成ZIP。详细验证见 artifacts/validation-0.3.2.md，文件和源码指纹见本版本 manifest.json。

原始证据：artifacts/regression-0.3.2/comparison.json（72组），artifacts/buffered-paired-0.3.2/comparison.json（15组），artifacts/write-profile-0.3.2.json（阶段测量），artifacts/languages-wire-0.3.2.log。使用 tools/run_regression_comparison.py 的 --baseline-label 0.3.1 --current-label 0.3.2 --native-case batch100_sync --native-case update_buffered --affinity 0x5555 可复现本轮场景。
