# 自适应等候接入前的性能模式服务器业务专项（2026-11-10）

版本说明：本报告的72个样本对应自适应短等候接入前的源码，表格保留为历史证据。当前主引擎的定向复测见 [自适应等候报告](STORE_ADAPTIVE_WAIT_20261110.md)，本次没有重跑完整矩阵。

该版本 FengquDB 已完成 24 种条件各三轮，共 72 个样本。全部业务结果和独立进程重开校验通过，全部最终版本已持久化。吞吐中位值在 21/24 项高于下表全部历史常用方案；按约 5% 的实用接近范围区分，21 项领先、1 项接近、2 项落后。这个范围不是统计显著性检验。

## 口径

沿用之前服务器专项：同一镜像，Linux 原生命名卷，CPU 0/2、2 vCPU、4 GiB，无额外 swap，4096 份十字段 DTO，Zipf(0.99)、相同轨迹种子。简介 128/4096 B，初始化 Protobuf 205/4173 B。三组为 4096 B/1线程、128 B/8线程、4096 B/8线程，每条件约1秒。每个调用线程仅一笔在途，计入业务编解码、重试和最终可靠 Sync。FengquDB 使用最终主代码、性能模式 50 ms/1 MiB，启用后台维护 200 ms/32 MiB/32 MiB；数据缓存预算沿用该专项的显式512 MiB配置，库默认缓存仍为64 MiB，实际占用按需增长。

其他数据库全部沿用历史实测，未重新运行服务。主表使用历史 BUFFERED（非逐笔刷盘）数据，包含 SQLite 普通表、JSON文本、JSONB、MySQL、Redis、MySQL+Redis，避免用逐笔可靠写列与性能模式混为同一保证。各产品持久化周期不同；非同期测量也不能提供严格同场硬件负载对照。此处比较的是指定业务的吞吐和响应延迟，不能证明所有数据库能力、所有负载或相同可靠性下全面领先。SQLite protobuf存储不列入“常用业务方案”主排名，原历史数据保留。

batch32 是一次读取32份完整档案，不是32条原子批量写。C++原生业务驱动的结果也不能直接代替 C#/Java/Python DTO 调用性能。本轮保留完整私有二进制缓冲与减法裁剪，未调整写入可靠性或周期刷盘阻塞。
