# 当前候选实际资源故障与受控回收审查

本轮对保留原调度、独立修复私有事务额度的候选执行实际 Linux 资源故障与持续覆盖回收。两种文件布局的 22 次故障/恢复执行，以及两种持久性的 48 轮回收与独立重开均通过。没有修改核心源码或替换主工程、SDK、旧发布包；本记录证明这份候选的有限验收范围。

候选仍为 `build/atomic-owner-lab-20261107/source/` 的 138 文件清单。Linux 核心 SHA256 为 `23503158ea1411f8c123aa67fe9ff24b14c717121703393f4d28ae9465a81d7b`，与上一轮原生、三语言和性能测试相同。本批证据位于 `build/atomic-resource-lab-20261107/`，汇总为 `summary.json`，探针只使用生产 C/C++ API，不含内部头文件、FQDB_TESTING 或故障注入。

## 资源故障

在原有资源探针基础上增加显式布局选择，实际读取容器镜像头 `FQSEG002` 和 64 MiB 段大小，并检查平铺目录、名称不超过 30 字符和物理文件上限。整理失败改为比较实际文件清单，不把文件数固定为三。旧单文件写满使用 16 MiB tmpfs，分段写满使用 96 MiB tmpfs，确保真正跨越默认段边界；强杀点也安排在跨段后。

| 场景 | 单文件布局 | 分段布局 |
| --- | --- | --- |
| 实际 ENOSPC | errno 28，111 笔确认全部恢复，截去 92205 B 不完整尾部 | errno 28，749 笔确认全部恢复，截去 69645 B 不完整尾部；实际产生第二个物理容器 |
| 整理候选写满 | IO_ERROR，CURRENT/已发布版本/原文件清单不变，旧快照有效，释放空间后可继续写、整理及备份 | 同样通过，按实际分段清单检查清理 |
| RLIMIT_AS 分配耗尽 | 42622976 B 地址空间上限，126 个 256 KiB 压力块，C ABI 返回 NO_MEMORY | 同样通过 |
| 96 MiB cgroup OOM | OOMKilled=true，退出 137，95 笔确认全部恢复 | 同样恢复 95 笔 |
| SIGKILL 第一轮 | 确认 23，恢复 23 | 确认 36，恢复 36，修复尾部 1965459 B |
| SIGKILL 第二轮 | 确认 26，恢复 27 | 确认 44，恢复 44，修复尾部 3687947 B |
| SIGKILL 第三轮 | 确认 32，恢复 33 | 确认 55，恢复 55 |

每笔事务同步写入 Protobuf 载荷、镜像记录和递增 head。宿主只把观察到的成功返回计为确认；恢复核对整个确认前缀、完整尾部和下一事务不存在孤立键。额外恢复出的完整但未确认事务符合结果不确定语义。恢复后继续提交、校验和检查点；强杀/OOM 恢复还会关闭再重开验证。

分段强杀恢复实际出现 2～4 个物理容器，最大单文件为 **67174400 B**（64 MiB 数据加 64 KiB 头区）。写满后原实例返回 RECOVERY_REQUIRED；分配失败的事务不能提交，暂存 guard 不可见，释放压力后新事务可成功。

所有故障容器均关闭网络、根文件系统只读、移除 capabilities，CPU 固定为 0、2，内存与 memory-swap 同值。普通故障 512 MiB，OOM 96 MiB，强杀/恢复 256 MiB。`single/` 和 `segmented/` 各有 11 次执行的宿主日志、完整 inspect 和实际资源限制。

## 持续覆盖与回收

BUFFERED 与 SYNC 分别使用独立卷，限制两核/4 GiB、无额外 swap。每种模式 48 轮，每轮四个写者对 512 条 32 KiB Protobuf 记录做八轮覆盖，累计约 **6 GiB 纯载荷写入**；活跃数据约 16 MiB，缓存设置 8 MiB，writer 工作预算 1 MiB。每轮另以八字节二进制 patch 修改四条记录，再同步确认轮次，逐条检查当前和保留快照的完整模型。

后台使用 20 ms 间隔、默认 1 秒任务期限，每次迭代配置读写请求额度各 64 MiB。两段保留旧快照的阶段实际等待 CURRENT 换代并验证旧数据；快照释放后要求回收继续收敛。覆盖范围包含补丁祖先、跨段 I/O、有界缓存、旧读者退役和超过 4 GiB 的逻辑尾部。没有扩大缓存或改用测试段大小。

两模式各另起容器，核对宿主最后确认的版本 6209 和全部模型，再提交新键、同步、关闭并重开，版本 6210 和全部旧数据均正确。打开耗时是在本次系统缓存条件下的单次观察，不能当作冷设备或任意数据量的重启保证。

每轮保存缓存、pin/事务计量、文件数、物理占用、RSS、后台状态和完整版本。采样中出现的 LIMIT 是配置的后台 I/O 切片额度耗尽状态；任务随后继续，并由实际完成次数、轮次收敛和最终模型验证约束。不能把瞬时 LIMIT 隐藏为无错误运行，也不能直接称为数据损坏。

`steady-v4/` 为最新峰值版本的四次执行。此前 `steady-v3/` 的两个 48 轮场景及独立重开也通过；补充内核峰值采集后仅重跑持续回收，没有重复整个故障矩阵。12～14 秒的执行是在重复覆盖中加速触发维护边界，不等同于运行多年或正式吞吐测量。

## 探针修正与失败证据

第一次持续探针编译把 C++ 强类型 Status 与 C 状态常量直接比较，编译失败；`steady-v1.cpp` 和失败构建报告保留，改为显式转换。下一版运行在第五轮提前要求清单已换代，但先前在途的回收也可能先增加完成计数，因此该等待条件不成立。修正为等待实际 CURRENT 换代后，两种模式完整通过。

失败运行的独立诊断核对了第 5 轮、517 个键和版本 662，数据模型正确；宿主此前已收到四轮完整确认。失败数据库按稀疏文件压缩为 `steady/post-diagnosis-data.tar.gz`，逐个核对十个文件的逻辑长度和 SHA256 后才清理容器与卷，诊断后归档清单及哈希保留。

归档后首次清理按创建顺序先删卷，Docker 因仍被停止容器引用而拒绝；错误记录保留。随后重新核对标签和停止状态，先移除自有容器、再移除对应卷，保存独立清理报告，没有改写失败运行的成绩。

本批不需要核心修复。主工程 114、原 SDK 137、当前候选 138 文件和两个旧 DLL 的哈希保持不变。所有本批自建资源已按所有权清理；源码、构建/失败报告、确认日志、模型与归档保留。

## 验收边界

当前候选已补齐上述真实 ENOSPC、分配失败、内核 OOM、跨段强杀及有界 48 轮回收证据。tmpfs 和进程强杀没有切断宿主内核或物理设备，不能代替硬件断电验证；有限轮数也不证明所有长期负载。

默认日志保留压力需要与最终候选/适配器核对，最终源码采用、包体及正式五方案多轮吞吐比较仍未完成。向量检索、全文检索、RAG/Wiki 继续延期，跨进程协作不纳入本轮底座。长期目标保持进行中。
