# 大批量写入、连续页描述与分离页头实验

后续已回到 retained2 基础实现按字节分流，见 [retained2 分流候选记录](STORE_RETAINED_BYTE_ROUTE_20261108.md)。分离页头布局未采用；本文保留此前实验的结果与回退，不把其收益归为最新候选。

本轮在 retained2 原型上研究大值原子批量写入，不修改主引擎或 SDK。最终实验源码位于 `build/arena-bulk-20261108/final-source/`。它有性能收益，也有明显回退，**不替换此前候选，更未合入主引擎**。主源码仍与 `store-only-source-v6.json` 一致。

## 做了什么

先只用 64 KiB × 32 条原子完整覆盖进行筛选。第一项把新页的四份空白初始化与最终数据写入合并，写入请求从约 51.2 MB 降到 38.3 MB，但仍明显落后当前主引擎，没有据此扩大矩阵或宣称解决。

随后实现独立文件格式的分离页头布局：

- 每个逻辑页仍有四份独立页头及相应数据槽。两份较旧数据槽被替换，另外两份上一版本保持不动。
- 页头按四条副本通道分开放置；每条通道内的页头和数据体分别连续排列。启动小组为四个逻辑页，后续组为六十四页。
- 扩展普通文件后，新暴露字节按系统语义读取为零，因此新容量只写少量空页头，省掉四份 4032 B 空白数据体的显式写入。不调用可能暴露未初始化磁盘内容的特权 API。
- 每个副本分别校验页头 CRC、数据体 CRC、页号、数据库身份、generation、版本及有效长度。CRC 全部匹配才参与恢复选择。
- 更新的数据体按物理地址顺序成批写入，页头随后成批写入；只有一次 fdatasync。恢复不依赖这两类写入的先后落盘顺序。
- 未使用页有可能包含废弃日志，重用前仍检查或清空。可选关闭回收要清理前面副本通道中仍位于文件长度以内的废弃内容，防止再次扩容时复活旧版本。

连续内存也落实到局部路径：用连续 `vector` 保存脏页描述，以连续页号数组代替每页一个树节点；先收集页号再排序。写出缓冲最多 256 KiB，一次预留容量、反复使用，减少分配和系统调用。新建且已知为空的备用页立即记录到内存描述中，不在下一次追加时重复读取四份磁盘内容。

这里的连续指 C++ 容器提供的虚拟地址连续，不要求物理内存连续。页内容仍由原型页缓冲管理，并没有把整库反复拼成一个大数组；完整业务二进制缓冲、减法裁剪和 WAL 对不可变大值的借用保持原实现。连续布局能减少指针追踪和无关内存访问，但不能消除持久化副本的写入量。

## 定向性能结果

最终证明场景为每条 64 KiB、每笔 32 条、连续八笔，共 16 MiB 业务数据。上一版原型、新实验和当前主引擎各两个样本，按 A/B/C/C/B/A 顺序运行；每次都独立重开、逐字节核对并调用 Store verify。所有编译先完成，性能阶段没有新增 CPU 配额节流。

| 项目 | retained2 | 本轮实验 | 当前主引擎 |
| --- | ---: | ---: | ---: |
| 两样本记录吞吐算术均值，条/秒 | 2440.84 | 3351.92 | 9233.71 |
| 系统写入请求，B | 102,416,384 | 35,777,280 | 16,791,816 |
| pwrite 次数 | 25,004 | 616 | 520 |
| 持久化同步次数 | 8 | 8 | 8 |
| 数据文件长度，B | 87,461,888 | 89,370,624 | 21,006,659 |
| 普通文件实际分配合计，B | 87,465,984 | 44,183,552 | 21,016,576 |

相对 retained2，吞吐约提升 37.3%，写入请求减少约 65.1%，pwrite 次数减少约 97.5%。数据文件含零值区域，因此长度略大而实际分配更少；实际分配按 Linux `st_blocks` 汇总，不包含目录元数据。

**本轮实验仍只有当前主引擎约 36.3% 的大批量吞吐，短板没有完全补齐。** 数据体两份写入、逐页 CRC、内存页构造及多位置持久化仍然有成本。不能将减少请求字节数等同于相同比例的吞吐提升。

相关负载的单轮筛选结果如下，其中 BUFFERED 包含最终 sync 的时间：

| 负载 | 本轮实验/当前主引擎 |
| --- | ---: |
| 256 B 单条修改，SYNC | 1.78× |
| 256 B × 32 条，SYNC | 0.92× |
| 4 KiB × 32 条，SYNC | 0.83× |
| 4 KiB × 32 条，BUFFERED，含最终同步 | 0.17× |
| 8 线程、4 KiB 单条修改，SYNC | 0.88× |

小值仍比主引擎的单条 SYNC 快，但与此前 retained2 的同类结果相比收益变小。批量、BUFFERED 和并发也有回退，因此不能默认采用新布局。

另运行一组大值主体每个 8 B 单元随版本改变的完整覆盖，避免只改变版本字段的数据模式：当前主引擎约 6559 条/秒，本轮约 3299 条/秒；请求字节数与常规大值样本一致，没有使用自动差分绕过全量写入。

中间版本的系统调用计时表明，写入和同步等待都占成本；分段计时还覆盖预留、内存暂存、提交准备与输出。它们是单案例诊断，不是稳定峰值或各优化项独立贡献的证明。此次没有单独 A/B 隔离 vector 的贡献，不能把整体 37.3% 收益全部归因于连续内存。

## 空间与可靠性

新布局单个小库的数据文件长度为 84 KiB，较 retained2 的 68 KiB 增加。32 个一条记录的小库实测普通文件实际分配合计仍为 2,359,296 B。64 个较活跃小库测试中，文件长度合计约 58.5 MB，实际分配约 11.8 MB；通道中的零值间隔会放大文件长度，这也是不默认采用它的原因之一。复制、导出与维护接入仍需继续设计，不能只比较占用块数。

验证包括：

- 默认预测额度与零预测额度下，值大小由 256 B、4 KiB、256 KiB 跳到 1 MiB、2 MiB再回到小值；每步同笔写两个键，一次同步，独立重开核对所有历史值。
- 64 库由八线程并行写入，共享预测额度为 256 KiB，峰值不超额度，当前必需写入成功，关闭释放额度。
- 关闭保留容量和可选回收两种模式反复打开、写入、关闭；snapshot 固定旧值、BUFFERED 允许丢失未刷盘尾部但不产生撕裂、健康重开再增长。
- 13 项恢复镜像：旧状态、只完成首/尾页、缺中间页、每页单份新副本、完整提交、页头先落/数据先落、预留中断、单份与双份页头损坏、单份与双份数据损坏。
- 成功恢复的镜像均继续写入、再次重开。单份损坏由其他副本恢复；双份无效返回 CORRUPT，失败打开保留文件哈希。页头或数据单独先落且造成双份无效时也拒绝打开，**不是所有断电镜像都能自动截尾恢复**。
- ASan/UBSan 定向检查覆盖小/大完整值批量、独立重开、可选回收再扩容，无错误报告。
- Windows x64 最终源码构建、实际 DLL 加载路径、两种大小完整值批量、重开与可选回收检查通过。Windows 未做系统调用计数或全性能矩阵。

以上是软件镜像与原生运行验证，不是设备真实断电测试。原型仍有约 32 MiB 逻辑文件上限、内存保存研究页及未接回的生产受控缓存、分段和完整维护 I/O 预算。本轮不改变这些边界。

## 证据与决定

保留本轮实验及全部日志，暂不替换 retained2 或主引擎。下一步需要减少大块完整值的持久化冗余与多位置 I/O，同时保持恢复语义；仅继续扩大预留、整理内存或对业务值做增量修改，不能证明已经修复全量大批量的短板。

证据目录为 `build/arena-bulk-20261108/`：`pilot-report.json` 是融合初始化，`split2-report.json` 是分离页头首测，`profile-report.json` 和 `phase-report.json` 是诊断，`expanded-report.json` 是最终定向对照及恢复检查，`sanitize-report.json` 与 `windows-report.json` 是平台/内存安全验证。`final-manifest.json` 固定最终源码。

最终 Linux 库 724,392 B，SHA-256 `883291b3c910449fabbcd8bcffa9a1450ed56cf80535a5d49adb8c01f0ef619b`；Windows 库 777,216 B，SHA-256 `de2b2124707974f3a2bccc77d3405c25e95773446ea02dce05a4c15893c310e6`。研究库含空间诊断导出，没有发布为 SDK。

第一次分离布局启动器因生成脚本的命令引号错误而未启动测试，保留 `split-resource.json` 和失败日志；后续执行使用独立的 split2 记录，没有覆盖原失败。所有本轮成功容器/卷及该空失败资源均核对所有权标签后清理。
