# 0.3.1：缓存二进制的局部编辑与性能回退修正

0.3.0 没有完整实现“在缓存的完整二进制上做减法”。它主要共享不可变键值片段，再为输出组装片段；事务内每次 patch 也重新分配完整值并追加前缀、插入内容和后缀。共享片段减少了大值复制，却增加了普通短值批量的元数据和小块追加成本。

0.3.1 在适用的缓存上直接覆盖、裁剪或替换，并保留快照隔离、事务提交和故障恢复协议。它不是把数据库文件改成原地覆盖。

## 私有值缓存

事务暂存值由可变分配创建，对外仍以不可变引用保存。patch 只有在事务写集独占该值时才直接修改：

- 等长替换覆盖变化区间，不构造全部未变化字节。
- 删除用 erase 裁剪，移动必要尾部；普通连续字符串的中间删除仍是 O(尾部长度)，不是 O(1)。
- 插入或变长替换用 replace，容量足够时复用分配，容量不足时由字符串扩容。
- 缩小到原容量四分之一以下且原容量超过 256 字节时，重新分配紧凑值，避免长期保留巨大的无用容量。
- 成功编辑后清除该值缓存的 CRC；先检查限额和故障注入，再修改数据。

第一次编辑已发布值、仍被准备批次持有的值或其他共享值，仍须创建私有值。后续编辑才能复用该缓存。已发布根、历史、快照、其他事务和准备批次的内容不被原地修改。事务本身仍要求单线程使用。

例如，事务内把 `ABCDEFGH` 删除区间 `[2,4)` 后变为 `ABEFGH`，独占缓存只需把 `EFGH` 前移。连续等长修改则只写变化位置。对共享原值，必须先隔离所有权，不能为了少复制破坏读快照。

`Transaction::patch` 操作的是原始字节区间，不会自动识别业务 Protobuf 消息中的字段。调用方负责消息内部长度、偏移及合法性；数据库负责自己的事务封装长度和校验。

同事务连续 patch 仍以最终完整值提交，沿用 0.3.0 的日志回退规则；没有增加复杂的多段增量合并。格式 3 的首次单次 patch 仍可记录小增量，最多连续 8 次后回退完整记录。

## 准备批次的完整 wire 缓存

5 条以上、编码总长不超过 64 KiB、每个值不超过 1 KiB 且没有增量操作的批次使用连续的编码缓存。普通短值事务在单次编码后只向输出追加一个连续载荷，避免每条操作都追加多个小片段。普通事务之间没有已知相同输入时，仍必须编码本次输入。

`PreparedBatch::with` 有完整旧缓存可用：复制不可变缓存一次作为新对象的私有数据，然后只编辑变化操作。值长度相同直接覆盖值区间；值长度变化则编码这一条操作并替换旧区间，长度前缀一并更新。未变化操作不重新编码、也不逐块拼装。新增键同样只插入新操作。

准备批次保持不可变，因此原批次和派生批次之间仍有一次缓存复制；写集映射也有复制成本，未变化值共享所有权。不能把它描述成整个接口 O(1) 或零复制。

大值和增量操作继续使用共享片段，避免为一个大值额外永久保存整份编码缓存。短批次缓存的空闲分配由数据库实例复用，保留容量最多 64 KiB；活动准备对象和同时在途请求另占各自内存，不受这个空闲缓存上限约束。

## 其他修正

- IEEE CRC32 使用 slicing-by-8，组合校验使用预计算的字节长度变换，减少串行逐字节计算和重复矩阵平方。多出约 16 KiB 静态表，算法、校验结果和文件格式不变。
- 大写集使用 lower_bound 加提示插入，减少暂存新键时的重复树查找；4 键以内仍使用内嵌小映射。
- 基准增加进程 CPU 时间，使用相同 EXE/SQLite DLL 交替加载各版本 Core，并验证关闭重开后的全部键值。计时阶段不并行编译。

版本号为 0.3.1，C ABI 仍为 1，文件格式仍为 1/2/3。Windows 和 Linux 共享、静态 SDK 放在 `artifacts/release-0.3.1`，0.3.0 原始发布目录保留。性能及实际限制见 `PERFORMANCE_0_3_1.md`，验证记录见 `artifacts/validation-0.3.1.md`。
