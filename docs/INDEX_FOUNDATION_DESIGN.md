# FengquIndex 索引底座设计草案

状态：2026-11-14 已实现第一阶段原生库，尚未完整替换 PTpma。当前可用能力和验证见 [实现状态](INDEX_IMPLEMENTATION.md)，实际 C/C++ 接口见 [接入说明](INDEX_CPP.md) 与 `proto/index.proto`。下文仍包含未完成的长期设计目标，不能当成已交付清单。目标是完整承接 PTpma 的项目 AI 索引和电脑操作经验，并为 RAG、Wiki 共用检索能力。

## 产品与协作边界

- FengquDB：事务、快照、恢复、受控缓存及二进制数据存储。
- FengquIndex：通用记录、结构导航、全文与结构化检索、版本与来源校验；可选向量索引。
- FengquRAG：调用索引进行召回、融合或重排，组织证据和上下文，连接业务模型。
- FengquWiki：来源入库、主题与实体页面编译、引用关系、冲突及失效传播，调用公共检索。

新索引层采用 C++20，公开 C ABI，语言包装复用现有 SDK 的生命周期和缓冲设计。完整替代 PTpma 现有能力的基础版不要求下载或加载模型。语义检索及模型推理分别为可选组件。

已建立 `codex/index-foundation`（D:/study/FengquDB-index），与 `codex/rag-foundation`、`codex/llmwiki` 各用独立工作树，数据库共同基线为 `32348fb`。分支是开发隔离手段，最终模块应能组合发布。原 develop 的未提交开发成果保留，索引会话本轮不提交或推送。

检索算法归索引层维护，RAG/Wiki 不各写一套倒排或 HNSW。先对齐记录标识、版本、过滤表达式、检索请求/响应和变更游标；其他会话可依赖这些接口草案推进，不同时修改同一公共头文件或根构建文件。

公共事务/快照桥接、独立投影版本和完整性返回值的协作草案位于索引工作树的 `docs/FOUNDATION_COORDINATION.md`。教师蒸馏受用户完整流程 10 小时上限约束，当前从开发依赖中排除。

## 完整替代清单

| 现有能力 | 新底座与适配要求 |
| --- | --- |
| overview/query/show、目录分页、文件用途与分类策略 | 持久目录树与路径索引；精确名称优先，字段分开评分；游标包含目录修订 |
| references、文件改名与移动 | 记录有向引用及来源观察版本；词法引用明确标为不完整，不声称完整语义分析 |
| maintain/check/batch 与用途更新 | 有界扫描、可恢复维护游标、源码哈希及用途修订保护；保持逐项部分成功的公开含义 |
| 源码变化与项目理解 | 监听加补扫、来源修订证书、增量目录归并缓存；覆盖率与语义复核状态分别报告 |
| records 通用资料库 | CRUD、过滤、检索、分页、容量策略、历史与 tombstone；原子维护记录和派生索引 |
| experience 经验存取及召回 | 按应用、环境和版本筛选；保留候选/验证/降级状态、成功失败证据和完整读取确认 |
| experience 反馈、纠正、删除、导出 | 幂等反馈、修订冲突保护；修订后原验证失效；反馈不挤掉操作步骤历史；删除后旧请求不可复活 |
| GUI、CLI、JSONL/MCP 共用行为 | 在 PTpma 适配层保持同一命令语义；协议包装和权限检查不进入通用搜索内核 |

完整替代包括业务含义和现有资料一次性导入，不是只把 SQLite 的读写 API 改名。导入保留原 ID、修订、历史、删除标记、来源及验证证据；切换后保留可核对导出，不长期维护两份可写权威数据。新模块不承担旧 FengquDB SDK 兼容。

## 专业检索范围

### 必做的无模型检索

1. 路径、文件名、标识符、错误码及 ID 的精确查找和前缀查找。
2. 自研倒排索引，支持字段化 BM25、词项 AND/OR/NOT、短语与邻近匹配。
3. 中文字符和相邻字对作为通用基础，按需加小词典；英文词、camelCase、snake_case、路径、C++/C# 等技术记号分别处理。
4. 通用类型化元数据过滤：相等、集合、范围、存在性及组合表达式；应用/项目只是外层字段。
5. Top K、有界摘录、命中字段与原文 UTF-8 字节位置、评分解释及稳定分页。
6. 有界更新、删除、重建、暂停/取消及索引健康状态，不能查询时临时扫描全部原件。

项目文件的精确名称和自身用途优先；继承的目录描述只给低权重。经验按应用/环境先排除不适用记录，再在可用记录中排序。默认权重从 PTpma 当前行为起步，再由小样本测量调整，不承诺某组权重通用最优。

参考公开的 BM25、Block-Max WAND/MAXSCORE 算法独立实现，不链接 zvec、FAISS、Lucene、SQLite FTS 等作为检索引擎。Block-Max 的目标是跳过无法进入 Top K 的整块候选；上界必须包含可变统计、差量与所有正向加分，不能因为上界过小漏掉正确结果。未证明安全时回到普通精确评分。

### 共用的可选向量模块

- 支持外部提供向量和模型空间标识，模型生成向量不属于数据库事务或搜索内核。
- 候选少时用连续向量数组和 SIMD 精确距离计算；规模较大时用自研 HNSW，切换点由实际维度、过滤选择率和样本测量决定。
- 支持余弦/点积及显式归一化约定；同空间的模型、分词器、查询指令、维度和归一化身份必须一致。
- 过滤不能简单在近邻 Top K 之后才丢结果；高选择率过滤可直接精确扫描候选，图搜索保留必要的遍历通路。
- FP32 为正确性基准，SQ8 等向量压缩作为独立选项；量化召回后可用原向量重排。ANN 与向量量化都须评估 Recall，不能声称与精确检索等价。
- 语义模块不启用时词法能力完整；调用方明确要求语义模式却不可用时返回具体状态，不伪装为完整语义检索。

## 公共数据与接口草案

本节是整体目标；已实现 v1 的精确字段、预算和返回值以 `proto/index.proto` 为准，尚未覆盖的能力见实现状态。

记录：`scope / collection / id / revision / title / summary / body / metadata / sources / deleted`。内部使用稳定整数 DocId；外部字符串 ID 不直接变成物理文件名。来源另保存版本、内容哈希、观察时间及适用条件。

请求：查询文本、字段/集合、类型化过滤、检索模式、可选查询向量与模型空间、Top K/游标、时间与内存预算、一致性要求。普通调用直接传文本，不要求业务填写数据库内部 Protobuf。

响应：记录 ID/修订、评分与命中理由、字段与摘录、来源版本、目录/资料库修订、下一页游标、搜索策略、扫描/候选统计及完整性标记。限额、取消或索引未追平不能返回看似完整的成功结果。默认只回必要摘要，正文和历史按需读取；C/C++ 借用视图绑定快照或显式租约。

RAG/Wiki 对接只依赖以下能力：记录写读、批量写入、过滤搜索、向量写入/搜索、按版本读取来源、稳定遍历、变更游标、等待索引水位、重建与 Explain。Embedding 与 reranker 用回调/Provider 接口接入，不能把 500 MiB 模型变成基础库强制依赖。

## 在 FengquDB 中存储

所有持久数据使用同一 Store 的逻辑键空间，例如：

| 前缀示意 | 内容 |
| --- | --- |
| `r/`、`h/` | 记录、当前修订、历史和删除标记 |
| `n/`、`e/` | 目录树与引用边，记录来源观察版本 |
| `d/`、`p/` | 每篇记录的反向词项清单、分块倒排 |
| `f/` | 元数据过滤索引 |
| `v/`、`a/` | 可选向量、图索引及其版本 |
| `m/`、`j/` | 格式/分词配置、发布水位和待处理任务 |

实际键使用有长度边界的二进制编码及便于范围查找的整数序，不直接拼接未经转义的用户 ID。索引块受单值和事务预算约束，超大词项不得形成单个无限增长值。数据库仍用自身的浅层短名文件，不为每条记录或每个词项新建磁盘文件。

原件修改先计算新旧词项差异；最终事务重新校验记录修订，原子保存原件、反向词项、过滤索引、必要的倒排差量和变更任务。长时间解析、模型推理在事务之外进行。后台结果附带源修订；过期结果不覆盖新修订。

正文、词项和过滤读取使用同一提交快照。ANN 等异步派生结构额外报告水位；要求最新结果时搜索待索引的小差量或等待水位，超预算时明确拒绝/返回不完整状态。进程崩溃后根据持久任务和检查点幂等重放；不能只依赖已过保留窗口的内存通知。

用户确认保存的用途、经验和验证证据默认走可靠写入；可重建的批量缓存可选性能模式。完整备份沿用 FengquDB 工具。索引不另造一套文件 WAL 或恢复协议。

## 性能设计

- 变更按 DocId 合并，未变的字段、编码缓冲、词项和向量复用；不因反馈计数变化重新编码/嵌入整份正文。
- 分块倒排使用连续压缩 DocId、频次与按需位置数据。更新以块内删除掩码和有界增量表示，读取跳过被裁掉的记录；超过预算只重写受影响块。
- 减法裁剪保留未变二进制区域；避免每次重建整个热门词的列表，也避免永久堆积小块、使每次查询都拼接长链。
- 查询优先排除集合、应用和环境不匹配的候选；Top K 堆只持有必要结果，最后再取摘录/正文。
- 归一化规则和查询计划按配置版本缓存；Unicode 归一化保留原文字节位置映射，不能拿变形后偏移切原文。
- 热查询缓存按集合修订、过滤条件、模型空间和配置版本失效；有总内存预算，模型/外部推理内存单独报告。
- 保持原有目录流式枚举和键集游标；监听只使受影响目录/文件变脏，监听丢事件后执行补扫，真正空闲时休眠。
- 向量计算提供标量基准、x86 运行时指令分派及 ARM64 路径；不依赖未对齐强转、本机字节序或 Windows 独有行为。

查询、维护、扫描本身不自动花费模型调用。项目理解的模型归并维持显式触发、增量复用和来源修订证书。来源校验说明观察时的内容，文件枚举完整不等于 AI 已理解全部源码。

## 宿主与跨进程

FengquDB 目前独占打开库目录。PTpma 的 GUI 与独立 CLI/MCP 当前能分进程操作 JSON 原件及 SQLite 缓存，因此完整替代必须单独处理接入方式。

建议一个宿主进程持有 Store 和索引，GUI 直接调用，其他本机入口转发同一命令；权限和工作区边界沿用宿主。独立部署时由应用选择唯一持库进程。数据库不增加多进程共享内存和多写者文件协议，也不关闭独占锁。宿主转发尚未实现，不能据此宣称多进程替代已经完成。

## 开发与验收顺序

1. 冻结公共记录/查询契约；列齐现有命令，先完成无模型的存储、精确查找、目录与版本保护。旧资料迁移已取消，只对对应存储重建。
2. 自研倒排、BM25 和过滤；先用一个代表性短查询/单记录更新证明候选定位与块内更新有效，再扩大负载。
3. 接入 PTpma 项目索引和经验适配；完成宿主访问路径和等价行为验收。
4. 可选语义模块先用精确向量基准，确有规模收益再加入 HNSW/量化；供 RAG/Wiki 共用。

必须验证：源码改动与监听补扫、改名和删除、跨客户端过期 guard、稳定分页、清空后旧请求、经验环境不匹配、失败降级、纠正后旧验证失效、历史与导入身份保留、事务中断恢复。检索优化用精确评分/精确向量作正确性对照，特别覆盖热门词、强过滤、频繁修改和删除。

业务对照固定同一份语料和查询，分别记录词法 Recall@8/NDCG@8、经验适用性、冷/热延迟、P99、更新耗时、内存与包体；语义 Recall 与 ANN 相对精确召回率分别报告。Windows/Linux 做接入和恢复实测，Android/iOS 独立记录编译与设备验收，不能相互代替。通过前不标注“完全替代”或承诺超越其他引擎。
