怎样测，怎样理解

相同业务，各用常规方式

业务对象有 ID、修订号、余额、等级、状态、姓名、邮箱、简介、地区、登录时间共 10 个字段。128 B／4 KiB 指简介长度，实际记录还包含其他字段。

FengquDB 使用 Protobuf wire 编码；SQLite 与 MySQL 使用普通类型列和预编译 SQL；Redis 使用 Hash、原生增量操作和 Lua 原子转账；MySQL+Redis 使用 SQL 持久化与 JSON cache-aside。计时包含业务编解码和数据库调用。

这比较的是整套业务访问方案。内嵌调用与本机 TCP、数据结构、事务和缓存都影响结果，不能把全部差距归因于 Protobuf。

确认成功，不等于已经可靠落盘

FengquDB：性能模式 50 ms／1 MiB；MySQL：InnoDB flush=2、关闭 binlog；Redis：AOF everysec；SQLite：WAL + NORMAL；混合方案：同 MySQL，Redis 仅作缓存。

周期是触发设置，不是任何负载下最大丢失时间的承诺。“确认吞吐”计至业务调用结束；“含最终同步吞吐”还计入末尾显式持久化屏障。它也不会把之前每次确认变成可靠提交。

纯读取不需要新的持久化屏障；含同步指标保留驱动统一调用的固定开销。

范围与校验

同一隔离容器同时容纳客户端与对应服务，限制 2 个逻辑 CPU、4 GiB 内存、禁用 swap，网络为本机 TCP。每轮交替数据库顺序。预热后计时 1.5 秒；新增与删除各访问 65,536 个独立键一次。

热场景为 4,096 份档案、Zipf 0.99 分布。每个样本执行完整字段核对、预期值核对和独立客户端进程重开验证。此处不是断电测试，也不是超内存、远程部署或长期运行测试。
