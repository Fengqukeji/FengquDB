# Linux 2 CPU / 4 GiB 五方案正式比较（2026-11-08）

本轮原生比较已经完成：1280 项并发扫描、960 项三轮峰值复测。完整覆盖审计核对了 945 次独立进程验证、15 次组末服务重启验证、15 组自有资源清理，五种方案各有 192 项新复测。原始失败、驱动修正和续跑历史保留在 [阶段记录](DOCKER_CURRENT_COMPARISON_20261107.md)。后续 pwritev 候选未采用，最终 SDK 沿用本文受测核心，见 [SDK 交付](SDK_RELEASE_20261108.md)。

4 KiB 复制读取和批量读取的吞吐中位数在这五种接入方案中领先；256 B 复制读取、批量读取和两种载荷的缓冲批量写入均有 SQLite 领先的结果。可靠新增、完整修改、删除和批量写入的峰值中位数仍低于 Redis。这些结论限于以下工作负载与配置，不能概括为全面超越任一数据库。

## 环境与计量方法

- 宿主 AMD Ryzen 9 9950X3D，Windows / Docker Desktop，WSL2 Linux；测量镜像基于 Ubuntu 26.04。服务与原生 C++ 客户端合计受限于 2 CPU 配额、Linux CPU 0 和 2、4 GiB、无额外 swap，数据使用 Linux 命名卷。guest cpuset 不代表宿主物理核心独占。
- 方案为 Store、SQLite 3.54.1、MySQL 8.4.11、Redis 8.10.3、MySQL+Redis。Store/SQLite 为进程内调用，其他方案包含本机 TCP、协议与调度成本。
- 每项准备 131072 条有效 Protobuf，载荷为 256 B 或 4096 B。这是热数据接口比较，不能当作超内存吞吐、完整 SQL 或所有索引查询的比较。
- 先扫描 1/2/4/8/16/32/64/128 线程，再为每个场景选择最强的两个扫描点，各做三轮新测量。每个并发点先取三轮中位数，再选较强并发点；表中不是单次最高值，也不是理论上限。
- 新增和删除每项固定完成 65536 次调用，其余峰值项目每轮约五秒；准备、预热和模型验证在计时之外。批量每次 32 条，吞吐按记录计，延迟按整次调用计。
- SYNC 等待可靠提交，并发允许引擎合组共享同步；BUFFERED 不承诺每次确认都已可靠落盘，各引擎后台同步周期仍有差别。两种模式分别报告。
- Store 使用默认单文件布局、2 GiB 缓存和后台维护。SQLite 使用 WAL、预编译语句、mmap 和受预算限制的连接缓存；独立 MySQL 缓冲池 2 GiB，独立 Redis 上限 3 GiB、单 I/O 线程。
- 组合方案中 MySQL 和 Redis 各配置 1 GiB；MySQL 为权威数据，Redis 关闭 AOF 和定时 RDB。写入先提交 MySQL，再失效缓存；客户端分片锁只协调本测试进程，不证明跨进程一致性。

以下每格是记录/秒，括号为对应线程数。各方案并发点可能不同。

## 单线程弱项与诊断边界

以上峰值只复测扫描最强的两个并发点，未保证包含 Store 单线程。先前单轮扫描中，4 KiB 单线程 SYNC 新增/修改/删除约为 799/800/806 次/秒，SQLite 约为 1627/1343/1713；这些负值继续保留，不能由高并发峰值替代。

既有指标分析中，完整修改的每调用逻辑净增长为 4212 字节，八字节修改降为 173 字节，吞吐仅约 800→862 次/秒；两者无 CPU 配额限流。后续系统调用跟踪确认每次修改一次 fsync，文件层对照显示已初始化区域覆盖明显快于持续追加。完整诊断和兼容性约束见 [I/O 评估](STORE_SYNC_IO_REVIEW_20261108.md)；诊断没有修改核心、文件格式或同步屏障，数值不能当作生产改造的已实现收益。
