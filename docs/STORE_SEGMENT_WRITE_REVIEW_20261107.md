# 分段写入的重复计数与句柄复用对照

本轮针对上一批写入回退，完成两个隔离实现及对照，没有合入主工程。小值写入有提升，但 4 KiB 批量和部分尾延迟仍变差，文件层精简尚未解决主要差距。证据根为 `build/segment-write-lab-20261107/`，逐轮范围、P99、后台回收状态、二进制及源码身份见 `summary.json`。

## 实现与审查

两个副本都来自最终 137 文件 SDK，保持旧写锁、Root5 回收和全部持久性规则：

- `source-counters` 删除 NativeFile 中没有调用方的七个原子统计字段及其更新。SharedFile 原有逻辑统计、维护调用线程的字节额度与同步计数保持不变。
- `source-writer` 在上述基础上，借用 dirty_ 已持有的写文件指针和段号。同段连续写入省去句柄查找、LRU 时钟修改、共享指针增减及脏集合重复查找；不增加文件强引用或缓存容量。

借用指针只在 mutation_ 锁下访问，所有者是独立于读缓存的脏文件集合。刷盘清空脏集合前清空指针，截断移除旧尾段前清空旧指针，脏文件驱逐先完成同步，再使借用失效。新段创建、完整写单元额度预检、异常后的 poisoned 状态、目录持久化及旧读者保护没有删减。

新增测试使用一个槽位的读/脏句柄缓存：读操作驱逐仍在写的文件、同步释放脏所有者、两端交替写导致脏文件驱逐、截断删尾后重新增长，最后检查全部字节和重新打开的模型。它检测借用生命周期问题，不仅检查某个缓存字段是否被赋值。

## 原生性能

Linux 使用同一个比较 EXE（SHA256 `45d11610cc5296dfe359be36bd3bef949e9085d3feb63073f7646708e0e5eb75`），三个不同核心 SO；两核 CPU 0、2，4 GiB、无额外 swap，数据在命名卷，计时不与构建、消毒器或 Windows 测量并行。每组预填 32768 条、8 线程、预热 0.2 秒、计时 3 秒，三轮轮换方案顺序，均为 buffered，批量每次 32 条。

## 原生与 C# 热路径复查

复用上一批完全相同的原生 EXE、C# 程序和 4176 B 载荷；三轮交替三种核心和语言顺序，32 个热键，单条一百万次。计时包含语言调用和目标复制，不包含写入样本、启动、序列化及校验。

| 准备键目标缓冲路径 | 当前 Root4 | 原分段候选 | 新组合候选 |
| --- | ---: | ---: | ---: |
| 原生次/秒 | 11,371,800 | 11,305,600 | 11,386,500 |
| C# 次/秒 | 9,111,086 | 8,806,453 | 9,212,149 |

C# 三种核心均保持每次 0 B 托管分配，新组合相对本轮 Root4 为 +1.11%，没有复现上一批约 -5% 的中位数回退。其三轮范围为 9.060～9.235 M/s，Root4 为 8.470～9.135 M/s；三个短样本和组合变更不能证明根因已修复，更不能把差异归因于读取时没有使用的写文件借用。普通复制和批量路径也完整保留，新组合相对 Root4 为约 -0.53%/-0.31%。

## 包体、采用决定与下一步

Windows 组合 DLL 为 863232 B，与原候选同尺寸；Linux 仅删除计数为 994656 B、组合为 994768 B（均未去符号），后者增加 112 B。删除字段与指令没有带来本轮二进制包体缩小，不以源码行数代替实际包体结果。

主工程 114 文件和原 SDK 137 文件逐一哈希一致，原 DLL 与发布包未覆盖；0.3.1 完整私有二进制缓冲及减法裁剪没有修改。两份源码 ZIP、二进制、模型及审计留在实验目录，自有容器/卷确认所有权后清理，没有 OOM。

两个提案继续隔离，组合提案不进入当前采用清单。现有证据说明减少这些文件层步骤不足以解决主要并发写入回退。随后另行实现并验证的自然合组、排队撤出与逐笔语义见 [buffered 合组审查](STORE_BUFFERED_GROUP_REVIEW_20261107.md)；它没有叠加本批文件层提案。新方案并发单条写入有收益，但混合回退和临时快照额度问题仍未解决，不能把本批正确性成绩转作其采用证明。
