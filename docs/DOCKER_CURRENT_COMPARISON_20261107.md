## 方法与身份

每个容器的数据库服务与原生 C++ 客户端合计限制为两个 Linux CPU（固定 CPU 0、2）、4 GiB 内存、无额外 swap。数据放 Linux 命名卷；计时期间不构建、不运行消毒器或另一个性能任务。

现场宿主为 AMD Ryzen 9 9950X3D（16 核、32 逻辑处理器），Docker Engine 29.8.2 运行于 Windows 的 WSL2 Linux 内核 `6.6.87.2-microsoft-standard-WSL2`。已从正在执行测量的容器核对 `NanoCpus=2000000000`、`CpusetCpus=0,2`、`Memory=MemorySwap=4294967296`，完整只读观察见 `build/final-comparison-ready-20261108/environment-observation.json`。guest cpuset 与 CPU 配额不代表宿主物理核心独占；最终数值只说明这套环境、接入方式及工作负载下的观测吞吐。

方案为 Store、SQLite 3.54.1、MySQL 8.4.11、Redis 8.10.3、MySQL+Redis。服务通过本机 TCP 接入；Store/SQLite 为进程内调用。因此端到端差距包含协议、连接及调度成本，不代表单独存储算法的差距。组合方案只保证本测试进程的协作访问，不是跨进程一致性产品。

Store 使用默认单文件布局、2 GiB 缓存和后台维护；分段属于可选能力，没有暗中替换默认布局。SQLite 使用 WAL、mmap 与受预算限制的连接缓存。MySQL 独立方案缓冲池 2 GiB，组合方案中 MySQL 1 GiB、Redis 1 GiB；独立 Redis 上限 3 GiB、单 I/O 线程。各方案仍共同受容器 4 GiB 总额限制。

组合方案的 Redis 是可重建缓存，关闭 AOF 和定时 RDB，可靠性由 MySQL 权威数据提供；独立 Redis 方案才启用 AOF。组合写入先提交 MySQL，再删除相应缓存；读取未命中时回源并填充，单次批量失效使用一条 DEL。客户端分片锁协调本测试进程内的读写，不能据此宣称跨进程缓存一致性。源码配置与实际首项设置均已核对，例如 `build/final-comparison-ready-20261108/scan-write-4096/j0004/t0000/report.json` 中 `appendonly=no`、`aof_enabled:0`；该组合不要求缓存额外做一份可靠刷盘。原始报告中的 `appendfsync=always` 在 AOF 关闭时不表示有 AOF 同步。

首次镜像为 `fqdb-final-current:20261107`，完整输入清单含 68 个文件，位于 `build/final-comparison-current-20261107/source-manifest.json`。其裁剪核心 SHA256 为 `3b1be49d9baa091f0273b2695a533930672cbb49c9779dbd791fd38482f41df8`，与采用验收的裁剪副本相同。五方案 × 两持久性共十组互通、自检和恢复检查通过。

读取扫描使用 131072 条、每值 256 字节的有效 Protobuf 数据，四种工作负载、1/2/4/8/16/32/64/128 线程，共 160 项；读取统一使用 BUFFERED 配置。每项计时三秒，保存抽样延迟、CPU、含文件缓存的容器内存、完整模型与独立进程校验。服务按组复用，组末才强杀并重启服务核对；不能称为每项都重启了服务。

## 写入中断与 SQLite 基准客户端修正

SQLite 仅供性能对照；FengquDB 核心、C/C++ API 和语言绑定均不依赖 SQLite。以下锁等待处理只属于基准客户端，不是本库新增功能或本库锁机制修复。

后续 256 字节写入中，Store 的 96 项已通过模型与重开；SQLite 完成 37 项后，在 32 线程、65536 次单条可靠新增的任务中，某个写者超过 30 秒 busy_timeout，返回 SQLITE_BUSY。原整阶段报告保持失败，不能把已通过子项合称为全部写入完成。

失败数据库先逐文件归档并校验 SHA256，再用同一 SQLite 动态库执行 integrity_check 与全量数据模型检查。131072 条种子完整，46213 条已落库新增均为各线程连续前缀，所有值的完整字节正确。诊断与归档位于 `build/sqlite-busy-lab-20261107/`；验证后才按所有权移除自有容器和卷，原失败日志与报告保留。

基准客户端只对自动提交状态下的 SQLITE_BUSY 增加有界重试，不重试 LOCKED 或显式事务，不降低 WAL/FULL 可靠提交设置，也不从成功写入中增加时钟查询。等待与重试计入实际耗时、抽样延迟及重试计数。这是基准适配修正，不是修改 SQLite 存储实现。

新镜像为 `fqdb-final-retry:20261107`，仅 `tools/final_benchmark/sqlite.cpp` 输入变化，Store 核心 SHA256 不变。32/64/128 线程的同一新增任务各完成 65536 次，完整模型与重开通过，实际发生 1/6/25 次 BUSY 重试。总计时约 44.09/46.01/47.84 秒；独立写连接争用的尾延迟很高，不能概括为 SQLite 所有接入方式的固有限制。

## 已合入的批量查找优化

当前读取差距促成 `build/bulk-path-lab-20261107/` 的隔离提案：一次请求内复用最多三个不可变索引页，按代际身份、偏移与读取上界核对；不要求键有序，不跨请求保留。暂存预算不超过 writer_bytes 的八分之一及 256 KiB，另保留正常的一页读取暂存。公开接口目前只在至少八个键且缓存启用时使用，事务暂存读取沿用原路径。

Windows 七项、Linux ASan/UBSan 七项通过。内部冷页测试以真实文件读取计数比较 32 个相邻键，192 次降为 6 次；这是隔离的页面查找验证，不代表公开接口在缓存关闭时自动启用，也不代表吞吐提高 32 倍。测试覆盖任意顺序、重复/缺失、TTL、删除、旧根与换代、预算及返回对象生命周期。
