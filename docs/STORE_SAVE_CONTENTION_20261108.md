# BUFFERED 并发完整保存诊断

BUFFERED 是持久化策略，不是并发开关：提交不要求在返回前完成可靠刷盘。SYNC 要求可靠提交后才返回。这两种策略都可以单线程或多线程调用。

本轮只调查业务比较中 4 KiB 简介的完整编码保存，没有修改数据库引擎、接口或发布包。结论是：当前提交串行区和停车/唤醒交接存在明显开销，不能把这次并发回退解释成 Protobuf 编码慢，也不能仅凭此判断减少内存复制就能解决。

## 实际调用链

1. `tools/business_benchmark/fq.cpp` 的 `FqConnection::put` 在调用线程生成 key 并完整编码 Protobuf，然后创建事务、暂存完整值、提交。
2. `src/paged/core.hpp` 的 `Transaction::put` 为暂存数据分配并复制；`stage` 查找原记录并登记事务依赖。编码发生在写入锁之外。
3. `Core::commit_checked` 将 BUFFERED 请求送到 `commit_direct`，SYNC 请求通常送到 `submit` 合组。BUFFERED 当前没有使用该合组队列。
4. `src/paged/group.hpp` 的 `commit_direct` 持有 `Core::writer`，依次执行必要检查点、冲突校验、WAL 构造与追加、增量索引视图更新、发布及事务清理。锁的范围远大于文件追加。
5. `src/paged/core.hpp` 的 `WriterGate` 使用 mutex、busy 状态和 condition_variable。竞争者进入至多 2 ms 一次的有界等待；释放时 `notify_one`。并发调用者反复抢锁、停车、唤醒，只有一个调用者能进入提交区。这里没有 `notify_all` 惊群，2 ms 也不是每次必等的固定延迟。

单写者能够保证顺序日志和发布一致性，但不意味着这种逐笔交接已经足够高效。1 个调用线程能持续执行同一条路径；8 个调用线程增加竞争、唤醒及迁移，不能并行执行该提交区。

## 最小诊断复测

证据目录：`build/save-contention-20261108/`，入口 `lab.py`。复用业务比较的完整保存程序和同一核心，没有重新编译数据库，也没有同时运行其他基准或构建。Linux 容器限制客户端和后台合计 CPU 0、2 两个 vCPU、4 GiB、无额外 swap；4096 条记录、每条简介 4096 字节、BUFFERED。只测 1 和 8 个调用线程，每项计划 3 秒，各 1 次，并附加 perf CPU 采样和进程计数。因此下面是诊断样本，不替换正式三轮成绩，也不是长期吞吐上限。

## 修复方向与边界

- 优先减少提交串行区的线程交接：只在确有并发积压时复用写者或自然合组，摊薄发布和唤醒成本，保持每笔事务独立版本和结果。不能把多个独立事务改称一笔原子事务。
- 同时缩短锁内工作：考察完整值的校验准备、WAL 编码和可提前释放的私有对象。只有不依赖最新视图的部分可以提前；冲突校验、日志顺序、版本和发布仍需严格有序。
- 完整值暂存、WAL 缓冲复制和预算原子计数还有优化空间，但本轮没有测出各自的独立收益，不能写成已证实主因。

不能直接把之前的实验当作修复。`STORE_WRITER_REVIEW_20261107.md` 的三状态锁方案改善过纯写，却有混合/尾延迟回退；`STORE_BUFFERED_GROUP_REVIEW_20261107.md` 的合组候选也有混合负载和快照额度问题，均未采用。本轮只确认当前业务路径的实际症状和热点，没有合入这些旧提案，也未宣称问题已经解决。
