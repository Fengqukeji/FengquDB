# Docker Linux 读取扫描阶段记录

本阶段完成五种方案、四种读取方式、1/2/4/8/16/32/64/128 并发的 160 个用例。每个用例计时 3 秒，预填 131072 条、每条 256 字节合法 Protobuf 数据，完整预热、准备语句、最终同步和完整字节校验不计时。各并发点目前只有一轮，尚须复测峰值候选；这不是最终吞吐上限或全数据库性能结论。

每个方案的调用程序和全部服务合计受限于两个不同物理核心及 4 GiB cgroup，禁止额外 swap。数据使用新的 Linux 命名卷。主机为 AMD Ryzen 9 9950X3D，Docker cpuset 为 0、2。固定 MySQL 8.4.11、SQLite 3.54.1、Redis 8.10.3；完整镜像与源码哈希在原始报告中。

Redis 先在相同镜像下对照 1/2 个 I/O 线程。本次两核额度内，1 线程的短扫描表现更好，因此正式读取扫描使用 1 线程。调参记录独立保留在 `tune-rio1`、`tune-rio2`，不混入正式扫描。

表格为各方案在已测试并发点的最大记录/秒，各行的峰值并发可能不同；完整并发曲线、抽样 P50/P95/P99、CPU、内存和重试数见 [逐项 CSV](../build/final-benchmark-20261107/read-report/trials.csv) 与 [汇总](../build/final-benchmark-20261107/read-report/summary.md)。32 条读取的延迟是整批调用延迟，吞吐按记录计。缺失键固定落在已有最大键之后，组合方案预热负缓存；不能将该项外推为任意位置或任意键分布的未命中性能。

当前结果包含需要继续分析的短板：FengquDB 的并发命中和批量读取落后于 SQLite，且高并发下尾延迟升高。FengquDB 与 Redis/组合方案批量峰值相近，单轮中的几个百分点不足以证明稳定领先。服务方案使用本机 TCP，嵌入式方案使用原生函数调用；两条调用路径的差异属于结果范围，不能据此推导服务端内核本身的普遍差距。

内存为计时期间每 20 ms 抽样的 cgroup 总额，包含文件缓存和全部服务，不是进程 RSS。group 模式复用 MySQL 服务启动和缓冲池，逐项重建表及 Redis 数据；缓冲池和分配器保留容量会随试验次序变化，不能把某个并发点的内存数字当作应用最低内存。

全部 160 项通过完整键集和全字节模型核对、原生库重开及独立进程验证。group 模式仅最后一项重启 MySQL/Redis 服务，报告的 `server_restart` 字段标明范围。所有自有容器和数据卷均已清理；没有 OOM kill。此前两种持久性下五种方案的 10 项 smoke 也通过 CRUD、批量、局部修改和逐项服务重启。

读取扫描使用工作镜像 `sha256:1fe9249396d5db7648cb39ba6ce13ff0354eb70bfaa95188e02a5e2252908db4`。原始证据位于 `build/final-benchmark-20261107/matrix-read-256/`；汇总工具为 `scripts/summarize-final-comparison.py`，只汇总已成功核验的同镜像结果。样本载荷另经官方 protoc 按 `value.proto` 解码通过。

尚未完成的最终比较包括匹配持久性的新增/修改/删除/局部修改/批量写/混合负载、4 KiB 载荷、峰值多轮复测和较长稳态。完整长期目标保持进行中；本阶段没有修改数据库核心、打包新 SDK 或覆盖已发布版本。
