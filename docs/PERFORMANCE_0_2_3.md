# FengquDB 0.2.3 性能优化与实际边界

本轮实现三项已批准改动：并发可靠事务合组刷盘、发布状态锁与I/O分离、复用编码缓冲及合并写入；同时优化私有批量索引编辑，并新增C/C++与Python批量写入入口。文件格式和C ABI版本保持不变。

## 测量条件

Windows 11 build 26200，AMD Ryzen 9 9950X3D，Release x64，同一台机器、同一磁盘；值256字节，诊断接收器关闭。SQLite采用官方3.54.1、WAL、可靠事务FULL、预编译语句、WITHOUT ROWID、每连接64 MiB缓存、关闭mmap及自动检查点；缓冲场景NORMAL且计入末尾TRUNCATE检查点。Python3.12.10使用标准库SQLite3.49.1。

各组取三轮中位数，不是长期稳定峰值或统计显著性结论。并发测试在每个场景内交替旧版/新版/SQLite的次序，使用相同可执行文件及相同SQLite DLL；先前与构建重叠的探索数据保留在 concurrency-comparison-0.2.3-20261106，不用于本报告。正式数据均在交付构建结束后采集。

原生12场景和Python3场景各自交替FengquDB/SQLite，旧版与新版套件顺序运行，因此跨版本百分比可能含设备和后台负载波动；没有对这些波动做归因推断。读写输入预先生成，初始数据预热；每个场景完整核对键和值，并关闭重开后再核对。

并发场景基数1万键、独立写线程各400个事务；混合场景4个普通当前状态读线程加1个可靠写线程、1000次更新。FengquDB共享句柄，SQLite每个工作线程独立连接，保留初始化连接。读取计时包含取当前状态与复制到复用缓冲，不借长期快照绕过发布锁。混合读取逐次采样，存在计时/采样开销。

## 并发可靠写入

单位：独立事务/秒，每个事务1条新增且成功返回前完成可靠同步；不能与一笔事务中的多条记录混算。

| 写线程 | 0.2.2 | 0.2.3 | SQLite | 新/旧 | 新/SQLite | 新版实际sync次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4,785 | 4,768 | 4,447 | 1.00× | 1.07× | 400/400事务 |
| 4 | 4,715 | 9,196 | 3,419 | 1.95× | 2.69× | 779/1600事务 |
| 16 | 4,417 | 26,560 | 3,542 | 6.01× | 7.50× | 800/6400事务 |

组提交的收益来自摊薄设备同步，不是降低可靠性。各请求保留独立事务帧、版本、历史及冲突检测；成功返回前同步已完成。空闲时立即处理，没有人为延迟等待成组。组提交不能让单个严格串行的“提交后再发下一笔”请求省掉刷盘。

## Python便利接口

批量场景旧DLL使用同一当前Python封装的逐条回退，新DLL使用txn_put_many；SQLite使用executemany。二者输入均为计时前准备好的bytes列表，Python侧参数转换仍计时。

| 场景 | 旧版 | 新版 | SQLite | 新/旧 | 新/SQLite |
| --- | ---: | ---: | ---: | ---: | ---: |
| read | 365,510 | 368,482 | 335,125 | 1.01× | 1.10× |
| buffered_update | 83,456 | 84,158 | 57,268 | 1.01× | 1.47× |
| batch100_sync | 1,437 | 1,687 | 2,092 | 1.17× | 0.81× |

Python批量约提高17.5%，仍比SQLite慢约19.3%。减少100次FFI调用为1次并不能消除ctypes切片/所有者对象构造和写集分配。C#/Java本轮受益于公共内核改动，尚未新增put_many封装，也未重测其吞吐，不能据Python推算两者速度。

## 恢复、内存与包体

追加日志恢复、复制读取、借用视图、全扫描另用同一共同基准与两套DLL目录交替测量。以下为热缓存恢复耗时，不代表大文件冷启动：

| 数据来源 | 0.2.2恢复ms | 0.2.3恢复ms |
| --- | ---: | ---: |
| insert / buffered+final_sync | 17.947 | 18.555 |
| insert / per_commit_sync | 17.717 | 17.471 |
| update / buffered+final_sync | 20.083 | 19.413 |
| update / per_commit_sync | 19.822 | 19.998 |

恢复大致持平；旧版已经在私有恢复树上就地编辑，本轮没有新的恢复算法收益。共同基准的10条缓冲插入从411,358升至666,520记录/秒；单键缓冲更新从250,941降至246,033记录/秒。不同基准的数据规模及计时范围不同，不能把它们混成同一条性能曲线。

10万键原生单读私有内存增量约54.34 MiB，新旧基本一致，SQLite约35.83 MiB；FengquDB并未实现更低内存。私有批量索引编辑降低的是临时路径复制，100次稀疏更新/1万键的定向测试分配621个索引节点，旧快照仍完整；未测旧算法该用例节点数，不给出虚构降幅。旧节点仍受快照、事务和历史生命周期约束。

Windows核心DLL由208,896增至216,576字节，增加7,680字节（约3.7%）；Linux stripped核心SO为105,384字节。可选诊断/JNI组件独立，DLL大小不代表应用所有依赖。每线程编码缓存最多保留64 KiB，写者复用合并缓冲；编码在途预算64 MiB、256请求，不限制调用方原始写集和全库内存。

## 从PTFramework序列化借鉴了什么

参考 D:/work/PTFramework/Assets/PTFramework/Serialize/CodeHelper.cs 的缓存字段比较/变化片段生成，以及 ByteHelper.cs 的ReplaceBytes：等长数据可覆盖，变长数据需重排尾部。PTSerialize.cs主要承担Unity编辑器代码生成，不适合复制进C++核心。仅只读研究该项目，未修改。

这次落地的是“复用稳定部分，只对变化部分付成本”：一笔批量事务共享同一私有树编辑器，碰到仍被其他版本共享的节点才复制，之后对本次独占节点原地修改；编码字符串和I/O合并缓冲复用容量；bulk入口减少跨语言调用。所有可见旧版本保持不可变。

直接在已发布Protobuf二进制或打开的数据库文件中改几个字节，需要同时解决varint长度变化、后续字段位移、CRC、旧快照、事务回滚和断电原子性。仅缓存旧二进制不能消除这些成本，因此本轮保持追加日志格式。它不是压缩算法，也没有自动字段增量更新功能。

## 继续逼近硬件约束的方向

| 已测过程 | 下一步值得验证的设计 | 预期节省与代价 |
| --- | --- | --- |
| 单线程可靠新增/修改/删除 | 持续剖析编码、索引、排队和设备同步；需要更低尾延迟时选择具备断电保护的低延迟持久介质 | 严格逐笔可靠完成受一次设备持久化延迟约束；应用主动一笔事务包含多操作是另一种语义，不伪装成逐笔提交。 |
| 并发可靠提交 | 研究公平唤醒、减少队列锁往返和批次候选根的重复复制 | 已通过组提交摊薄同步；后续需兼顾低并发延迟、冲突和失败回滚，不能只提高批次上限。 |
| 单键缓冲更新/批量写 | 小写集内联存储、排序数组写集、事务私有arena及复用预编码输入 | 减少std::map节点、临时对象、重复遍历和分配；必须保留写自己可见、同键覆盖、预算及异常回滚。 |
| 热点点读/范围读/索引内存 | 用高扇出紧凑页节点和前缀压缩替代逐键指针节点，按真实负载评估附加哈希索引 | 降低缓存未命中和每键元数据；哈希会增加内存及维护成本，需保留有序扫描，不能单看O(1)。 |
| 大对象只改小字段 | 可选字段/片段patch日志、带基准版本校验，变化链达到阈值后合并全量值 | 节省整值编码和写入，增加读取重组、恢复链和格式演进成本；先做独立原型及断电验证，不在现有文件上偷偷原地改。 |
| C#/Java/Python接口 | 可复用的预编排批次、批量读/写、必要时专用原生扩展和直接缓冲 | 降低边界转换和每条所有者对象开销；需要明确输入存活期及线程规则，不能把序列化时间移出基准却不说明。 |
| 大文件打开/超内存数据 | 分段日志、可定位的紧凑检查点、受控页/值缓存和冷热分层 | 缩短全量重放、降低常驻内存；引入磁盘读、索引持久化和缓存失效成本，与当前全内存热读目标分开测量。 |
| 旧版本释放/内存峰值 | 观测快照寿命、历史固定量和分配器峰值，再评估arena回收或epoch回收 | 引用计数与内存滞留都可能成为并发瓶颈；新回收算法需要专门验证安全性，不能只取消所有权检查。 |

下一阶段优先CPU路径与接口转换，再以独立可切换实现验证紧凑索引和字段patch。上表均为待验证方向，不属于本版已完成能力。不存在不受工作负载、可靠性、容量和硬件约束的一个“通用理论最快数据库”，也没有Redis同条件实测。
