# 三项弱项的定向研究（2026-11-10）

95%读/5%小字段更新的低成绩有明确调度原因：稀疏写入间隔容易超过写线程的短自旋预算，导致反复休眠和唤醒。隔离原型只延长写后短等候，三轮中位吞吐由25.4万升到149.5万次/秒。50ms/1MiB、可靠确认、WAL及业务数据处理均保持相同。此原型尚未接入主代码，主引擎仍是上一轮正式版本。

## 历史成绩没有记错

以下来自原始JSON，均为4KiB正文、4096条档案：

| 版本/口径 | 单调用线程95/5 次/秒 | 八调用线程95/5 次/秒 |
|---|---:|---:|
| 早期手动BUFFERED | 1,055,120 | 1,498,080 |
| 首次自动性能模式完整矩阵 | 205,761 | 945,597 |
| 最新主引擎正式矩阵 | 278,060 | 1,039,310 |

早期BUFFERED允许调用线程直接执行非可靠写，最终显式同步；当前自动性能模式由专用写线程执行，后台按周期/阈值同步。不能把全部历史差值当成同配置下的代码回退，但此前高成绩是真实记录，不是用户记错。

历史依据：[原始比较](../build/business-comparison-20261108/summary/summary.json)、[首次性能模式](../build/write-modes-20261109/summary.json)、[最新正式矩阵](../build/read-reuse-20261110/summary.json)。

## 1. 95/5：写线程过早进入休眠

当前 `periodic_loop` 在处理完一批写入后最多检查512次CPU pause，仍无请求就进入条件变量等待。调用方做完一段读取后才出现下一笔写入；95/5平均约19次读才有一次写，更容易错过这个短窗口。`submit`仍要等待写线程完成内存执行，因此会产生跨线程唤醒和调度往返。

最新正式矩阵的4KiB/单线程95/5每次写入约对应1.7次主动线程切换，50/50约0.06次。该统计含子进程完整生命周期，不能当作每笔请求精确的futex次数；但和下面的受控对照共同支持调度瓶颈判断。

### 隔离对照

仅在 `build/weak-study-20261110/candidate-source` 修改诊断控制，未改生产源文件。基线SO为 `84f27a6bc3a1fff8b66fdbabbb428cc2dfc640f71aa0b002fb6854ce6107817c`；沿用上一轮服务器业务可执行文件，固定CPU 0/2、2 vCPU/4GiB、原生命名卷、4096档案及512MiB缓存预算。每个调用线程一笔在途，仍为性能模式50ms/1MiB，计时包含最后Sync，每次独立进程重开验证所有业务字段。

先做约0.6秒的五个代表性样本：生产25.78万、候选默认控制26.19万，候选只把写线程等待检查上限改到2048次为138.93万、4096次为145.72万；同时增加调用方等候上限的样本为157.19万。候选默认控制和生产接近，因此不是单纯换编译布局带来的数倍变化。

随后仅对“写线程4096次、调用方仍512次”做三轮约1秒、交替顺序复测：

| 指标 | 当前主引擎 | 隔离原型 |
|---|---:|---:|
| 业务吞吐中位值 次/秒 | 254,061 | 1,495,350 |
| 三轮范围 次/秒 | 241,886～279,999 | 1,186,130～1,594,350 |
| P99中位值 | 65.067 μs | 2.615 μs |
| 测量容器CPU用核 | 1.134 | 1.728 |
| 主动线程切换数中位值 | 23,892 | 2,065 |
| 每次写入对应主动线程切换 | 1.791 | 0.0247 |

吞吐约5.89倍。原型仍低于纯读吞吐，且消耗更多CPU，不能称作免费收益。4096次是CPU pause次数，不是4096微秒；耗时随CPU和平台变化，不宜直接把这个数字当作所有移动端的固定最佳配置。

两个单样本边界检查未见回退：4KiB单线程50/50为37.19万→45.20万次/秒；八线程95/5为115.60万→151.15万次/秒。它们不是三轮正式矩阵，不能推广为全部负载结论。

**建议方向：有限、自适应的写后短等候。** 最近请求密集或单生产者连续交互时维持短暂热状态；长时间无请求时进入OS等待，避免持续占核。保留停止、重配置、周期/阈值判断及可靠写屏障。正式接入前还需覆盖Windows、移动端功耗、可靠请求、空闲和并发边界；本轮没有把固定4096次直接改为产品默认。

证据：[初步对照](../build/weak-study-20261110/pilot-report.json)、[三轮及边界](../build/weak-study-20261110/repeat-report.json)。

## 2. 4KiB/八线程整存：阈值触发过于频繁

当前完整保存每次向WAL追加完整新值，1MiB阈值在该负载下频繁先于50ms到达。上轮正式样本每秒约242～300次同步，远高于仅由50ms周期形成的20次/秒。此处没有改整存为业务局部修改，也没有调整后台整理算法。

同一生产库，只比较既有配置的1MiB和4MiB阈值，周期均50ms，三轮约1秒、交替顺序、包含最后Sync及独立重开：

| 指标 | 1MiB | 4MiB |
|---|---:|---:|
| 中位吞吐 次/秒 | 61,444 | 87,990 |
| 三轮范围 次/秒 | 58,913～66,189 | 83,655～91,772 |
| P99中位值 | 2.847 ms | 1.770 ms |
| 同步次数中位值 | 253 | 90 |

吞吐约提升43.2%，可接近历史SQLite普通表84,292次/秒。此前单次0.6秒探针中4MiB的P99也出现过比1MiB更高，因此不能承诺更大阈值总能降低尾延迟。

**建议方向：持续整存业务先使用已有阈值配置做调优。** 4MiB不需要新增引擎实现，但会允许更多待持久化字节，应结合移动端存储、内存和响应目标选择。默认50ms/1MiB仍保留；单笔强制可靠和可靠模式的同步要求没有调整。本轮没有重跑SQLite或其他数据库。

证据：[三轮配置对照](../build/weak-study-20261110/save-report.json)。

## 3. 128B/八线程一次读32份档案：轻量尝试无明显收益

生产、候选默认控制、候选追加构建结果的单次0.6秒样本分别为255,100 / 256,082 / 257,072次/秒。候选尝试避免预先零初始化结果数组，再逐项覆盖；相对候选控制只约0.4%变化，没有形成足够明确的收益，因此没有扩大测试或合入。

该项最新正式成绩250,713次/秒，历史SQLite普通表256,642次/秒，相差约2.3%，应放在上述95/5调度问题之后。未来可研究已有准备读取器对批读键和结果计划的复用；本轮没有测试该调用方式，不能声称已有额外收益。

证据：[轻量探针](../build/weak-study-20261110/otherpilot-report.json)。batch32是一调用读取32份档案，不是32条原子批量写。
