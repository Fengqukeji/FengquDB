# 同业务数据库比较（2026-11-08）

已完成 **936 个正式样本、312 个场景中位数**。每个场景三轮，保留最小/最大吞吐、抽样延迟、CPU、内存、缓存命中率、重试和独立校验。经典来源和建模见 [基准说明](../tools/business_benchmark/README.md)。

结论：本轮完整读取、读多写少及多数可靠提交场景表现较强；大档案并发整存仍有明显短板，结果不支持“全面胜出”。

- 4 KiB 简介、8 并发完整读取 3,716,640 次/秒，为 SQLite 普通表的 1.62 倍、SQLite JSON 的 2.73 倍。
- 同条件非逐次刷盘整存仅 30,754 次/秒，为 SQLite 普通表的 0.36 倍、Redis 的 0.58 倍；本库单线程 82,702，8 并发下降 62.8%，应优先分析并发整存路径。
- 逐次可靠提交整存 4,954 次/秒，高于 SQLite 普通表和 Redis，但低于 MySQL 的 6,890 次/秒。
- 字段投影接近 SQLite 普通表，部分原子计数和大记录转账由 SQLite 领先；完整原始结果均保留。

此结果比较各引擎常用业务实现，不能把所有差异归因于 Protobuf。本轮工作集是 4096 个用户档案，所有方案处理相同十字段并生成相同 C++ DTO；简介 128/4096 字节，编号 7 的初始化 Protobuf 样本为 205/4173 字节，JSON 为 286/4254 字节；编号或变更戳变化后长度可能变化。没有把简单字节读取当作完整业务对象读取。

环境：Linux Docker，客户端及所需服务合计 **2 个指定 vCPU、4 GiB、无额外 swap**，同容器 TCP loopback，单线程或 8 并发。热工作集，Zipf(0.99) 访问。MySQL 8.4.11、Redis 8.10.3、SQLite 3.54.1、yyjson 0.12.0；本库为最近共享读取审查的同一生产库。

## 业务吞吐

以下单位为 **业务操作/秒**。save 使用调用方预建 DTO，完整编码后保存修订戳和简介末字节，不使用八字节 patch；SQL 更新常规列、Redis 写完整 Hash。修订戳包含写入者与序号，每轮从零修订重新装载，首次更新的记录长度增长也在测量内。一次 batch32 操作返回 32 个拥有字符串的完整档案，要看按档案计的吞吐可乘 32；转账算一笔业务事务。A/B/F 的每次读或写各算一个操作。这里是给定并发点的中位数，不是各产品全局峰值。

## 格式控制与归因

SQLite Protobuf 为控制组，使用相同 wire 编解码及可写 BLOB 固定字段接口；主比较仍是 SQLite 普通表、JSON/JSONB，MySQL 类型列及 Redis Hash。它可以说明同一引擎内换格式后的影响，但布局、提取方式和字段更新方式也会随之变化。

| 简介 | 编解码 | Protobuf wire 次/秒 | yyjson 次/秒 | 比值 |
| --- | --- | ---: | ---: | ---: |
| 128 B | encode | 28,064,100 | 7,762,700 | 3.62× |
| 128 B | decode | 27,617,100 | 8,595,250 | 3.21× |
| 4096 B | encode | 11,905,800 | 1,289,820 | 9.23× |
| 4096 B | decode | 11,771,300 | 1,412,190 | 8.34× |

这是使用本库 wire 工具编写的**定型 schema、可信内部数据**编解码，未采用 Google 生成代码，也不做额外的 UTF-8 验证；JSON 仍需处理转义与语法。结果支持此模型/实现的格式成本差异，不能推广为所有 Protobuf/JSON 运行时的固定倍数。业务读取中没有使用固定单键的长期结果缓存；本库使用一次性共享 get，再物化 DTO。revision/credit 增量更新使用本例显式编码器保持的固定头偏移（10/19），这属于本库的增量接口用法；不能将这些偏移照搬到省略默认字段或结构变化的任意生成 Protobuf。补充的 save 则接收调用方完整 DTO，完整编码并覆盖保存，不依赖这些固定偏移；计时包含编码、驱动和提交，不包含从库中先读回对象。

端到端还包含索引查找、缓存、驱动、IPC、分配及持久化。MySQL/Redis 的单条同步调用受往返延迟影响；Redis 同时测了流水线批量读取。即使本库远高于网络数据库，也不能将这个倍数全部称为 Protobuf 优势。

## 持久性与校验

SYNC 对齐为本库 SYNC、SQLite WAL/FULL、MySQL flush_log_at_trx_commit=1、Redis AOF/always。BUFFERED 分别为本库 BUFFERED、SQLite WAL/NORMAL、MySQL flush=2、Redis AOF/everysec；其断电丢失窗口并不等价。组合方案持久性取决于 MySQL，Redis 缓存不持久化。

所有装载和完整预热在计时外；BUFFERED 最终同步也在计时外。每次运行后按独立修订号及余额增量模型核对全部字段，再由独立进程重开核对。每容器最后一个场景另杀服务后重启核对；不代表每个场景都经历杀服务，更不是真实断电认证。原子转账核对每个账户余额及总额，F 原子计数核对每键增量。组合缓存以进程内锁防止旧值回填，仅对应同一业务进程。

## 延迟、波动与资源

每阶段工作线程先建立连接；吞吐的阶段时间含末尾在途操作完成和连接释放，延迟样本仅围绕业务调用及公共消费/记账。SQLite 最后连接释放可能触发正常 WAL 检查点，故它也不是纯引擎调用理论上限。P50/P95/P99 是每轮抽样延迟的分位数，再取三轮中位数；不是合并全部请求的精确 P99，也未模拟开环到达率。BUFFERED 每 64 次采一条、SYNC 每 8 次，单线程最多 100000 条。少样本尾部只能供观察，不能当作生产 SLA。CPU 包含客户端和服务；内存是计时期间 cgroup memory.current 的采样峰值，包含文件缓存。

各轮吞吐区间、P99、CPU、内存、命中率与重试均在 `summary.csv`；`trials.csv` 保留逐轮数据。`coverage.json` 给出全部原始报告路径、SHA256、校验摘要、重启种类及资源限制。

## 使用范围与证据

本轮覆盖用户档案、完整编码保存、字段更新/投影、热点计数、批量读取及两账户事务；批量读取在只读数据上进行，不要求跨键一致快照，Redis pipeline 不能替代跨键事务。未覆盖关联查询、范围/聚合、超内存、长期后台整理、真实断电、开放环路过载、网络远端或 C#/Java/Python 业务客户端。它们不能由本轮吞吐推断。经典工作负载仅借鉴 YCSB A/B/C/F，F 允许原生原子加法，并非官方 YCSB 合规跑分；转账也不是 TPC-C。

完整输出：`build/business-comparison-20261108/formal/`、`formal-save/`、`codec/` 和 `summary/`。原始失败试验也保留：首次编译的十六进制字面量分词错误、首次 MySQL 夹具父目录未创建，以及修正前的短样本，不混入正式汇总。正式编译前还移除了成功路径的错误字符串分配，并让 SQLite 控制组直接借用列字节解析。

核心 SHA256：`2f11cb668c212167f8adc202e31c1c69b456f44aec2de5d623e0317ad092042d`。主矩阵冻结源码及程序在 `frozen-primary/`，完整保存使用另一个已记录身份的扩展驱动，核心库相同；每个业务场景内所有数据库使用相同驱动版本。此次只增加独立工具与文档，没有修改数据库主引擎或发布包。
