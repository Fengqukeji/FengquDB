# 0.2 增量索引与维护能力

> 历史开发记录：下文旧单文件 Database 的代码与接口已删除，项目尚未发布。当前接入使用 [Store API](STORE_API.md)。


这是从正确性基线向可扩展引擎推进的一个子阶段。文件 v1 仍可读写，C ABI v1 原有结构与入口保留；增加入口与状态码，不代表所有产品目标已经完成。

## 索引与读取

使用自有不可变 AVL 树，最长 24 字节的短键内联在节点内，大键和值共享只读所有权。事务基于当前已提交根构造新根，单次键更新只复制 O(log N) 路径，批量 W 次更新一般为 O(W log N)；空索引的首批装载从有序写集以 O(W) 建树，不复制整棵键索引。所有分配、旋转、编码与历史节点准备均在写日志之前；刷盘成功后发布新根与变更批次不再分配。

快照固定旧根，读值视图有效期不变。读键用 string_view 查找，避免为查找复制临时键。范围游标仅固定树根与 O(log N) 路径栈，按需遍历，过滤删除标记；返回切片直到关闭游标前有效。增量游标固定批次引用，不再复制全部键值行。

## 冲突语义

写事务验证每个点读键和写键的最新修改版本。无关键的提交不再互相冲突。读键被改变导致冲突，包含读取 NOT_FOUND；同键写入也导致冲突。删除在内存索引中保留 tombstone 与版本，以检测 absent→put→delete 的 ABA 情况。读自己的暂存写入不需要额外记录基线读取。只读事务仍使用开始时的一致快照。

该 API 尚无事务范围读取，不能将普通快照扫描误当作事务的范围读集。未来加入事务扫描时必须同步实现幻读验证。删除版本标记会随不同已删除键增长，当前通过关闭重开或导出新检查点清除，不宣称全库严格内存有界。

## 历史保留

默认保留上限为 1024 个提交和 16 MiB Protobuf 载荷，两个上限同时生效；超过时按完整提交淘汰。单个提交大于字节上限会整批淘汰，不能返回部分提交。每个上限传 0 表示该维度不限制。

* `fqdb_open_ex`：在恢复前设置历史上限，避免恢复时先保留全日志历史；原有 `fqdb_open` 使用默认上限。
* `fqdb_history_configure`：运行期立即应用新上限；放宽上限不会恢复已淘汰历史。
* `fqdb_get_history_info`：返回 floor_version、批次数、载荷字节和配置。游标 `after_version < floor_version` 返回 HISTORY_LOST（14）。等于 floor 可以继续。

统计为引擎历史队列保留的编码载荷，不包含容器开销、当前索引、删除版本或已被外部游标/快照固定的数据，不可当作 RSS 或严格缓存预算。已有增量游标在队列淘汰后仍可消费其捕获批次。保留设置不写入文件，重开时按打开选项从磁盘重新建立；旧日志仍在源文件。

增量消费者恢复过期游标时，应先捕获快照及其版本 V，用该快照重建，再从 V 消费增量；如果期间再次过期，必须重试或调高保留上限。不能先读当前版本再另取一个不同时间的快照。暂停消费者不能阻止默认历史淘汰。

## 一致检查点导出

`fqdb_checkpoint(db, new_path)` 捕获调用时的一致已发布根，然后分块写到一个不存在的新文件。导出过程中源库可继续提交。成功表示输出数据和提交标记完成系统同步；POSIX 同时同步目标父目录。输出保留全库版本与每个存活键的最后修改版本，省略已删除键和旧变更历史，可以独立打开并继续提交。

它是紧凑备份/离线替换来源，不是在线缩小源文件的 API，不自动替换或删除源库。目标已存在时返回 ALREADY_EXISTS（15），绝不覆盖。输出失败不封锁源库写入。0.2.2 改为私有临时文件写完并同步后发布，不再在最终目标暴露半成品；发布后父目录同步失败可能返回 COMMIT_UNKNOWN。崩溃可能留下临时文件。只有成功返回的输出可直接确认为已完成备份，详细边界见存储契约。

输出使用文件格式 2：32 字节文件头保留基线版本和 checkpoint-required 标志；`FQCHK001` 分块保存 SnapshotEntry 的 key/value/修改版本；`FQBASE01` 完结帧保存条目数、分块数与跨块连续 CRC32。帧仍使用原有长度/序号/CRC/尾部结构。分块通常约 1 MiB，大值可使单块更大，仍受 64 MiB 帧限制。

恢复必须看到有效完结帧；已存在格式 2 头但检查点未完成时返回 CORRUPT，不截成空库。检测整个块的缺失依赖最终计数和聚合 CRC。检查点之后继续使用普通事务帧；其不完整尾部沿用正常恢复规则。CRC 用于意外损坏检测，不提供恶意篡改防护。

打开导出文件时增量 floor 是基线版本，之前的增量不可用；从基线之后可继续消费。旧 0.1 运行库拒绝格式 2，但可继续打开由 0.2 普通追加写入的格式 1 文件。

## 三语言接口

C#：构造参数 maxHistoryCommits/maxHistoryPayloadBytes，HistoryInfo、ConfigureHistory、Checkpoint。

Java：带历史参数的构造器，historyInfo、configureHistory、checkpoint。Java 计数限制为非负 signed long 范围。

Python：构造参数 max_history_commits/max_history_payload_bytes，history_info、configure_history、checkpoint。参数进行 uint64 范围检查。

本轮原生 API 为加法扩展，语言封装应与 0.2 原生库配套，不能只替换 JNI 或 JAR 的其中一端。

## 验证与剩余工作

测试新增无关键并发提交、读写偏差、缺失键 ABA、提交前分配失败、索引平衡/计数/快照稳定、按键更新分配规模、恢复期历史限额、过期游标与旧游标固定、检查点版本与压缩体积、逐字节截断、导出中断、整块缺失及失败后源库继续写入。

性能比较使用同一个 0.2 基准可执行文件分别加载旧 0.1 DLL 和新 DLL，区分插入/预填充后更新、逐笔刷盘/缓冲末尾刷盘，并记录复制读取、视图读取、完整扫描与热恢复。重点是衡量本次改动，没有与 Redis 等竞争产品对测。

仍需磁盘分页索引、容量受控缓存、group commit、在线原子切换式整理、独立 Linux 主机与三语言双平台矩阵、真实断电和长时间压力。本轮结果以实际验证报告为准。
