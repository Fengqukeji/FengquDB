## 已确定的默认值

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 写入周期 | 100 ms | 单调时钟；有待处理请求时按期安排处理 |
| 业务字节触发门槛 | 1 MiB（1,048,576 B） | 达到门槛提前处理；不是每批固定大小 |
| 接收结果 | 待确认凭据 | 接管输入不等于已经可靠保存 |
| 可靠成功 | 对应日志同步成功后通知 | 一批共享同步；保留各事务版本及原子边界 |

Windows、Linux及移动端采用同一默认值，不根据平台名称偷偷改成256 KiB。周期、字节门槛和队列内存预算允许分别配置；256 KiB可以作为用户调整或未来移动端测量中的对照值。

1 MiB是已有4 KiB完整保存原型中的有效点，不能据此保证所有数据大小和手机都最佳。核心原有最大分组笔数等边界也会影响实际批次，接入时必须覆盖小记录、多操作事务、超门槛大事务及背压，不能仅按4 KiB档案作特化。

## 周期和开销

采用等待通知及有数据时的截止时间，不用忙循环。空队列时休眠等待请求，不为每个周期扫描所有键、集合或空文件；阈值达到时只唤醒写者。

低流量且达不到字节门槛时，100 ms、10 ms、1 ms分别对应约10、100、1000个周期刻度/秒。短周期容易产生更多小批次，增加同步调用、唤醒与功耗。高流量时由字节条件提前触发，缩短周期未必提高吞吐；实际完成频率还取决于处理和设备同步耗时。

慢盘上，可靠确认延迟包含等待、已有积压、日志写出和同步，不会因为配置100 ms就被保证在100 ms内完成。应记录队列最老请求年龄、实际批次字节、事务数、写入/同步耗时及队列预算使用量，再决定是否调整阈值。较大批次可以摊薄同步固定成本，也可能拉长单次I/O，不能只凭磁盘型号增大或减小。

## 断电与闪退

100 ms不是严格的最大数据损失窗口：阈值可以提前触发，慢盘和积压也可以令待确认时间超过一个周期。故障只允许影响尚未可靠确认的请求；已经可靠成功的提交必须在系统和硬件遵守同步语义时可恢复。

如果收到请求立即向业务宣称保存成功，随后仅放在 RAM 等周期，那么这些输入确实可能丢失。待确认凭据不能被包装成可靠成功。若要求待确认输入本身也必须可恢复，就必须让输入或其来源先完成可靠持久化；这项成本无法由校验、双份内存或长周期消除。

关键保存允许显式 `FlushAndWait` 提前处理并等待结果。Unity挂起与正常退出可以主动请求保存，但系统可能不给退出回调执行时间，因此它们不能成为断电安全的唯一依据。不要在Unity主线程用每笔阻塞等待破坏集中合批；应通过异步结果或批次确认接入。

在UTF-8输出中，字符门槛对应的字节数随内容变化，ASCII和中文日志并不相同。达到门槛的路径只调用 `sw.Write(LogBuffer)`，不显式 `Flush()`；若它恰好清空了构建器，下一次定时回调的条件也可能跳过 `sw.Flush()`。因此100 ms并非该日志所有流缓冲尾部的严格刷新上限。

普通 `StreamWriter.Flush()`没有请求文件的可靠设备同步，不能等同数据库可靠提交。`LogManager.cs`把路径设置在 `Application.persistentDataPath`，并在正常退出时调用Close；这些做法可参考，但不提供突然断电零丢失保证。日志源码中的吞吐注释未经本轮验证，不作为数据库性能证据。
