# 默认周期写入：接入、审查与业务复测（2026-11-09）

> 历史实现与测试记录，后续内存确认的性能模式已替代其默认提交契约；当前语义见[写入策略](STORE_WRITE_POLICY.md)，新结果见[性能模式复测](STORE_PERFORMANCE_MODE_20261109.md)。

完成主引擎100 ms／1 MiB默认周期提交、持久配置与C/C++、C#、Java、Python接入。普通同步写在周期模式立即返回ASYNC_REQUIRED；关闭周期后保留原严格路径。使用方式见[写入策略](STORE_WRITE_POLICY.md)，审查及验证见[接入审查](STORE_WRITE_POLICY_REVIEW_20261109.md)。

## 口径

沿用4096档案、十字段DTO、128/4096 B简介、Zipf(0.99)、相同种子与轨迹、Linux同一镜像、CPU 0/2共2 vCPU、4 GiB和无额外swap；数据在原生命名卷，热数据。每项校验后删除本次拥有的夹具，释放前一项的文件缓存。实际初始化Protobuf为205/4173 B。计划1秒生成请求，每64操作检查停止时间；计时继续至全部已提交操作可靠完成及冲突重试结束，尾批按默认周期处理，没有通过主动Sync强行提前刷盘。纯读采样每64次，其余每8次。

调用契约变化必须单独理解：旧测试每调用线程最多1笔未完成；本次完整保存每调用线程最多512笔未确认，其余写入合计最多512笔（单调用线程512，8调用线程各64）。同时只有一个数据库业务写线程执行。线程数列表示调用线程，不能把它解读为相同在途请求数或单笔延迟下降；差异同时包含异步窗口和合批策略，不能全部归因于引擎代码或Protobuf。

完整保存使用公开submit_put盲覆盖；字段修改、计数、转账使用原快照事务的submit，CONFLICT从新事务重做，不改为静默重定基或丢失更新。异步重试可能改变重叠操作的成功顺序；每份档案按实际成功版本选取最终修订，计数与转账验证所有成功操作及每户余额。入队不计可靠成功，重试不算额外业务吞吐。

以下写负载历史列均取SYNC；纯读三项取旧BUFFERED只读结果，它们不产生写入，不能把旧BUFFERED写入改称严格可靠。batch32仍是读取32份档案，不是32条原子批量写。

## 结论与限制

完整保存可以通过多个待确认输入摊薄同步固定成本，出现明显吞吐收益；收益以异步并行在途请求和更长的确认等待为代价。只读路径保持直接读取。

现有事务在调用方读取旧快照后排队，100 ms周期使热点写冲突成批出现；重试再次等待周期，计数、转账和部分小字段更新明显回退。这是当前方案真实短板，不能声称默认模式对所有写入大幅提速。此类业务目前应选择严格模式；若继续优化，应另行设计写线程内执行的原生原子命令，保留一般事务的快照契约，不能为跑分忽略冲突。

例如余额100时，两个排队事务都算出101；第一笔提交后，第二笔必须冲突并重读101再算102，下一次提交又可能等一个周期。完整保存的盲覆盖没有这类读依赖，因而更容易把大量独立请求合为一次同步。线程排队本身没有消除业务读依赖；原生计数命令可以让写线程按最新余额逐笔执行，但当前普通事务不能被擅自改成这个语义。

短样本及后台整理会带来波动；完整最小/最大、吞吐离散、混合P50/P95/P99、入队P99、确认延迟、CPU、容器内存、I/O读写字节、刷盘合组及重试均保留在CSV/JSON。这里是闭环有界窗口成绩，不是开环SLA、移动真机、冷缓存、长期稳定吞吐或真实硬件掉电验收。
