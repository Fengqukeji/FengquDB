# BUFFERED 竞争优化隔离审查

主核心尚未合入此候选。为解决 BUFFERED 原子写入在竞争时频繁交接写租约的问题，初始候选保留无竞争直接路径，仅在竞争时复用已有队列，合用写租约与发布；内部原子事务处理后提前释放不对外暴露的捕获。手动可取消事务、带期限调用、线程 I/O 预算及组大小为 1 的路径继续直接执行。SYNC 的发布仍等待同步成功，BUFFERED 不增加持久性承诺；完整私有二进制缓冲的减法裁剪未改。

## 三轮交替实测

证据位于 `build/buffered-lab-20261107/`：`ab-report.json`、`ab-summary.json/csv/md`、每个 `ab-*/report.json` 及其原始用例报告。按 A/B、B/A、A/B 顺序运行，合计 54/54 次通过完整模型和独立进程验证；每组最后一项另执行服务重启验证。容器和卷均经所有权检查后清理，158 个主核心/测试快照文件哈希仍匹配原基线。

基线和候选使用相同 C++ 比较程序，SHA256 为 `6c17b52fc163b7ac1ff430543b72ad2978d1897c67b9d54af6ff0d1b3f44ce27`。服务与客户端合计 2 个不同物理核心、4 GiB，无额外 swap；数据使用新建 Linux 命名卷。种子 131072 条，值为 256 字节合法 Protobuf。覆盖/混合每点 5 秒，新增每点 1048576 条，实际单线程新增计时约 3.8 秒，已替代之前约 0.079 秒的短样本。

## 一致性验证与后续方案

初始候选通过 Windows operations/features/io_budget 3/3，以及 Linux ASan/UBSan 含泄漏检测 3/3；后加检查点同步失败发生于原子 prepare 之前的用例，两平台 operations 各 1/1 通过。Docker 两种持久性 smoke 共 2 项含自检、模型和重启通过。失败注入证明该检查点场景返回 IO_ERROR，没有复现先前怀疑的空事务 COMMIT_UNKNOWN 收尾问题，未为此修改生产代码。

第二份 `source-adaptive/` 提案使稀疏写入碰撞继续直接交接，至少三个原子写调用者同时争用后才启动合组；已有组仍允许等待者加入。另增加两名等待写者不入组且计数正确释放的确定性用例。

初次 operations 在两平台均因测试仍强制单个 BUFFERED 写者入队而失败；这是旧提案的测试假设。调整为观察稀疏直接等待，另增加 8 名等待者在检查点同步失败后全部退出、计数归零、确认前缀恢复与继续写入的检查；生产提案代码没有为此更改。最终 Windows 与 Linux operations 各 1/1 通过，features/io_budget 在之前各自通过。Linux ASan/UBSan 启用泄漏检测与遇错退出。

Linux TSan operations 通过，前 4 次因已知地址布局在 main 前失败并保留日志，第 5 次进入并完成测试。检测包装文件将 stdout 设置为即时刷新，确保进入 main 的标记不会被重试条件误判；编译与执行前后源码清单匹配。Docker 两种模式 smoke 共 2 项含模型和重启通过。
