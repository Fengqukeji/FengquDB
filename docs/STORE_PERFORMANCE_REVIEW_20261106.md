# Store 性能、体积和代码审查记录（2026-11-06）

本轮针对剩余功能交付后的源码优化；不改变公开 ABI、SYNC/BUFFERED 持久性、事务冲突规则及 0.3.1 完整私有二进制的减法裁剪。旧发布 SDK 保持不变。

主要改动：

- 查询未命中直接返回空结果，集合和索引内部不再以异常表达正常缺失；首次读取和写入复用已取得的基础记录引用，减少重复索引定位。
- 命令解析只在当前调用期间借用输入视图，事务暂存仍拥有自己的数据；C++ 请求预留最终编码容量，避免大值编码后的扩容。
- 命令响应先校验完整编码大小，再一次分配最终 C 返回缓冲并直接编码；移除中间编码字符串、每行临时消息及返回前的整块复制。
- Hash 直接读取固定同一不可变视图和读取时间，省去临时快照对象及其计费；返回值仍单独计入固定内存预算。
- 普通文本键整段复制，二进制转义预留完整容量；扫描、List 和计数操作不生成用不到的成员键。冷错误构造集中为不可内联函数，减少热路径代码重复。

审查问题及修复：

1. 长二进制键转义后的分页游标可能超过普通键的 64 KiB 限制，导致合法下一页请求被拒绝。现在扫描/索引查询单独接受不透明游标上限 263168 字节；Hash、Set、SortedSet 和非唯一字段索引均增加长游标、重启与校验回归。
2. Hash 单次直接读取曾额外占用快照槽，已有快照耗尽额度时会错误返回 LIMIT。现在与普通 KV 单次读取一样，不消耗快照槽；共享 SDK 测试覆盖 max_snapshots=1 已占用时的读取。
3. 响应总大小过去没有在分配前完整计算末尾游标。现在统一将值、所有行和游标纳入 64 MiB 上限，分配前拒绝超限。输入借用另以调用后立即覆盖请求缓冲、随后提交并重启读回的方式验证。

测量采用同机、相同可执行文件、旧/新 DLL 隔离目录，交替顺序执行 5 轮并取中位数。每轮预热读取缓存，结束时同步、重开并验证数据。写入计时均为 BUFFERED，末尾 sync 不计入吞吐；这些结果不能推导单条每次可靠刷盘性能，也不涉及 SQLite/Redis 对比。同一个 C++ 基准使用新头文件编译，因此 C++ 请求预留容量同时作用于两边，不单独归因到新引擎。

普通 KV 命中和新增约 1% 的变化属于微基准噪声范围，不宣称稳定收益。Hash 新增的吞吐提高，但 P99 从 20.9 升至 29.1 μs；尾延迟未改善，负值保留，不以吞吐提升替代尾延迟结论。
本进程完整工作负载的峰值私有内存中位数为 11,751,424 → 9,854,976 字节，降低 16.14%。这是包含基准计时数组和分配器的进程累计峰值，不是单个调用的缓存额度或数据库最低内存。

Windows 核心 96、诊断 7、JNI 50 个导出名称全部保持一致；Linux 动态导出（含版本标签）97 个也全部一致。体积、节区和 SHA-256 见 [Windows 二进制复核](../build/performance-review-20261106/binary-review.json)、[Linux 二进制复核](../build/performance-review-20261106/linux-binary-review.json)。
