# 数据库能力与业务用途

下表对应当前源码的 Store 引擎。项目尚未发布；旧单文件 Database 引擎、接口和迁移器已删除。库、头文件和语言绑定须配套构建，旧开发包仅供追溯。当前代码移除、验证和性能诊断见 [核心审查](STORE_CORE_REVIEW_20261108.md)。

FengquDB 是进程内的二进制键值数据库。业务把对象编码成字节保存；可以用官方 Protobuf 生成业务类，也可以保存其他字节。Protobuf 是编码格式，不等于压缩。字段索引只解析配置过的顶层标量，不会自动理解所有业务关系。

| 能力 | 直白例子 | 用途与设计原因 |
| --- | --- | --- |
| 新增、读取、覆盖、删除 | 保存 player/42，按同一个键读取、更新或删除 | 用 ID 找一条记录，避免每次遍历全部数据；缺失和已有空值明确区分。 |
| 条件写入与版本 CAS | 只有余额仍是读到的那个版本时，才扣款 | 防止并发线程用旧值覆盖新修改；冲突后重读重算。 |
| 仅变化时写入 | 玩家数据没变就跳过保存 | 比较原字节，减少无变化提交、WAL 和刷盘；语义相同但编码字节不同仍视为变化。 |
| 原子整数加减及范围约束 | 金币加 5，结果须在 0 到上限之间 | 不必在业务层先取值再更新；越界或 int64 溢出拒绝，不回绕。 |
| 多记录事务与回滚 | 扣掉金币，同时增加道具 | 一组修改要么全部生效，要么都不生效；中途出错可撤销。 |
| 事务内读取、保存点 | 先加道具，再撤销其中一个步骤 | 事务能读到自己的修改；保存点保留既有工作，避免复杂操作全部重算。 |
| 点读与范围冲突检测 | 查询某队成员后更新队伍，期间新增成员会使提交冲突 | 覆盖“之前不存在、后来出现”及扫描范围变化；它不是 SQL 查询优化器。 |
| 一致快照 | 导出期间后台继续修改，导出仍看到同一版本 | 防止导出、遍历和上层索引重建时前后数据不一致。 |
| 并发读取与合组刷盘 | 多线程各提交一笔存档，共享一次可靠同步 | 摊薄设备同步成本，各事务保留独立原子边界；读者在刷盘期间仍可读上一完整版本。 |
| 批量与准备键 | 一次读取 32 条，或反复查询同一热点键 | 减少跨语言调用及重复参数构造；批量是否更快须按实际载荷测量。 |
| 目标缓冲复用与共享值 | 循环向同一数组读取；C++ 持有只读值视图 | 少分配、少复制。Java/Python 有显式可选的缓冲复用途径；视图与子句柄须及时释放。 |
| 二进制局部修改与减法裁剪 | 只替换记录中变化的字节区间，裁掉不需要的部分 | 保留完整私有二进制缓存，在其中覆盖、裁剪和必要地移动尾部；不反复拼接所有旧块。Protobuf 变长前缀由业务正确维护。 |
| 超内存数据与受控缓存 | 文件大于缓存，只加载访问到的页和值 | 避免全库常驻内存。缓存、增量元数据、事务、快照和固定对象分别计费；不等于进程 RSS 硬上限。 |
| 范围与前缀分页 | 按 player/42/item/ 前缀取下一批物品 | 有序定位并按批读取，避免一次返回过多内容；支持正反方向。 |
| 字段与复合索引 | 根据队伍与等级查玩家 | 只维护变更字段对应的索引；支持等值前缀、范围和分页，避免解码全库。 |
| 唯一、必填约束 | 玩家 ID 不能重复，指定字段必须存在 | 在事务提交时保证约束；Protobuf optional 明确保留 0 和空串，业务非空规则仍由业务校验。 |
| 字段投影 | 查询玩家时只返回名字和金币字段 | 减少上层传输和解析无关字段；不是任意 SQL 表达式。 |
| 原生复杂查询与自动索引选择 | 红队 20～60 级或 VIP，排除封禁；按金币取前 20 名 | C++ 内过滤、Top N、预算和 Explain，减少跨语言传输。 |
| 聚合、分组、去重 | 各职业人数、总金币、平均金币，只取人数超过 100 的职业 | COUNT/SUM/MIN/MAX/AVG、GROUP BY/HAVING、DISTINCT。 |
| 字符串匹配与等值关联 | 名字包含“张”，关联玩家与订单，找无订单玩家 | Contains/LIKE/受限正则/UTF-8 编辑距离；主键、索引或有界哈希关联。 |
| TTL 与分批回收 | 会话到期后不可见，后台按批清理 | 读请求按到期时间判断，后台不必扫描全部值；实际文件空间由后续整理回收。 |
| Hash、Set、List、SortedSet | 物品属性、去重成员、任务队列、排行榜 | 按元素增量读写，不必每次重写整个大集合；集合操作也可放进事务。 |
| 检查点、快速重启与在线整理 | 周期性收拢元数据，后台删除过时内容 | 减少重启重放量，回收旧日志空间；旧快照仍能读取旧代际，释放后才回收文件。 |
| 维护取消、期限与 I/O 预算 | 整理任务每轮最多读写一定字节 | 限制后台工作量，避免无限追赶；预算不等于设备 I/O 的毫秒级截止保证。 |
| 完整备份、增量链、PITR | 昨天全备，今天增量，恢复到某版本或时间 | 不必反复复制所有历史；校验身份与连续版本，输出到新的独立目录，避免覆盖原库。 |
| 持久历史水位与变更订阅 | Wiki 只处理上次消费之后的记录变化 | 以提交为单位拉取并显式确认；持久水位可跨重启保护历史，落后超过可用历史会明确报错。 |
| 中断恢复与损坏检测 | 进程被杀后重开，只丢弃不完整尾部 | 校验完整记录与事务边界，完整坏记录报损坏；不能把 SIGKILL 测试称为真实硬件掉电验收。 |
| 显式根目录与短文件 | Unity 保存到 persistentDataPath/db/main | 不依赖当前工作目录；库内平铺短文件，创建前检查路径预算，日志和备份由宿主显式指定。 |
| 可选诊断与状态统计 | 找到哪次提交慢、哪一阶段 I/O 失败 | 用版本、阶段、偏移及错误码定位；诊断日志不记录业务键值，也不参与数据库恢复。 |
| C/C++、C#、Java、Python | 游戏或服务直接链接库调用 | 无需启动独立数据库服务；一个 Store 目录由一个实例独占，进程内可多线程使用。 |

最短 C++ Store 增删改查：

```cpp
#include <fengqudb_store.hpp>

auto db = fengqudb::Store::open_at(persistent_root + "/db", "main");
db.put_if_changed("player/42/hp", "100");
db.put_if_changed("player/42/hp", "80");
auto hp = db.get("player/42/hp"); // std::nullopt 表示缺失
db.delete_many({"player/42/hp"});

auto tx = db.transaction();
tx.put("player/42/gold", "80");
tx.put("player/42/item/sword", "1");
auto result = tx.commit(); // 必须检查结果；冲突时重开事务重做
```

默认性能模式在内存原子生效后确认，后台按 50 ms／1 MiB 可靠同步；force_reliable 或可靠模式等待同步成功。底层 SYNC 表示系统同步 API 返回；BUFFERED 需要显式 Sync。设备和文件系统须正确执行同步。所有权、错误和预算见 [Store API](STORE_API.md)，操作见 [操作说明](STORE_OPERATIONS.md)，查询见 [索引查询](STORE_QUERY.md) 和 [复杂查询](STORE_SELECT.md)，业务结构生成见 [Protobuf 接入](../examples/protobuf/README.md)。

当前不提供 SQL 文本解析器、远程服务、账号权限、复制和跨进程协同；已支持程序化多源等值 JOIN，边界见复杂查询文档。全文、向量检索、模型推理、RAG/Wiki 业务层、透明加密及任意业务 schema 自动迁移尚未实现；上层保存模型结果、消费变更不能被称为已有这些专用能力。

用户于 2026-11-07 明确暂缓向量检索、全文检索和 RAG/Wiki 上层，留待以后单独设计；本轮先完成数据库底座及其性能、可靠性和接入验收。

## 早期验收记录（历史）

下列进展和比较只代表记录阶段，当前默认行为与接入以上述契约和文档入口为准。

主工程现已采用分段文件、稀疏/整段空间回收及原子操作私有事务额度修复，保留原提交调度和减法裁剪；分段布局按创建选项启用，默认仍为单文件。采用后修正了 Windows 分配量滞后造成的后台触发问题，相关跨平台回归、安装后消费者及两布局默认日志压力通过，见 [采用与验证记录](STORE_ADOPTION_REVIEW_20261107.md)。[早期复制原型](STORE_MAINTENANCE_REVIEW_20261107.md)、[早期原位回收](STORE_RECLAIM_REVIEW_20261107.md) 和写者调度实验的采用状态仅描述当时阶段，不应当作当前主工程状态。

当前证据覆盖注入故障、截断/进程崩溃、实际磁盘及内存上限、日志轮转和数值边界。超过 2 GiB 存活值在 512 MiB 容器内的全字节校验、旧快照及独立重开已通过；那次未启用后台维护，不能代替正在准备的超内存、批量读取和自动整理组合验证。默认日志已实际跨过 64 MiB 总量并核对 8 MiB 轮转、七天过期样本清理；具体源码身份与复用范围须结合各阶段报告理解。真实硬件掉电和长期生产运行尚未验收。

同一冻结原生核心的五方案已完成 1280 项扫描：256 B 共 640 项，4 KiB 读取 160 项、写入 480 项；960 项三轮峰值复测正在运行，见 [当前比较记录](DOCKER_CURRENT_COMPARISON_20261107.md)。当前 SDK 已通过两平台三语言、两布局的批量接入验证；正式调用成本复测尚未执行，不能拿旧核心成本替代。单线程可靠写入、部分小值并发读取以及 4 KiB 缓冲批量写入仍有 SQLite 领先的区间；没有全工作负载胜过其他数据库的结论。历史 [SQLite 对比](SQLITE_COMPARISON_20261106.md) 使用旧单文件引擎，不能当作新版 Store 的最终结果。
