# 主引擎整合与实测

后续审查修复见 [主引擎代码审查](STORE_REVIEW_20261108.md)。本文性能数据对应整合时的版本，未用后续功能验证替代性能实测。

2026-11-08，retained2 派生的按字节分流方案已整合到 `src/paged/`，默认新建非分段 Store 使用它；没有增加另一套查询、事务或 SDK 引擎。C、C++、C#、Java、Python 的接口定义保持不变。历史研究目录只保存对照记录，正式构建使用工作区主源码。

## 本次处理

- 保留四单元 COW 小日志、一次提交一次同步、连续描述数组、复用工作缓冲、大值借用、完整二进制缓存及减法裁剪。
- 默认按此次同步暂存的实际字节分流，小于 32 KiB 使用小通道，其余使用顺序追加通道；32 不是固定批量行数。
- 文件层改为共享读锁，普通持久化 I/O 和等待位于映射写锁之外。提交工作与借用值在屏障结束前保持有效，发布仍在持久化成功之后。
- 移除约 32 MiB 的研究文件上限；保留单值 16 MiB、单事务 64 MiB 等现有公开限制。三个合法 12 MiB 值、继续小写、快照、检查点及独立重开通过。
- 小日志不再常驻所有历史页的完整数据体，保留至多约 16 页的尾部缓冲；旧页按需读取并校验。页元数据和映射仍随日志增长。业务页和值缓存继续遵守原配置，缓存预算不是整个进程的 RSS 上限。
- 恢复按 64 KiB 块校验数据，不为完整大提交再分配一个等大的恢复缓冲。
- 维护计量、分段文件、原地空间回收和备份恢复保留。双通道向直接镜像的转换支持小额 I/O 预算下继续推进；写入全部镜像、同步、原子发布后再切换，快照逻辑偏移保持一致。
- Windows 转换在 Store 的目录租约和文件层排他锁保护下关闭数据句柄、发布并重新取得数据租约；不确定结果阻止继续写入。Linux 保留已打开镜像的原子替换方式。
- 移除主库中的研究环境变量选择和研究诊断导出，统一为正式构建。

备份/整理构建输出、分段布局，以及完成上述转换后的代际使用直接记录路径。下列小写加速结果适用于仍使用双通道的代际，不能解释为所有维护之后和所有布局均有同样加速。

## 并发与写入结果

报告：`build/engine-merge-20261108/performance-report.json`、`summary.json`。旧主库和最终合并主库在同一个 Linux Docker 原生卷环境交错运行；4 个 CPU、2 GiB 内存，编译、Windows 测试和 sanitizer 均已结束。全部样本和慢样本保留。

并发输入为 512 个 256 B 只读键和一个独立修改键，3 个读线程，混合场景另有 1 个持续 SYNC 写线程。每轮 600 ms，每个实现每种场景两轮。键通过一笔初始化批量写入；关闭业务缓存不等于清空操作系统页缓存。

| 场景 | 旧主库 | 合并主库 | 结论 |
| --- | ---: | ---: | --- |
| 关闭业务缓存，只读 | 426 万次/秒 | 419 万次/秒 | 约下降 1.6% |
| 关闭业务缓存，混合负载的读取 | 430 万次/秒 | 310 万次/秒 | 约下降 28.0% |
| 同一混合负载的同步写入 | 890 次/秒 | 1470 次/秒 | 约提高 65.2% |
| 命中缓存，只读 | 586 万次/秒 | 587 万次/秒 | 基本持平 |
| 命中缓存，混合负载的读取 | 568 万次/秒 | 565 万次/秒 | 约下降 0.6% |
| 同一混合负载的同步写入 | 877 次/秒 | 2078 次/秒 | 约为 2.37 倍 |

原候选持锁刷盘的测试曾使关闭业务缓存的混合读取降至约 550–1215 次/秒，见 `preflight-report.json`。修复后不再出现这个阻塞结果。上表仍有真实回退，不能称为所有并发场景都更快。关闭缓存时还有共享锁、映射定位等开销，且合并主库同时完成了更多次写入；要拆分各项原因还需固定相同写入速率的专项测试。

独立单线程小写：256 B 完整修改，每次同步，每轮 256 次，双方各两轮。按累计耗时计算，旧主库约 913 次/秒，合并主库约 2098 次/秒，约为 **2.30 倍**。双方每轮均有 256 次持久化同步；各样本独立重开、核对完整字节并 verify。候选累计请求写入量仍约为旧主库的 29.5 倍，不是固定存储空间倍数。

64 KiB × 32 条原子批量，每轮 12 笔事务，双方各两轮：累计吞吐约 8178 与 8134 条/秒，相差约 -0.5%，本次未证明稳定优势；各轮有明显波动。两边每轮均 12 次同步、780 次 pwrite，请求字节约 25.19 与 25.21 MB。此前原型约 +8.1% 的短测仍保留，不能用它覆盖本次结果。

## 容量、内存和启动

2048 条 × 64 KiB，共 128 MiB 业务值；64 KiB 业务缓存，完成检查点并关闭，然后用独立进程打开，完整扫描核对值并 verify。

| 指标 | 旧主库 | 合并主库 |
| --- | --- | --- |
| 逻辑文件长度 | 134631540 B | 134631540 B |
| 两次重开耗时 | 3.15 / 3.29 ms | 98.07 / 97.92 ms |
| 重开后的进程 RSS | 约 4.5–4.75 MiB | 约 5 MiB |
| 扫描后的进程 RSS | 约 4.75–5.25 MiB | 约 5–5.5 MiB |

这证明原型容量边界已移除，历史业务值没有整库驻留在内存中。**启动仍需要扫描双通道校验和重建映射，本次明显慢于旧主库**；约 98 ms 是本机该样本的绝对耗时，不能外推到 GB/TB 数据或清空 OS 缓存后的启动。尚未增加持久化映射检查点。

## 正确性与构建证据

- 最终 Linux 21 项 CTest 全部通过，包括事务、SDK、索引/约束、TTL、原子操作、快照、历史、Watch、维护预算、备份恢复、分段、空间回收以及新增的混合文件检查。
- 新增确定性检查暂停实际持久化屏障，确认关闭业务缓存的旧视图读取仍可在屏障释放前完成；不是仅用吞吐推测不存在阻塞。
- ASan/UBSan 覆盖混合文件、跨 32 MiB、借用值、批量路径、分页缓存回收和限额转换。最终平台修复后重新运行混合文件 sanitizer 检查通过。
- Windows x64：C++ SDK、维护、分段与新增混合文件四项检查通过；核对实际加载 DLL 路径。
- Linux 和 Windows 的 Python 接入检查通过，涵盖普通/批量调用、事务、索引、快照、备份恢复、历史、Watch 和维护限额。未重新执行 C#/Java 的独立运行测试。
- 崩溃点 2 在真实持久化屏障之前，测试允许完整旧状态或完整新状态，仍要求索引与业务数据一致；屏障之后必须恢复完整新状态。用于恢复 spill 的 BUFFERED 数据与人工追加的非法 WAL 先显式同步，保证测试实际存在磁盘输入。没有把尚未写到文件的数据当成恢复成功。
- Python 测试清理器增加双通道身份、镜像、CRC、UUID 和代际配对校验后才删除文件，未知文件仍拒绝清理。

本轮没有设备级真实断电实验，也没有完成所有并发形态的性能矩阵。当前主要性能后续项是关闭缓存时的混合读取和双通道大库启动；它们是实测限制，不能被“已合并”覆盖。
