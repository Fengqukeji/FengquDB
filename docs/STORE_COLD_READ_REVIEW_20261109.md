# 冷读校验优化、P99 与事务冲突说明（2026-11-09）

冷缓存普通值读取的重复完整 CRC 已移除，仍保留最终完整数据的长度和 CRC 校验，以及补丁/引用和缓存标签检查。默认保持性能模式 50 ms / 1 MiB，写线程刷盘方式不变。

## 修改与验证

原始普通值未命中缓存时，Generation::value 读取 base 后校验一次，公共结果出口又对同一份数据校验一次。无补丁分支中的 base 就是最终结果；现在仅在公共出口校验，结果缓存继续保存已知 CRC。补丁冷重建仍在公共出口校验最终结果，不省略独立的文件帧/引用检查。

新增测试构建专用观察器，按当前线程和指定内容长度计数：

- 直接及分段文件，值长 0、1、128、4093、65533、1048573 B，普通冷读恰好一次逻辑内容 CRC。
- 缓存命中再次读取时不重新扫描内容。
- 错误预期 CRC 和真实文件内容篡改仍返回 CORRUPT。
- 冷补丁重建仍做一次最终内容 CRC；已有减法裁剪、保存点别名和可靠重开回归继续通过。

Windows、Linux 各 6/6 相关原生测试通过：paged_storage、paged_store、paged_store_sdk、paged_crc_delta、paged_committed_cache、paged_write_policy。两平台 C#、Java、Python 写策略与常规接口回归通过。本次没有重复全量性能矩阵或 sanitizer；修改未改变缓冲区读写边界或事务提交逻辑，相关校验/恢复/并发路径已覆盖。

## 最小性能对照

Linux 2 vCPU（CPU 0、2）、4 GiB，直接文件布局，数据库页/值缓存均关闭，操作系统文件缓存已预热。四个键，单调用线程，每项约 250 ms，旧/新库交替三轮。每次读用同一公开 get_shared 接口；计时前后完整核对数据，计时内核对长度与首尾字节。这隔离了数据库值缓存未命中的校验开销，不代表机械硬盘/闪存的真实冷盘随机读，也不是 SQLite/Redis 对比。

## P99 的含义

上一轮 50 ms / 1 MiB、4 KiB / 8 线程整存的 P50 为 3.146 微秒，P99 为 2687.45 微秒，约 2.69 毫秒。P50 表示约一半采样调用在该时间内完成；P99 表示约 99% 在该时间以内，并非 99% 的调用都要花 2.69 毫秒。

2.69 毫秒是调用响应分位，既不是刷盘周期，也不是一次 fsync 的耗时。性能模式在内存发布后确认，但请求到达时可能排在前一批刷盘后面。现有单写线程兼做刷盘，合批可摊薄同步成本，同时会形成少数排队延迟。本轮按用户意见保留该机制。高吞吐和存在 I/O 等待本身不能证明设备已达到最大物理带宽；没有据此声称硬盘已跑满。

## 为什么无 bug 也会出现事务重试

普通事务先在调用线程捕获快照并读取、计算，再由写线程检查并提交。单一写线程串行发布结果，不会把此前在多个调用线程进行的读取和业务计算也自动串行化。

例子：A、B 两账户最初都是 100。两笔重叠事务都读到这个旧状态：

1. 第一笔从 A 转给 B 10，提交得到 A=90、B=110。
2. 第二笔原来计划转 20，若直接提交基于旧值算出的 A=80、B=120，就覆盖了第一笔转账的效果。
3. 第二笔返回 CONFLICT，重新读取 90、110，再计算并提交 A=70、B=130。

因此这里的“重试”是并发冲突后的业务重新计算，不是磁盘故障重写。旧基准的“73”是每 1000 笔完成事务约有 73 次额外尝试的比率，不是系统固定执行 73 次。驱动只在 FQDB_CONFLICT 时从头重读重算，不会把 I/O 错误计为这种重试。

本次正式回归包含：

- 两笔共享旧余额的事务：后一笔被拒绝，拒绝不修改当前余额，重读后得到正确的 70/130。
- 两笔读取、写入不同键的重叠事务：两笔都成功，即使数据库全局版本已经变化。
- 8 个线程各操作自己的键，每线程 100 笔：800 笔中零冲突、零丢失，Hybrid 和分段两种布局均验证。

另外用隔离诊断库在真实转账基准中给冲突检查分类，保留原检查条件和正常提交行为；诊断代码未进入主引擎。单次样本：

- 完成业务调用 86,912 笔，驱动记录冲突重试 5,191 次。
- 读取记录版本变化：5,191；代际/模式变化：0；范围变化：0。三类计数之和与驱动重试数完全相符。

该样本的拒绝全部来自事务读过的记录版本已变化，没有发现“仅因全局版本变了就拒绝独立键”的问题。当前采用记录级版本检查，同一记录的版本变化会保守地形成冲突。不能将一次诊断的绝对计数拿去覆盖以前不同负载的统计。

若业务要求热点更新也尽量零重试，可以另行提供“整笔读取→判断→修改进入写线程执行”的声明式多键原子接口，让后来的命令直接读到前一个结果。已有单键原子操作采用类似的最新视图路径。普通固定快照事务仍应保留冲突检查，不能删除检查后允许旧结果覆盖新结果。本轮未更改事务语义。
