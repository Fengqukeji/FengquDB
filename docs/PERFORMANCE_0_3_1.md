# 0.3.1 性能：缓存减法与回退修正

本轮针对 0.3.0 的性能回退修正短值片段组装、CRC 和重复映射查找，并实现事务私有缓存的直接裁剪/覆盖、不可变准备批次缓存的复制后局部编辑。实现与边界见 OPTIMIZATIONS_0_3_1.md。

## 条件与结论范围

Windows 11 build 26200、AMD Ryzen 9 9950X3D，同机同盘 Release x64；SQLite 官方 3.54.1。三个 Core 加载完全相同的原生基准 EXE，SQLite DLL 也完全相同。每个场景紧邻轮换版本顺序，3 轮取中位数，共 180 组实际调用；不在计时期间编译。最终完整对照把所有进程固定到亲和性 0x5555，即前一个 96 MiB L3 分组的 8 个物理核心各取一个线程，覆盖四线程读；设置在建库/预热之前完成。初始/最终有序键和所有值字节均校验，关闭重开再次校验。

原生基数 10 万键、值 256 字节；读取 200 万次，四线程各 50 万次，范围扫描 2 万次；可靠单写 1000 笔，可靠批量每笔 100 条、1000 笔；缓冲单写 5 万笔并计入最终 sync。SQLite 使用 WITHOUT ROWID、预编译语句、WAL FULL；缓冲场景 NORMAL 并计入最终 TRUNCATE 检查点，64 MiB 每连接缓存，mmap/自动检查点关闭。没有诊断接收器。

增加的进程 CPU 时间包含所有线程的用户态和内核态 CPU，不包含纯等待时间。Windows 该时钟有约 15.625ms 量化，短场景的小差异不能作精确 CPU 归因。墙钟吞吐也受调度、CPU 迁移、设备同步和后台负载影响。保留所有样本，没有剔除慢样本或以最佳值替代中位数。

## 阶段成本定位

诊断程序以相同编译选项分别包含各版本源文件，100 条/256 字节，1 万次，3 轮中位数；包括相关分配和析构。这是阶段成本探针，不是 DLL 整体调用时间，也不能把各阶段简单相加当作整体时间。探针的临时对象没有借用 Core 的空闲缓存，真实提交路径会借用。

| 阶段，微秒/100条 | 0.2.3 | 0.3.0 | 0.3.1 |
| --- | ---: | ---: | ---: |
| 写集暂存 | 22.262 | 23.680 | 22.007 |
| 编码与 CRC | 43.042 | 42.578 | 11.372 |
| 向连续输出拷贝 | 0.189 | 1.215 | 0.195 |
| 索引准备与销毁 | 48.384 | 48.794 | 48.381 |

0.3.0 小片段输出确实增加约 1 微秒/批，不能单独解释此前一次完整测量的 14% 退步。编码加 CRC 原先约 43 微秒，是更大的 CPU 成本。连续短批次与 slicing-by-8 一起将其降到约 11.4 微秒；预计算 CRC 组合变换也减少大值反复提交的校验成本。索引探针没有发现同量级的退化。不能把此前全部墙钟差异归咎于一种数据结构。

单位为调用/秒；batch100_sync 为 100 条事务/秒，scan100 为 100 行扫描/秒。各列分别取中位数，比例是中位数之比，不是统计显著性结论。

可靠批量在本组提升约 12.4%，为同场 SQLite 的 1.235 倍；不能概括为所有调用都加速。read_into 低约 1.5%、scan100 低约 2.0%、缓冲单写低约 2.7%，单条可靠新增基本持平。这些小差异没有隐藏，也没有证明统计显著性。

在缓存回收生命周期修正前，未绑定亲和性的候选完整对照曾出现 read_into 和缓冲单写低约 6% 的读数；对同一候选固定 0x5555、每项 5 轮的定向复测则分别高约 1.3% 和 6.9%。因此尚未证明它们有稳定的同等幅度代码回退。最终表使用最后修正后的实际交付 DLL、相同固定亲和性，仍保留上述小幅低值。该 CPU 的两个 L3 分组容量不同，本次读吞吐高于历史未绑定结果，不能将跨表数值变化全部当成代码收益。

## 复用缓存的实际调用

基数 1 万键。批次是同一组 100 键/256 字节；prepared_with 每笔由原准备批次派生一份，改变一个值，包含派生对象构造、事务提交及析构。prepared_rebuild 使用相同输入重新准备整个批次。private_full/private_patch 都在每笔事务中编辑同一个 100 KiB 值 100 次，共 500 笔，包含首次隔离、最终完整记录提交、最后 sync 和历史维护。所有最终值重开后逐字节验证。两版本使用相同基准 EXE。

| 场景，事务/秒 | 0.3.0 | 0.3.1 | 新/旧 |
| --- | ---: | ---: | ---: |
| batch | 7,150 | 9,737 | 1.362× |
| prepared_batch | 15,517 | 15,520 | 1.000× |
| prepared_with | 8,444 | 12,481 | 1.478× |
| prepared_rebuild | 7,258 | 9,734 | 1.341× |
| private_full | 3,140 | 5,321 | 1.695× |
| private_patch | 3,160 | 12,038 | 3.810× |

连续私有 patch 提高约 3.81 倍；0.3.1 同场 private_patch 对 private_full 约 2.26 倍。两者都写最终完整值，日志同为 51,236,500 字节，所以这项优势不依靠减少持久化保证或减少最终记录。普通整值写也因校验优化受益，不能把全部跨版本收益只算成直接裁剪收益。

准备批次改单值提高约 47.8%；原批次重复提交基本持平，说明局部编辑不能加速本来已经准备完成且完全不变的输入。首次准备 100 条数据的成本仍单独记录在原始样本中，不假装所有输入都可以免费准备。

## 包体与内存代价

Windows 核心 DLL 为 280,064 字节，0.3.0 为 265,216 字节，增加 14,848 字节；Linux stripped SO 为 183,272 字节，原为 162,760 字节。CRC 两组表共约 16 KiB，不能声称这一轮包体缩小。

每个数据库实例最多保留 64 KiB 空闲编码缓存；每个活动准备批次另可持有不超过 64 KiB 的编码副本，在途请求也有自己的载荷。私有大值缩小超过四倍时重新压紧分配。历史、快照和派生对象的持有成本仍存在，未实现全库内存限额、超内存分页或 RCU。

## 原始证据

- artifacts/write-profile-final-0.3.1.json：最终源文件阶段原始测量及探针 EXE 哈希。
- artifacts/regression-0.3.1-final/comparison.json、samples.jsonl：最终交付 DLL 的 180 组完整调用，包含 EXE/DLL 哈希、CPU 时间、吞吐、准备时间、日志量和完整验证标记。
- artifacts/regression-0.3.1 和 regression-affinity-0.3.1：回收生命周期修正前的候选探索，保留原哈希和退步读数，不混入最终表。
- tools/run_regression_comparison.py、tools/write_profile：复现入口；最终完整对照参数 --affinity 0x5555 --read-count 2000000，默认 3 轮。
- artifacts/validation-0.3.1.md：本轮数据一致性、内存/竞态、ABI、跨平台与语言验证。

没有 Redis 同条件对照，没有理论极限、所有场景超越现有数据库、真实断电或长时间压力的证明。结果只覆盖所列工作负载与本机短时间样本。
