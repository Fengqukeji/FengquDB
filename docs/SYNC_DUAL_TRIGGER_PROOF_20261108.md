# SYNC 时间与字节双触发：最小验证

> 后续单线程验证：用户要求按单线程集中处理路线继续，采用1 MiB累计、每笔独立事务、共享可靠刷盘的原型，三轮中位数达到约5.30万条/秒。见[单线程验证](SINGLE_WRITER_PROOF_20261108.md)。下文保留原多调用线程实验口径。

## 结论与计算口径

“8 ÷ 0.1 = 80 次/秒”仅描述这样的封闭调用方式：8 个线程各自只有一笔在途请求，必须等待刷盘才发下一笔，每组都凑不到字节阈值，因而必须等满 100 ms。这还是忽略处理和刷盘耗时的条件上界，**不是双触发策略的通用吞吐上限**，也不能把低业务到达率当成数据库容量。

字节阈值先到就提前处理；增加独立在途请求也能改变合批条件。总体应分别看业务到达率、在途请求数与端到端延迟，以及数据库和磁盘的服务能力。稳定负载下在途数约等于吞吐乘平均延迟；这不意味着任何合批实现都固定受 80 次/秒限制。

本轮实测支持用户提出的双触发思路：4 KiB 简介完整保存、8 线程、32 KiB / 50 微秒，三轮中位数从 **5,243.56 提高到 5,822.97 次/秒，约 +11.05%**。尚不能称为最佳阈值或理论极限。本次 SYNC 仅在隔离原型中研究，没有合入主引擎。

## 隔离原型与可靠性语义

原型基于已合入 BUFFERED 定向代办的 0.3.2 主库，只复制到 `build/sync-submit-research-20261108/candidate/` 修改。普通事务入队前统计暂存 put 或 patch insert 的业务字节，队列互斥保护待处理字节总量；组长等待“累计字节达到阈值”或“从本组开始等待至截止时间”，任一满足即开始处理。原有组最大笔数、索引空间边界等处理限制保留。

这里统计业务载荷，不包括 key、WAL 封装、索引扩展、填充或写放大。基准的一条 Protobuf 档案约 4,173 B，8 条可达到 32 KiB，无法达到 64 KiB。没有把 32 条批量写当成固定业务规格。

复用原 WAL → 同步刷盘 → 发布 → 返回成功的顺序，没有用提前返回成功改变 SYNC 可靠性语义。各事务仍独立记录和校验。100 ms 是该实验的最长凑批等待，尚加上处理、I/O 和调度时间；它不是后台按墙钟持续触发的独立周期任务。

100 ms 通过私有实验开关设置，没有扩大公共 API 现有的 10 ms 上限。原型配置在调用线程启动前固定，不支持在活跃提交期间切换字节策略。尚未完成本轮 SYNC 修改的故障注入、TSan、跨平台和混合大小验证，不能据模型重开校验宣称生产验证完成。未引入流水线、分片或固定写线程。

## 一轮机制筛选

相同 4096 条业务档案，Linux Docker，CPU 0、2 两个指定 vCPU，4 GiB、无额外 swap，同一构建镜像。装载和预热在计时外；完整保存包含业务编码。可靠提交在计时内，记录真实耗时。除凑不满阈值的负例计划 1 秒外，每项计划 2 秒。

| 配置 | 在途调用上限 | 实测次数/秒 | 平均每次刷盘笔数 |
| --- | ---: | ---: | ---: |
| 当前主库，自然合组 | 8 | 5,004.83 | 4.69 |
| 原型策略关闭 | 8 | 4,919.70 | 4.66 |
| 32 KiB / 100 ms | 8 | 5,676.87 | 8.00 |
| 64 KiB / 100 ms，阈值凑不满 | 8 | 78.42 | 8.00 |
| 当前主库，自然合组 | 64 | 27,216.60 | 41.84 |
| 64 KiB / 100 ms | 64 | 19,851.10 | 56.96 |
| 32 KiB / 50 微秒 | 8 | 5,633.49 | 7.95 |

这直接证明相同的 100 ms 配置既可能只有约 78 次/秒，也可能达到数千或近两万次/秒，取决于阈值和在途压力。它没有证明越长周期或越大合批就越快。64 线程原型样本含一次自动整理，实际耗时 2.112 秒，末尾也可能等不满的一组；这一轮没有隔离这些因素，不能把其回退全部归因于单一机制。

策略关闭的一轮比主库低约 1.7%，保留该负结果；单轮不足以隔离框架固定成本。没有据此宣称零开销。

## 三轮复测与同期 MySQL

仅复测同一个 8 线程业务案例，调整正反顺序。另用当前主库公开参数 `group_max=8, group_delay_us=50` 作按笔数合批的控制，判断收益是否确实来自凑齐请求。

| 配置 | 吞吐中位数，次/秒 | 三轮区间 | 抽样 P99 中位数，微秒 |
| --- | ---: | ---: | ---: |
| 当前主库，自然合组 | 5,243.56 | 5,226.37～5,348.23 | 3,340.74 |
| 当前主库，8 笔 / 50 微秒 | 5,751.23 | 5,692.08～5,872.25 | 2,165.20 |
| 原型，32 KiB / 50 微秒 | 5,822.97 | 5,795.80～5,823.49 | 2,322.70 |
| 同期 MySQL 普通表 | 3,243.41 | 3,178.92～3,309.95 | 5,528.80 |

自然合组每次刷盘约 5.19 笔，双触发约 7.94 笔。按笔数控制也提高约 9.68%，因此本例主要支持“提高合批完整度有效”，不证明按字节必然胜过按笔数。字节控制用于适应业务载荷大小变化，其混合大小价值本轮未测。抽样分位数是各轮分位数的中位数，不是全量合并分位数或生产 SLA。

MySQL 使用同业务普通 InnoDB 表及预编译 SQL，本机 TCP，`innodb_flush_log_at_trx_commit=1`、binlog 关闭、doublewrite 开启、O_DIRECT，客户端与服务端共享相同 CPU/内存额度。测量后重启 MySQL，再由独立进程核验业务模型。切换至 FengquDB 时停止 MySQL，避免后台占用。

同期 MySQL 明显低于之前报告的 6,890 次/秒；当前主库在本轮也已经高于同期 MySQL。因此不能将此描述成“新策略首次打败旧报告的 MySQL”，或把约 11% 收益扩成所有磁盘和环境的保证。旧数据与本轮数据分开保留。

## 诊断依据与证据

此前带系统调用探针的一轮中，5,376 笔提交对应 1,172 次刷盘，每次约 4.59 笔。同步调用累计约占阶段 88%，pwrite 约占 4%；没有自动整理。这为提高实际合批数量提供依据。探针未用于本轮正式复测，避免将计数开销混入成绩。

7 个机制筛选样本及 12 个复测样本均完成全字段模型核验和独立重开，重试计数为零。private 驱动对 SYNC 每笔检查停止时间，防止 100 ms 周期强制多执行 64 轮；两侧使用同一驱动，真实耗时保留。主库 82 个受保护构建输入在研究后哈希全部保持不变。
