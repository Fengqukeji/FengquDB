# 0.3.0性能：减少重复工作后的收益与代价

本报告使用最终交付Core的二进制。实现及契约见 OPTIMIZATIONS_0_3.md，稳定性结果见 artifacts/validation-0.3.0.md。以下均为Windows本机短样本，不是理论极限或持续峰值。

## 条件与计时

Windows 11 build26200，AMD Ryzen 9 9950X3D，Release x64，同机同盘，无诊断接收器。SQLite原生对照为官方3.54.1，WAL FULL可靠提交、预编译语句、WITHOUT ROWID、每连接64 MiB缓存，mmap/自动检查点关闭；缓冲场景NORMAL并计入最终TRUNCATE检查点。Python3.12.10标准库SQLite3.49.1。

每组3轮取中位数。并发对照在各场景中交替旧版/新版/SQLite；12种原生及3种Python调用方式分别在每个套件内交替FengquDB/SQLite，旧/新版套件顺序执行，因此跨版本差异可能包含设备与后台负载变化。没有对这些变化做统计显著性或固定成因判断。

全部构建/消毒器执行结束后开始采样。输入预先生成，准备对象构造不计入重复调用计时，准备成本单独列出；运行前预热，运行后关闭重开并完整验证键和值。缓冲写吞吐包含最终可靠同步。所有正式结果、探索结果和退步均保留。

## 同一0.3.0内核：普通接口与专用接口

基数1万键；热点读重复同一键、值256字节，不等于随机全库读。批量用相同100键/256字节输入重复500笔事务，每笔仍保留独立版本和变更事件。大值为100 KiB，每笔更改1字节，共500笔。

| 对照 | 普通方式/秒 | 新方式/秒 | 新/普通 | 日志字节，普通→新 |
| --- | ---: | ---: | ---: | ---: |
| 热点复用读取→准备键 | 20,494,869 | 24,756,642 | 1.21× | 0 → 0 |
| 100条普通事务→准备批次 | 6,447 | 13,000 | 2.02× | 14,128,000 → 14,128,000 |
| 大值整值替换→splice增量 | 4,277 | 23,320 | 5.45× | 51,236,500 → 5,670,984 |
| 读改写计数→原生计数，短样本 | 238,908 | 69,958 | 0.29× | 395,000 → 395,000 |

准备100条输入的一次性构造约81.4微秒。准备批次的优势需要重复使用来摊薄，不能把首次构造和只使用一次的数据输入成本隐藏掉。增量日志少写约88.9%，仍需在内存中物化完整新值；第9次整值回退已计入。

原生计数的5000次短样本出现明显慢值，不能据此宣称计数原语有稳定加速。对同一交付Core和同一可执行文件，改为每轮50000次、普通/原生相邻交替的3轮定向复测，结果如下：

| 计数定向配对 | 读改写/秒 | 原生加数/秒 | 新/普通 |
| --- | ---: | ---: | ---: |
| 50000次/轮 | 355,087 | 363,815 | 1.025× |

因此当前原生计数的单线程收益很小；它提供的主要能力是写者按最新状态直接执行，以及并发同键加数不需要客户端冲突重试。本轮验证了并发正确性，未测与并发读改写重试的吞吐对照。短样本异常原值没有删除，也不自动归因为某个设备原因。

## 内存、包体与稳定性代价

10万键普通单读的PrivateUsage增量：旧版54.34 MiB，新版54.34 MiB，SQLite35.83 MiB。小事务少分配不代表整个数据库驻留内存大幅下降；本轮没有实现更低的全库内存上限。

格式3历史同时按编码及完整物化载荷预算裁剪，避免小增量日志保留大量完整旧值；活动快照、游标、准备批次和派生缓存仍有各自持有成本。原生计数和条件写是显式接口，普通put保留原有事件语义。

Windows核心DLL：216576 → 265216字节，增加48640字节（22.5%）；Linux stripped核心SO为162760字节。新接口与路径增加了包体，不能宣称包体也变小。诊断/JNI保持独立组件。

没有修改已有格式1/2文件。增量日志需显式创建格式3文件，旧库拒绝该格式，可用格式2物化检查点回到旧版可读数据。版本极值、proto3省略零字段、增量历史物化预算、暂存失败后重试和I/O不确定结果均经过直接验证。真实断电、长时间压力、超内存数据和Redis同条件对照仍未执行。
