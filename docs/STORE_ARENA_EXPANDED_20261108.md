# 单次刷盘原型：扩大负载、动态预留与容量保留

后续大批量写、页头分离与连续页描述实验见 [大批量研究记录](STORE_ARENA_BULK_20261108.md)。该实验有收益也有回退，未替换本文 retained2 候选或主引擎。

本轮是隔离研究，主引擎仍对应 `build/store-only-20261108/store-only-source-v6.json`。最终研究源码为 `build/arena-expanded-20261108/retained2-source/`，没有替换主库或 SDK。完整二进制缓存、减法裁剪及上层事务逻辑沿用原实现。本轮不涉及向量、全文、RAG 或跨进程协作。

## 预留的单位和最终策略

预留属于一个 generation 数据文件，由这个文件中的记录、普通写入和事务共同使用。不是每条记录或每次事务各占一块 1 MiB。普通 put、delete、patch 和原子批量写入共用底层追加、准备空间与同步路径，不要求业务显式创建事务。

最终策略根据用户后续指示调整为：

- 小库从必需的四个逻辑页起步，四副本实体页加文件头共 **68 KiB**，不统一预分配 1 MiB 或 64 MiB。
- 追加开始前计算**当前整笔 WAL 的最终位置**，包含键、值、事务头和校验；空间不足时一次准备当前完整请求所需容量。
- 在当前必需容量之外，按本次请求、近期追加量、约 100 ms 写入速率预测和已有容量比例安排额外空间。历史预测不是当前请求的硬上限。
- **正常关闭默认保留已扩容的历史高水位**。缩小业务值也不自动缩小实体文件。可选关闭回收独立控制；逻辑尾部恢复、整理和删除废弃 generation 仍属于数据一致性与维护职责。
- 预测空间有每文件上限和本库实例的进程内分配额度。额度耗尽仍允许写入当前事务必需的数据空间。
- 重开后复用尾部空白页时，逐字节确认四份图像都与当前身份的完整空页一致，才跳过重新初始化；有废弃版本、损坏或未完成初始化仍重新清空，避免旧日志复活。

原型参数如下，均是研究用环境变量，尚未加入正式 SDK 配置：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `FQDB_RESEARCH_RESERVE=smart` | 显式启用 | 动态策略 |
| `FQDB_RESEARCH_SPARE_BUDGET` | 4 MiB | 同一库实例进程内新分配预测空间的共享额度 |
| `FQDB_RESEARCH_FILE_SPARE_LIMIT` | 64 MiB | 单文件每次新增预测余量的上限，支持设置更小值或零 |
| `FQDB_RESEARCH_TRIM_ON_CLOSE` | 0 | 设为 1 才在健康关闭时回收多余物理尾部 |

64 MiB 只是可配置的研究上限，并不代表启动时分配这么多。当前预测器单次额外预测最多 128 个逻辑页，约 2 MiB 实体空间；默认共享额度又限制为 4 MiB。当前事务的实际数据容量、单笔事务大小限制、整个数据库大小限制应分别配置，不能把“预留上限”当成“数据文件最大长度”。

共享额度限定当前进程新批准的预测分配，**不是跨数据库目录、关闭文件和进程重启后的持久化磁盘总配额**。保留容量后，关闭会释放进程内额度，已经存在的实体容量仍保留。调低上限也不强制缩小已有文件。要控制所有历史热库的磁盘总占用，需要显式空间维护或独立的持久化配额设计；本轮没有声称实现这种全局硬配额。

## 实际空间测量

`space-final-report.json` 使用最终 retained2 二进制，三个场景均实际运行，并在关闭后逐库重开、逐字节校验全部值。每条业务值为 256 B。

| 场景 | 首次写完关闭时的数据文件 | 首次阶段普通文件实际分配 | 重开校验后全部普通文件长度 |
| --- | ---: | ---: | ---: |
| 1 库，1000 次单条写入 | 1,691,648 B，约 1.61 MiB | 1,695,744 B | 2,822,219 B，约 2.69 MiB |
| 1 库，1000 条一次原子批量写入 | 1,314,816 B，约 1.25 MiB | 1,318,912 B | 1,626,187 B，约 1.55 MiB |
| 1000 个独立小库，每库 1 条，同时打开 | 69,632,000 B，约 66.4 MiB | 73,728,000 B，约 70.3 MiB | 69,707,000 B |

这里的文件包含日志、索引、四副本和预留，不等于 256 B 业务值的净体积。实际分配按 Linux 普通文件 `st_blocks` 汇总，不含目录/inode 等文件系统元数据。重开可能进行 WAL 恢复后的索引 checkpoint，并增加按需预测空间，因此不能把初次关闭长度当成重开后永远不变的占用。测试明确保留了各阶段数值。

初版 balanced 实测 16 个独立小库的数据文件合计 16,842,752 B，即每库 1028 KiB；按该固定起步大小推算 1000 库约 1003.9 MiB。这是由 16 库结果推算，未实际创建其 1000 库。最终方案已实际验证 1000 库；冷库初始化放大约降低 93.4%。

1000 库全开时进程 RSS 约 30.75 MiB，起始约 3.5 MiB。关闭后分配器仍可能保留内存，所以不把 RSS 未立即下降当成泄漏，也不把虚拟预留等同于常驻内存。

## 各能力的扩大测试

首轮共 21 种负载，分别运行当前主引擎和小起步动态页原型，另外有两个冒烟样本；每个样本都由独立进程重开、逐字节核对并调用 Store verify。场景包括 256 B、4 KiB 的增删改、8 B patch、32 条原子批量写、BUFFERED、8 线程更新与热 get，以及 64 KiB 更新、patch 和批量写。下表为首轮数据，不混为最终 retained2 的全矩阵结果。

| 负载 | 256 B 原型/主引擎 | 4 KiB 原型/主引擎 |
| --- | ---: | ---: |
| 单条新增，SYNC | 2.41× | 2.26× |
| 单条完整修改，SYNC | 2.34× | 2.36× |
| 修改 8 B，SYNC | 2.39× | 2.37× |
| 单条删除，SYNC | 2.41× | 2.36× |
| 32 条原子批量写，SYNC | 1.17× | 0.67× |
| 单条修改，BUFFERED，含最后 sync | 0.96× | 0.52× |
| 32 条批量，BUFFERED，含最后 sync | 0.82× | 0.28× |
| 8 线程修改，SYNC | 1.32× | 1.37× |
| 热 get | 0.99× | 1.04× |

点操作各 128 次，批量各 16 次，每次 32 条；8 线程各 32 次；热读 20,000 次、256 个预热键。64 KiB 点操作各 32 次，批量 4 次。批量吞吐以记录/秒表示，不等同于事务/秒。短测中的小差别不是稳定收益证明，尤其只有几毫秒的 BUFFERED 与热读。

六个弱项只定向再跑两轮，没有重跑整个矩阵。含最终 sync 的三个样本中位数分别比较：256 B BUFFERED 批量约 0.99×，4 KiB SYNC 批量约 0.85×，4 KiB BUFFERED 单条约 0.49×、批量约 0.22×，64 KiB SYNC 单条约 1.12×、批量约 0.24×。64 KiB 单条初轮的 0.93×未表现为稳定回退；大批量的明显回退仍然存在。

最终 retained2 的定向对照：256 B 完整修改约 2133 对 883 次/秒，**2.42×**；4 KiB 的 32 条批量约 21,201 对 24,442 条/秒，**0.87×**；64 KiB 的 32 条批量约 1934 对 8089 条/秒，**0.24×**。最后一项仅四笔事务，不能将其当作稳定峰值，但与之前多轮的大批量回退方向一致。

预留直接减少扩容相关写入及同步开销，收益偏向小 WAL、高频 SYNC。批量本来已经摊薄同步次数；大块数据的初始化、页 CRC、复制和写放大占比上升。最终 64 KiB 批量四次提交的系统写入请求约 51.22 MB，主引擎约 8.40 MB。请求字节数不是设备实测物理写入量。

查询不执行追加或刷盘，因此此项优化没有直接的读取收益。不能由“小单条 SYNC 快”推导所有能力、所有值大小、BUFFERED 或所有批量都更快。

## 数据大小突然变化和扩容保留

连续值大小序列为 256 B → 4 KiB → 256 KiB → 256 B → 1 MiB → 4 KiB → 2 MiB → 256 B → 64 KiB → 1 MiB → 256 B。每一步在一笔事务里写当前值和该步的历史键，因此最大一步实际 WAL 超过 4 MiB。对默认额度、共享预测额度为零、每文件额外预测上限为 64 KiB 均完成 11 步，并独立重开核对所有历史值和最终值。

Linux 系统调用计数验证，每一步恰好一次 fdatasync，最多一个新空白初始化批次。零预测额度仍完成全部请求；64 KiB 文件预测上限也未阻止超过 4 MiB WAL 的当前事务。大于现有余量的突发写入仍需要初始化与 I/O，**动态策略不能保证未知的大突发没有额外延迟**。

最终“打开、写一条、关闭”连续 16 次的 ABBA 小对照：

| 关闭策略 | 两轮总耗时 | 每轮计时段空页初始化 | 关闭缩容次数，含准备阶段首次关闭 |
| --- | --- | ---: | ---: |
| 可选关闭回收 | 29.72 / 28.98 ms | 24 个单元 | 3 |
| 默认保留容量、校验空页后复用 | 24.88 / 24.84 ms | 0 | 0 |

约减少 15.3% 的本例耗时。两者各有 48 次 fdatasync，包含打开时恢复 checkpoint 和每笔提交；没有少做持久化同步来获得收益。此例保留约 96 KiB 额外实体空间，不能据此保证所有负载同等改善。

保留容量之前的版本在重开后仍重新清空本来已经初始化的尾页。修正后只跳过四份完整空页的冗余写入；不是无校验地信任预留区域。

## 可靠性和平台验证

- 首轮有 7 项恢复检查：跨页部分提交、单份完整新页、完整提交以及双份损坏拒绝；失败打开的文件哈希保持不变。
- 最终空页复用变化定向复验 6 个跨页镜像，覆盖首页、尾页、中间缺页、单份新副本、完整提交及旧状态；每项均恢复、继续写入、再次重开，未复活废弃尾部。
- snapshot 固定旧视图、主句柄关闭后仍读取旧值、最后引用释放额度、BUFFERED 未刷盘值丢失但不出现撕裂、已刷盘大值保留、重开再增长均通过。
- 64 个库由 8 个线程创建和写入，预测共享额度限 256 KiB，峰值恰为 256 KiB；当前必需写入均成功，关闭释放进程额度。
- Windows x64 最终源码编译通过，实际加载路径和二进制哈希有记录；验证大小跳变、64 KiB 文件预测上限、关闭保留/可选回收和重开完整值。Windows 未做系统调用刷盘计数，也未声称完成全性能矩阵。

全部性能阶段与编译分开执行。Linux 在 Docker 命名卷中运行，限制 2 CPU、固定 CPU 0/2、内存 2 GiB、不使用网络；没有 OOM。镜像检查不是硬件真实断电，仍不能由它替代设备级断电验证。

## 采用边界和证据

当前选择保留 retained2 作为继续研究的候选。小写 SYNC 收益成立；读路径基本持平；大块批量和 BUFFERED 有明显弱项，不能整体替换主引擎。原型仍将逻辑文件限制在约 32 MiB，并持有研究用页内容，尚未接回生产受控缓存、分段和完整维护 I/O 预算。四副本空间冗余不是可回收的空闲预留，满载仍约四倍；提高预留上限不能解决这个固有放大。

证据位于 `build/arena-expanded-20261108/`：

- `report.json`：首轮 21 对负载、7 项空间场景、生命周期与恢复。
- `repeat-report.json`：六个弱项定向重复、balanced 与小起步短对照、首次大小跳变。
- `retained-report.json`：默认保留容量及整笔需求外额外预测。
- `retained2-report.json`：跳过已确认完整空页的冗余初始化，最终定向性能与跨页恢复。
- `space-final-report.json`：最终策略实际 1000 条、1000 个独立库空间测量。
- `windows2-report.json`、`windows-retained-report.json`：初轮和最终 Windows 验证；第一次 Windows 日志写入的编码错误保存在 `windows-report.json`，没有覆盖为成功。
- `source-manifest.json`、`retained-manifest.json`、`retained2-manifest.json`：各阶段独立源码；相关二进制长度和 SHA-256 在报告中。

最终 Linux 库 720,304 B，SHA-256 `095ea84b7746365885224356c3434c4e70aab3fc4d67a96dd8e4135b25dd58e7`；最终 Windows 库 771,584 B，SHA-256 `ca71b41d49981eafd0ae7d0216d771d179591a8e1148f9bf82b2f2e29fd8c235`。原型含额外空间诊断导出，不是正式发行包。

所有本轮成功 Docker 容器与卷均核对随机所有权标签后清理；原始报告、日志和失败记录保留。
