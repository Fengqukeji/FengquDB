# 共享读取与外部接口优化（2026-11-08）

本轮直接修改唯一 Store 主实现，没有修改文件格式、事务、SYNC 屏障或完整二进制缓存与减法裁剪。接口用法与生命周期见 [共享读取](STORE_SHARED_READ.md)。

## 实现

- 新增原生准备共享读取器，键只复制一次；当前发布视图与 TTL 未变时复用载荷和行描述。时间回退强制刷新，不保留旧 View/Generation，仅显式固定完整值。
- C# 同步只读 Span 回调封装租约，处理异常、同读取器重入及并发关闭；未变热读无托管分配。普通 Get 直接从不可变值复制一次，pin 不足时回退原复制接口。
- C# 批量复制读取直接取原生行描述；C#/Python 的值与元数据合并读取，减少接口往返。
- Python 的 readonly memoryview 导出器保留独立原生所有者，派生切片不受外层关闭或下一次读取影响；包装分配失败也归还原生租约。
- Java 对 direct 缓冲附件关系做能力检查，支持时用 GC 引用队列保持所有别名生命周期，否则复制到 JVM 自有 direct 内存。两条分支均验证。
- C# 业务 PlayerSaves.Load 直接解析共享 Span，DTO 本身仍按 Protobuf 解析规则分配。

## 测量条件

Windows x64、.NET 10、4176 字节业务 Protobuf（其中 avatar 字段为 4096 字节）、固定 32 个键、热数据，无并发写入。每样本单条 300000 次，批量 18750 次 × 32；三轮交错旧/新 C#，取吞吐中位数。两版均设 DOTNET_TieredCompilation=0，使用完成优化的 JIT；初始默认分层 JIT 的 pilot 也全部保留，不能用它与优化 JIT 混算。原生参照取同一原生核心/驱动的 stage1 三轮，最终 SDK 补改未改变它们，避免重复无关原生测试。

这里的共享读取每次仍检查当前发布视图和 TTL；它不复制载荷，不创建独立返回数组。故与旧数组接口的倍数是**调用方式改变后的业务选择对比**，不能当作相同所有权接口的纯 FFI 提升。单次检查首尾字节，DTO 解析另列。数字按行计，批量不是每秒原子事务数。

| --- | ---: | ---: | ---: |
| 独立数组读取 | 2.968 | 3.058 | 8.704 |
| 准备键 + 复用目标 | 9.936 | 9.985 | 10.965 |

| 共享读取 + DTO 解析 | — | 1.220 | — |

新共享单条约为旧数组读取 5.74 倍、复用目标读取 1.71 倍；相同共享 API 下 C# 单条为原生约 80.2%，批量为约 75.0%。共享读取加 DTO 解析为旧读取加解析的约 1.51 倍。

普通 Get 的分配仍存在，提升很小；复制批量也没有共享批量的收益。没有声称 Python/Java 同样获得这些倍数，也没有冷盘、变更频繁或整体数据库胜过 Redis/SQLite 的推论。

## 验证

- Linux 新建 Release 构建，21/21 CTest；共享读取所在 paged_bulk_path 通过 ASan/UBSan（含泄漏检查）。
- Windows 新建相关目标，paged_store_sdk、paged_bulk_path、paged_hybrid 均通过。
- C# 验证空视图、批量一致性、旧值不变、回调异常/重入、跨线程关闭、父库关闭、固定预算回退及热点零托管分配。
- Python/Java 验证未命中/空值、派生视图跨关闭/下一次读取/整理、只读性、固定预算失败及释放；Java 同时验证能力检测和强制复制分支，使用 -Xcheck:jni。
- 最终复制接口通过三语言 smoke 和顺序跨语言 Protobuf 互操作；最后的 Python 包装分配失败守卫又分别在 Windows/Linux 执行共享用例。

过程中 Python 测试最初因未创建父目录失败，Java 能力探针最初过度要求直接指向根对象、误拒绝合法的附件链；均修正并通过相关复测。首次性能程序完成全部采样后，摘要打印变量遮蔽 Python round 导致退出 1，原始数据未丢失；已修正驱动。失败日志和 stage1 原始样本均保留。
