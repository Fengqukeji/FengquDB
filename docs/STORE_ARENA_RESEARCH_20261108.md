# 预初始化空间、单次刷盘和动态预留研究

后续扩大测试、针对多小库的小起步策略、动态整笔需求、默认保留扩容容量及读写负载取舍，见 [扩大测试记录](STORE_ARENA_EXPANDED_20261108.md)。本文保留此前单例阶段的结果和阶段限制；此前建议的较大起步预留已由后续小库策略细化。

当前阶段为隔离原型研究，主工作区核心保持 `store-only-source-v6.json` 对应源码。原型位于 `build/arena-sync-study-20261108/`，没有覆盖主库或 SDK。用户接受适度磁盘、内存开销换取性能和恢复可靠性；本轮仅以一个单线程、256 B 完整修改例子筛选方向。

## 单次刷盘方案

初版采用“日志同步、两个尾标记再同步”，需要两道屏障。同轮原生 C ABI 对照的中位数为：原 Store 886 次/秒、双屏障原型 1068 次/秒、单屏障页原型 2116 次/秒。后者约为原 Store 的 2.39 倍。这些是两轮各 256 次的短测，不是生产峰值或其他负载的保证。

新方向把版本、有效长度和 CRC 放在页内部，使用写时复制和冗余页：

1. 每个逻辑页有四个分离的 4 KiB 单元，每个单元保存 4032 B 内容、页号、版本、有效长度和校验。
2. 更新写入两个较旧的单元，上一版已确认的两个单元保持不动。同组对同一私有页的修改共用缓冲。
3. 页内容及其边界字段一起执行一次 `fdatasync`，成功后发布进程内视图、返回成功。
4. 启动时选取 CRC 完整的最高版本副本，按有效长度重建逻辑文件，再保留原有 WAL 整笔事务校验。完整新页可能来自尚未得到返回的提交，恢复完整事务是允许的；不会发布半笔跨页事务。

系统调用计数直接验证：256 次提交，原 Store 为 256 次 fsync，双屏障原型为 512 次 fdatasync，新页原型为 256 次 fdatasync。没有通过少刷盘或推迟成功返回提速。

单个损坏副本可用同版本完整副本恢复。若同一可达页有两个无效副本，可能是两份新页都撕裂，也可能是已确认新页后来损坏；当前原型返回 CORRUPT、保留文件，不静默回退。不能把“CRC 不对”一律当作未提交内容删除。

## 预留大小对比

固定页大小与预留大小分开：扩大预留不扩大每次修改的逻辑页。下表的预留粒度是初始化的实体空间，另有 4 KiB 文件头；每项两轮，每轮 256 次单线程更新，数据和验证相同。

| 预留策略 | 吞吐中位数，次/秒 | 计时期间扩容次数/轮 | 两轮最长调用 | 最终文件长度 |
| --- | ---: | ---: | ---: | ---: |
| 固定 64 KiB 粒度 | 2077 | 5 / 5 | 1.47 ms | 452 KiB |
| 固定 256 KiB 粒度 | 2226 | 1 / 1 | 1.51 ms | 516 KiB |
| 固定 1 MiB 粒度 | 2271 | 0 / 0 | 0.64 ms | 1028 KiB |
| 固定 4 MiB 粒度 | 2283 | 0 / 0 | 0.67 ms | 4100 KiB |
| 较小起步、动态扩展 | 2219 | 0 / 0 | 0.66 ms | 452 KiB |

本例中较大的预留主要减少扩容停顿。1 MiB 到 4 MiB 的吞吐差异约 0.5%，两轮范围重叠，没有证据表明继续放大会稳定提速。4 MiB 的初始化耗时也更高，本轮打开耗时约 9 ms，1 MiB 约 7 ms；短测只用于选型，不将此视为通用启动指标。

动态预留的零扩容只指计时期间：它在准备/预热时已扩展。报告同时保留打开耗时、准备耗时、每次最大延迟和初始化请求量，不把工作移到准备阶段后当作零成本。

## 按整笔操作与近期写入量预留

进一步原型在追加开始前取得整笔 WAL 的总长度，含键、值和日志元数据。即使 WAL 分为多个输出块，也先以总长度计算需求，避免写到一半反复准备空间。

扩容选择兼顾：当前整笔所需容量、近期追加量的预测、已有容量的比例增长、预留下限和上限。研究参数用近期写入量预测后续约 256 次追加，按页对齐；该常数不是生产默认值承诺。

新增 `balanced` 原型以约 1 MiB 实体空间起步，再按事务总量和近期增长动态扩展。与固定 1 MiB 的同例复验都为 256 次提交、256 次同步、计时期间零扩容。两轮短测差别不能归因于算法更快，重点是其容量规划行为。

另对一笔 256 KiB 值的原子事务检查：固定粒度、节省空间动态策略、balanced 都在一次准备过程中完成本笔所需空间，只有一次数据同步，关闭重开后逐字节验证通过。最终文件分别约 2 MiB、1.13 MiB 和 4 MiB。balanced 选择保留更多后续写入余量，节省空间策略更贴近本笔需求。

当前建议是较充足的预留下限配合动态扩展，而不是无限预留。空白页在内存中共用内容缓冲，只有修改过的私有页分配内容；预留磁盘大小不等于等量常驻内存。记录的进程峰值 RSS 受启动器高水位影响，不据此宣称准确的内存增量。

## 可靠性证据和范围

基础页原型的 13 个镜像检查包含：未写新页、前缀写入、一个完整新副本、另一个副本撕裂、一个已确认副本损坏、双副本损坏拒绝、预留扩展中断及保留原 WAL 校验。前缀写入若已覆盖所有变化字节，实际就是完整页，不能只按写入字节数断定其损坏。

动态预留构建另完成 6 个跨页原子事务镜像，覆盖新页只落首部/尾部、缺中间页、各页仅一个完整新副本及完整提交；恢复后继续写入、再次重开，未复活放弃的旧尾部。64 KiB 值及最终 256 KiB 值的大记录也完成原生写入与独立重开验证。

镜像检查是构造持久化状态的验证，不是真实硬件掉电。最终容量规划调整未重复与之无关的全部页校验测试，阶段身份和原始结果分开保存。第一次探针编译失败，以及一次把内容已完整的前缀误当作撕裂页的测试预期失败，均保留原记录；修正后单独复验。

原型还存在明确的工程边界：逻辑文件约 1 MiB 上限、用于研究的页内存保存方式，以及尚未接通的分段、维护 I/O 预算和空间回收；Windows 和其他业务负载未验证，因此不能替换主引擎。它保留上层完整二进制缓存和减法裁剪，并未重写这些逻辑。

文件布局满载约有四倍冗余。小值例子的系统写入请求从每 256 次约 94 kB 增至约 2.29 MB；这不等于设备实测流量。后续采用前须控制写放大，并接回受控缓存及完整维护能力，不能只凭这个低延迟例子宣布全面胜出。

证据目录：`build/arena-sync-study-20261108/`。主要记录为 `cell2-report.json`（六个原生 A/B 样本）、`cell3-report.json`（修正后的页恢复检查，复用原样本）、`reserve-report.json`（五种预留策略和跨页恢复）、`final-report.json`（整笔预留与 balanced 复验）和 `decision.json`。相关成功资源均核对所有权后清理；失败及恢复执行记录保留。
