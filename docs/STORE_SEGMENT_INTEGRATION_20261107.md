# 分段 Store 接入与故障审查（隔离候选）

本批将分段文件层接入实际 Store 的事务、检查点、恢复、原位回收、整理与全备。源码位于 `build/segment-store-lab-20261107/source/`，基于修复跨轮读者保护的 Root5 回收候选，**没有合入主工程，也没有发布 SDK**。它推进了单文件长度问题的解决方案，尚未完成长期空间、性能、语言或移动平台验收。

## 实际接入

- 原位置 I/O 实现保留为 NativeFile，SharedFile 提供统一门面。恢复、补丁祖先、索引页和流式复制继续用同一套逻辑偏移；段边界仅拆分实际 I/O，不改变值二进制缓冲的减法裁剪。
- 旧单文件容器继续按原布局读写。隔离头文件增加 `FQDB_STORE_SEGMENTED` 创建标志及 C++ `StoreOptions.segmented`；标志不改变 C 结构大小或版本。打开已有分段库会识别容器，读者不必再次传创建标志。**主工程和旧 SDK 尚未提供此选项。**
- 本批外层实验格式为 `FQSEG002`，保留 64 KiB 头区，身份头在物理偏移 0/64 各保存一份 CRC 镜像。探测避开根租约锁住的第 0 字节；取得租约后校验两份身份一致。根文件句柄独立保留，读缓存驱逐不会释放租约。内部 FQDATA04 和 Root4/Root5 检查点仍通过逻辑地址访问。前一份 FQSEG001 保留为独立原始文件层实验记录。
- 非测试构建选择 64 MiB 数据段，测试通过私有钩子使用 64 KiB 高频跨界；这不表示正式段大小已经完成性能比较。名称最长 30 字符，全部直接位于数据库目录中；分段创建前检查 32 字符内部名称余量。
- 前台追加和后台同步/打洞/整段删除共用文件层变更互斥；读缓存另有短期互斥。写者单独、有界地持有脏文件引用，读缓存驱逐不承担刷盘，SYNC 不会遗漏已驱逐文件。
- WAL、值复制、检查点及双根边界的写前额度预留包括新段的两份身份头，每新增一段增加 128 字节请求额度；一次完整 WAL 或双根边界在首字节前预付。额度不足不改变已确认前缀；部分 I/O 或同步失败阻止继续写入，重开后按有效事务尾回滚。
- 稀疏查询把原生范围映射回逻辑地址，跳过已删除段；完整无引用段，或打洞后已没有数据区分配的旧段，可以整体删除。段头区和当前尾段受到保护。删除仍由回收引用闭包及跨轮旧读者 epoch 保证，未改变补丁祖先保守标记策略。
- 活跃段索引用连续 ID 区间表达，避免为整个历史尾地址建立文件 ID 数组，最多 65536 个碎片区间；碎片分裂在删除文件前预分配。这个额外元数据目前尚未统一计入 Store 的 writer/pin 预算，不构成 RSS 硬上限证明。
- 整理继承实际来源的段几何；全备输出同类容器，代际退役和未发布目标清理覆盖整个文件组。失败备份的所有权描述仅保留已知创建段的区间，不保留原生文件句柄，允许发布前关闭句柄，清理也不必重新读取头部。

## 审查与实际失败

最初整合代码在 Windows 与 Linux ASan/UBSan 均为 **20/21**，失败项都是 `paged_io_budget`，信息为 `quota leaked staging directory`。新清理流程试图在额度耗尽后再打开并读取头部，连旧单文件备份的失败清理也受影响。失败源码、二进制、报告与数据分别保留在 `initial-source.zip`、`initial-*`，没有覆盖成成功记录。

修复后，旧文件恢复原有已知路径清理；本进程创建的分段目标持有共享的所有权区间描述，OutputDirectory 记录这个描述，Generation 析构和外层失败清理均可在不新增读取的情况下删除已知创建的文件组。若删除子文件失败，会保留主文件锚点。打开的旧代际仍要求验证身份后才删除，未知或身份不符的文件继续保留。

新增分段备份回归先测出写额度耗尽时的实际读取量，再以相同读取上限重跑，确保在读、写额度均没有余量时仍不遗留 staging 目录。测试同时确认输出未发布、请求字节未越过额度、源数据完整可读。

接入审查还修正了前台追加与后台回收访问脏集合的竞态风险、根身份探测与 Windows 租约字节冲突、跨段身份头未计入嵌套额度，以及缓存节点分配失败之前没有记录已发布新段所有权的问题。这些属于接入代码审查修正，未声称每项都由旧版运行复现。

1. 多键跨段事务、冷读取、完整私有补丁缓冲减法裁剪、检查点和结构校验；旧读者持有期间回收不删除文件，退出后受限 I/O 切片继续完成。
2. 受测模型段文件 **119 → 20**，所有当前值和补丁祖先保持正确；关闭重开、整理、全备后继续冷读取验证，整理和备份保留段几何。这个有限模型不等于持续稳态或相同工作量的压缩比。
3. C++ SDK 显式分段创建、SYNC 写入，C ABI 无创建标志重开；旧布局读写继续可用。
4. 整笔 WAL 的物理头额度预拒绝、跨段部分写后停止写入、有效尾恢复、恢复后继续写；重开后核对原有源值和结构。
5. 4 名写者与 8 轮回收同时运行，结束后核对最终值及重开；后台文件层同步、打洞、段索引与前台追加由 TSan 检查。
6. 在事务已同步但尚未发布、发布后、第一次根、第二次根、标记后和实际回收后共 6 个边界使子进程退出，再重开核对并继续写；另在确认 SYNC 版本后由父进程实际 Windows TerminateProcess / Linux SIGKILL，重开核对确认版本和最后值。
7. 耗尽读/写额度的备份失败清理，不发布目标、不遗留临时目录、不损伤源库。

TSan 下排除子进程崩溃/强杀组，由 Windows 与 ASan 覆盖；只重试了合计 28 次明确未进入 main 的地址布局失败，没有跳过已进入测试的错误。Linux 编译和运行均限制两核、4 GiB、无额外 swap；这是正确性验证，未计时性能峰值。测试二进制、日志和失败/成功数据均保留在 D 盘，自有容器和卷已按所有权核对清理。

## 尚未达到采用条件

本批没有采用任何新的写锁，旧写锁混合回退仍是独立未完成项。分段格式还需要覆盖字段索引/约束、集合、TTL、历史订阅和完整增量链在多段布局中的组合；现有旧布局功能测试通过不能代替这些组合。需要扩展段大小、页与帧跨界、实际 ENOSPC/内存上限和长期文件数量/回收进度验证，并检查标记内存随历史逻辑地址增长而变粗的问题。

三语言接入尚未用这个核心重新验收。现有 Python/Java/C# smoke 还含“数据库只有 3 个文件”“内部文件名最多 21 字符”的清理/布局假设，必须在隔离测试中适配并校验所有权，不能直接把新文件组交给旧清理逻辑。Java/C#/Python 的分段创建选项、旧 Java 类兼容、JNI、正式调用成本和较大数据跨段互通仍待完成。
