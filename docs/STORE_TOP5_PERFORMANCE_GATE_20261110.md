# 高频能力优化门槛研究（2026-11-10）

本轮按共用写路径、私有缓冲转移、字段读取及条件查询的顺序，先做完整接口调用的最小对照。只有发现超过10%的收益才继续复核；复核不能保住门槛则停止。本轮三个具体候选都未证明稳定超过10%，均未合入主引擎，原有生产源码174文件及库保持不变。

## 条件与结论

沿用上一轮服务器业务驱动、镜像、CPU 0/2、2 vCPU/4 GiB与原生命名卷。性能模式固定50 ms / 1 MiB；后台维护启用，200 ms、最小整理32 MiB、增长32 MiB。整存使用4096份档案、8个调用线程、显式512 MiB缓存，包含DTO编码和最终Sync。没有与编译或其他测试并跑。

## 原型边界及未采用的理由

**共用写路径。** 事务已记录基值依赖并在提交时验证版本，普通单命令则由写线程取得当前基值。原型复用这份引用用于记录数量统计，区分不存在与有版本的删除标记；冲突验证保留。同时为WAL操作头一次预留容量，减少字符串扩容。代表整存的整体收益只有0.6%，没有继续给增删改分别铺测试矩阵，也没有合入。

**缓冲转移。** 原型只搬走独占单命令的完整私有缓冲，不搬显式事务、保存点或私有游标可能共用的数据。先释放WAL内部对已复制小值的引用，再检查独占性；值必须小于16 KiB，避免搬走延迟I/O借用的大缓冲。缓存获得新的Data对象，事务预算对象仍随命令释放。未绕过缓存准入、CRC或减法裁剪。由于复核没保住收益，未进入生产级接入与故障测试阶段。

**字段及条件查询。** 按索引只取键原本已避免读取业务值，准备投影也已有结果复用。此次先测每线程一个、以不可变schema值的准确身份为依据的小型解析规则缓存，仍逐次取得schema并记录依赖，未跳过整份Protobuf有效性校验。使用4096个4 KiB档案、双字段唯一索引和变化查询键，完整调用公开C++接口并解码返回结果；每次核对结果。收益7.3%，没有继续开发覆盖索引、字段位置缓存或新的公开接口。

以上是三个具体候选未达门槛，不能据此推断这三个大方向都没有其他可能。CPU细节变快也不保证整体吞吐超过10%；磁盘、后台整理、线程交互仍会影响结果。本轮没有完成新的瓶颈采样来精确分解这些因素。

## 两项优化能否叠加：追加核对

两个实验开关可以同时打开，但当前原型没有覆盖同一带索引库的读写路径。缓冲转移仅在`SingleWriteCursor`分支执行；`AtomicUpdate::prepare`要求`checkpoint.features == 0`才使用这一分支。建索引会持久化扩展能力标志，之后普通写入走事务及索引维护路径，仍复制完整缓存值。因此当前原型在这个带索引的库上不能同时获得“搬移私有缓冲”和“复用查询规则”的收益。这个限制也适用于同库中不属于索引前缀的普通记录，不能按单条记录是否有索引猜测路径。

即使以后将缓冲转移安全扩展到事务路径，来自不同负载的吞吐百分比也不能直接相加。例如假设写入与查询各占原先一半耗时，分别稳定提速5.9%和7.3%，整段业务的吞吐增益约为`1 / (0.5 / 1.059 + 0.5 / 1.073) - 1 = 6.6%`。这是说明加权方法的假设例子，不是对混合负载的实测预测；原先5.9%本身也没有稳定收益证据。

追加最小混合负载使用同一组4096个4 KiB档案、一个调用线程，完整保存非索引字段后按双字段唯一索引查询，每轮一写一查，包含最终Sync。配置保持50 ms / 1 MiB及原后台维护设置，复用原库二进制，仅编译新驱动；每个样本关闭重开并核对全部业务值和索引结果。

| 方案 | 业务操作/秒 |
|---|---:|
| 当前主引擎 | 161,514 |
| 候选只开查询规则复用 | 146,918 |
| 候选同时打开两项 | 122,798 |

三个样本各约1秒，未出现超过10%的收益，按门槛停止，未合入。本表只作筛选，未交替复测，不能把其中差异认定为稳定回退比例，也没有用短测声称两个开关都会命中；上述不能搬移的结论来自明确的代码分支。原始数据及库哈希见[组合短测报告](../build/top5-combo-20261110/report.json)，驱动见[probe.cpp](../build/top5-combo-20261110/probe.cpp)。生产源码未改。
