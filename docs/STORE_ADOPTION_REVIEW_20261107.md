## 实际发现与修复

首次 Windows 默认构建成功，CTest 为 22/23，回收测试未在等待期限内收敛。九次重跑通过后，集中探针仍复现：版本 320、逻辑长度 42485649 字节，线程看到分配量仅 917504 字节，回收次数停留在 2。进程退出后从新句柄查询为 22085632 字节。

独立 Win32 探针确认，在稀疏文件打洞后追加缓存写入，`FileStandardInfo` 与 `FileCompressionInfo` 都可能暂时漏计脏尾部；显式同步后才刷新。后台仅凭该值可能漏触发回收。修复以“系统分配量”和“持久检查点之后的追加字节数”两者较大值判断压力，仍应用原有增长、垃圾比例、版本和 I/O 预算限制；不为轮询状态额外刷盘。这是触发依据的补充，不改变实际分配统计的定义，也不承诺每轮清除全部旧数据。

新增回归在测试构建中模拟滞后的分配量，等待实际后台任务完成后解除模拟，再检查物理分配、完整数据和重开。该测试钩子不进入生产库。修复后的 Windows 两轮并发覆盖探针连续 40 次通过。

首次 Linux 默认构建与 23 项 CTest、安装后消费者均通过，但分段日志压力在 Windows bind mount 上返回 UNSUPPORTED。相同的 `renameat2(RENAME_NOREPLACE)` 探针在 Linux 原生卷成功，在该共享挂载点返回 EINVAL。验证数据库与日志改到原生卷执行后，两布局通过；库没有降级为可能覆盖现有目标的发布方式。

## 存活数据超过内存

`build/store-large-live-20261107/` 使用生产共享库和公开 C++ API，不含内部测试钩子。数据库位于 Linux 命名卷，运行容器限制为两个 CPU、512 MiB 内存且无额外 swap，缓存配置为 8 MiB。

- 存放 131072 条确定性 Protobuf 值，存活值总量 2150367232 字节，超过 2 GiB，约为容器内存限额的四倍。
- 批量写入后，对分散的 1024 条值进行固定字段二进制修改；旧快照仍逐条匹配修改前模型。
- 三个独立进程分别完成创建与全模型校验、重开全量校验与继续写入、再次重开全量校验。最终版本 4129；每次全量读取都核对每个值的完整字节并执行结构校验。
- 文件平铺共 35 个，单个数据文件最大 67174400 字节，文件名不超过 30 字符。继续写入后的总物理分配约 2.03 GiB，存活数据未被误回收。
- 进程峰值 RSS 为 18087936～18350080 字节。容器含文件缓存的峰值约 512.2 MiB，出现实际内存压力与回收，无 OOM/OOM kill；不能把进程 RSS 当成整个容器占用。
- 成功后仅移除已核对所有权并停止的自有容器及命名卷，保留探针源码、二进制/核心哈希、逐阶段日志和资源报告。

此次未启用后台整理，主要验证超内存存活值、冷读、快照、局部修改和重开。它与此前小活跃集持续回收的证据互补，不代表超内存活跃集上的长期并发维护或吞吐峰值。记录的打开耗时受当前文件系统缓存影响，不作为普遍重启性能承诺。
