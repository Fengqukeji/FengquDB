# 单写线程、周期与字节合批的可靠性设计

状态：结合现有实现完成的接入设计，尚未修改主引擎或公共 SDK。已有[单线程性能原型](SINGLE_WRITER_PROOF_20261108.md)证明写入吞吐收益，本文件明确其安全边界与接入要求；没有新增运行测试或真实断电验证。

后续状态（2026-11-09）：主引擎和公共 SDK 已实现，见 [当前写入契约](STORE_WRITE_POLICY.md)。本文件保留接入前设计，内部原型成绩不代表公共接口成绩。

用户已确定所有平台默认采用 **100 ms／1 MiB**，保持可配置。PTFramework日志参考、空闲等待开销与移动端参数边界见[默认参数规格](WRITE_POLICY_DEFAULTS_20261108.md)。该规格仍不表示主引擎已经接入。

## 目标与不可替代的条件

采用一个专用写线程累计与执行修改，周期到或字节阈值到即处理完整事务，一组共享可靠刷盘。保留已有完整二进制缓存、减法裁剪、共享所有权和大/小写入文件路径。普通只读操作继续读取已发布视图，无须排队等待写周期。

**尚未到达任何持久介质、仅存在普通进程内存的数据，无法在真正断电后恢复。** 给内存再复制一份、校验、共享内存、mmap 或异常退出回调，都不能消除此条件。WAL 只有在内容已经可靠同步后，才能提供相应持久保证；日志名称或预留文件空间不改变这一点。

本库应默认保证：**已经向业务确认可靠成功的事务，在系统与硬件遵守同步语义时，断电或进程崩溃后仍可恢复。** 进入内存但尚未可靠确认的请求可能丢失，也可能已经写入并在恢复后出现，不能宣称全部未确认请求都能找回或都会回滚。

如果需求进一步要求“连待确认请求也一笔不能丢”，这些请求自身就必须先完成可靠持久化，或其输入来源保有可重放的持久副本。不能同时承诺普通 RAM 接收后立即返回可靠成功、持续延迟落盘、突然断电零丢失。

## 推荐的默认接口与确认边界

接口采用“提交请求”和“可靠确认”分开表达，以下名称为设计示意，当前并不存在这些公共接口：

```text
Submit/CommitAsync -> 待确认凭据
    -> 单写线程按周期/字节门槛收集
    -> 逐笔检查、写入独立 WAL
    -> 对本批覆盖的日志做一次可靠同步
    -> 发布已提交视图、推进 durable 水位
    -> 凭据完成，返回可靠成功及提交版本
```

`Submit` 返回表示库接管了请求及输入生命周期，不能命名或编码成“已提交成功”。单线程业务可以继续收集后续输入，不必为每笔等待创建线程；凭据支持轮询、批量等待以及各语言事件循环/异步等待。所有成功完成通知都发生在持久化屏障之后。

保留阻塞提交入口，由它等待相同的可靠凭据；单线程如果每次都立即阻塞等待，自然无法积攒下一笔，这不是内部写线程能够代替业务生成的工作。提供显式批次提交及等待入口，使同一个调用线程能够一次交给写者多笔待确认事务。

提供显式 `FlushAndWait` 屏障，用于主动保存、正常关闭和宿主挂起前的尽力保存：确保屏障前已接收事务都得到最终结果。它是明确请求的提前处理，不给普通每笔等待偷偷增加一次独立同步。不得依靠析构或退出回调实现断电安全；系统可能不给应用任何退出时间。

## 周期调度

正式接入应使用单调时钟和写线程自己的 `wait_until`，不再依赖下一次业务调用检查时间。没有新请求时，已有待处理数据也必须在期限到达后处理。

- 周期模式使用固定时钟刻度；阈值提前触发不会把后续固定刻度不断后移。空队列不写空日志、不刷盘。
- 入队通知只唤醒写者；完成通知只唤醒相关凭据，避免每个新请求唤醒所有调用线程。
- 写者进行 I/O 时新请求可以进入下一批有界队列。仍只有一个写者顺序执行，不引入并行写流水线或分片。
- 周期约束的是开始安排处理的时机，不是包含排队、索引处理及设备同步在内的硬实时完成保证。前一批耗时过长应记为超期，不能掩盖实际延迟。
- 阈值由完整事务的预计/暂存业务字节统计，真正文件写入量另计。单笔大事务不得为了达到门槛被拆成多个可见提交。原有组笔数、索引和内存预算仍约束实际分组。

1 MiB 是已有4 KiB业务原型的有效点，不是所有操作的全局最佳阈值。100 ms在高流量下常被字节触发提前结束，在低流量下会增加可靠确认等待。周期、门槛、队列预算应独立可配置，不能把内存预算或预留空间误称为必须持续占满的缓存。

## 各故障窗口的结果

| 故障时点 | 可保证的结果 | 凭据状态 |
| --- | --- | --- |
| 仅入队，仍在 RAM | 请求可能丢失，库无法凭空重建输入 | 尚未可靠确认 |
| 正在写 WAL 或正在同步 | 恢复后可能没有，也可能存在完整事务 | 结果未知；不得报可靠成功 |
| 同步成功，尚未发送完成通知 | 数据可恢复，调用方可能没有收到结果 | 需重启核对，避免盲目重做 |
| 已发送可靠成功 | 已确认事务必须可恢复 | 可靠成功 |
| 正常关闭并成功排空 | 已接收请求都有明确结果，成功部分已同步 | 逐笔最终状态 |

数据恢复和调用方是否收到通知是两件事。为处理“已经落盘但没收到回复”，业务可提供稳定请求 ID；幂等记录及对应数据变更应处于同一原子事务。进程内队列序号不自动具有跨重启查询能力，提交版本也不能在请求尚未验证时随意提前分配。计数、扣减、List push 等非幂等操作尤其不能在未知结果后直接重做。

幂等查询只有在记录仍被保留时才有效，不能承诺无限期去重。没有稳定 ID 或可核对业务状态时，继续保留现有 `COMMIT_UNKNOWN` 边界。

## WAL 与恢复的复用

现有 `src/paged/group.hpp` 已按 WAL、`file->sync()`、durable 水位、发布、完成通知的顺序处理 SYNC 合组。该屏障可以由整个批次共享，无须每笔增加一次独立刷盘，也无需再复制一份完整数据库文件。

现有 `src/paged/recovery.hpp` 从检查点顺序校验日志版本、内容与引用，再修复物理不完整的尾部并发布恢复检查点。完整记录的 CRC 或语义错误仍报损坏，不能为了让启动成功而随意截断可能包含已确认数据的区域。未确认但已经完整落盘的事务可以被恢复；跨多个独立事务不承诺整批原子性。

**当前 HybridFile 还存在应用内缓存层：** `write/write_known` 可以先进入 `pending_`，真正输出持久化包和同步发生在 `sync()`。因此，现有“WAL逻辑追加完成”不能直接解释成“数据已经进入操作系统文件缓存”。

可单独研究提前把完整 WAL 包输出给操作系统、周期性再做可靠同步，以减少进程崩溃时的 RAM 窗口。但它需要改造 HybridFile 的包封装与恢复协议，且尚未被本轮证明；不能只加一个 `write()` 就宣布防崩溃，更不能据此宣布防断电。该策略仍无法保证写者尚未处理的入队请求。

## 崩溃与断电的区别

| 数据位置 | 仅进程崩溃、系统仍运行 | 真正断电或内核崩溃 |
| --- | --- | --- |
| 进程内存 | 丢失 | 丢失 |
| 完整写入操作系统文件缓存、尚未可靠同步 | 通常可保留；仍须校验完整性和恢复路径 | 不能保证 |
| 已完成平台可靠同步的日志 | 按文件系统与硬件同步语义保证 | 按相同前提保证 |

Windows、Linux分别复用适用的文件同步原语；文件创建、切换代际、检查点和回收也必须满足元数据顺序。移动平台应另行审计自身的持久化要求和挂起行为，不能把桌面测试当作 iOS/Android 的断电证据。

UPS、具有掉电保护的存储设备可以增强系统可靠性，但设备保护只覆盖已到达它的数据，不能自动保存进程尚未下发的 RAM 请求，也不能替代程序崩溃恢复。

## 接入整个底座时必须覆盖的路径

写者以数据库实例为数据与故障隔离边界，同一实例内各集合/键空间共用提交顺序；不能给每个表、集合或事务创建线程。若同时打开多个独立数据库目录，需要明确写者调度策略，不能承诺一次文件同步覆盖多个独立日志文件。

普通 put/patch/delete、原子条件操作、集合、TTL及自动索引引起的修改都应进入同一调度与可靠确认路径。每笔事务内的数据、索引和约束仍作为整体处理；原子批量写仍保持原子边界。普通事务保留 begin 时的快照、读依赖与冲突检查，不能直接套用原型中“在写者中创建盲写事务”的方法重定基全部事务。

检查点、整理、备份屏障、TTL清理及恢复封锁同样需要协调。现有维护代码含线程内 I/O 额度和 `commit_direct` 路径，迁移时必须显式携带额度、取消和检查上下文，不能把调用线程的 TLS 指针留给后台写者使用。维护工作需有界执行，防止长时间阻塞正常写入。

待确认请求使用稳定、有所有权的对象及有界内存队列。保持已有共享缓冲与写时复制；调用方临时指针不能在返回后继续借用，托管语言的输入也必须具有有效固定/共享所有权或进行必要复制。队列满时背压或明确失败，不静默丢请求。排队取消与“已开始写日志后的结果未知”必须区分。

默认读取只看已可靠发布的视图；事务内仍可读取自己的私有修改。完成通知不能在写者上执行任意业务回调，否则回调再次阻塞调用数据库会死锁，并且占用唯一写线程。

## 落地后的最小验证门槛

1. 空闲队列中仅一笔写入，验证周期真的触发；高流量验证字节阈值先触发，无额外每笔同步。
2. 入队后、WAL写入中、同步前后、完成通知前后分别强制结束进程，独立重开；确认所有已可靠确认事务保留，未确认结果按协议处理。
3. 注入短写、磁盘满、同步失败和日志尾部损坏，验证无部分原子事务、无错误成功、无故障后继续写入。
4. 验证旧快照、同键更新、一般事务读依赖、原子条件、集合与索引、取消/超时、队列背压、正常关闭、显式保存及维护额度。
5. 公共 C/C++、C#、Java、Python 接口统一采用同一确认语义，并检查异步对象及缓冲区生命周期。

进程终止测试不等于真实掉电测试；系统/设备层的写入丢失、重排和断电验证应另列证据。先用单线程最小业务案例证明实际 SDK 接入后的收益，再按新增风险扩展验证，不重复完整数据库性能矩阵。
