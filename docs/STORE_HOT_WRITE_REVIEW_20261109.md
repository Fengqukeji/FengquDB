# 提交结果缓存与单键路径优化（2026-11-09）

完成主引擎的结果缓存复用、单键增删补丁准备简化和同步完成信号复用，并审查修复TTL后继续补丁的边界。**周期、阈值、刷盘阻塞方式和可靠屏障保持原样**。本轮单独测试5个短板条件，并对仍弱的路径采样。

## 实现与审查

- 完整修改结果在WAL追加成功后可进入有界值缓存，后续读取直接使用物化结果，避免重复解析补丁。缓存只持有普通不可变Data，隔离事务暂存预算；缓存关闭、容量不足或分配失败时仍走原WAL恢复读取。保存点、私有游标、准备批次和共享读取保留旧值所有权。
- 原型曾无差别缓存整值覆盖，导致纯写存档出现额外复制。最终按读取情况接纳整值覆盖：此前真正被读过才预热，新缓存版本尚未被读就又覆盖时跳过；减法编辑已经计算出的完整结果仍及时缓存，包括补丁深度达到上限后的完整记录。
- 无扩展索引/约束特性的普通单键put、delete、patch在写者最新视图准备，不创建通用事务的公开快照、读集和写集树；复用相同WAL、增量索引、原子发布及可靠同步实现。启用索引或约束后保留原事务路径，显式多键事务保留原快照冲突语义。
- 同步提交复用调用线程的条件变量，单独唤醒其生产者，减少每笔条件变量初始化/销毁；异步凭据仍支持多个等待者。私有额外互斥锁的候选出现回退，最终保留原队列互斥保护通知生命周期，移除了额外锁往返。
- 将有界二进制裁剪封装为公共内部函数；首次补丁保留已经取到的源值，减少重复取值。审查发现仅有TTL私有修改时仍需借用原值，已修复并添加用例。
- 未合入无稳定收益的批内合并快照发布；继续使用单业务写线程。全局ABI仍为2，公共接口签名没有新增变化。

## 同批性能A/B

采用原服务器条件：2 vCPU（0/2）、4 GiB无额外swap、同镜像原生命名卷、4096档案、固定种子Zipf(0.99)。每调用线程一笔在途，每项3轮、计划1秒。普通成功是内存确认，吞吐计入最后可靠sync；每轮都全字段/余额校验并独立重开，再移除本轮自有夹具。

优化前后均使用同一最新业务驱动：独立字段覆盖调用公开patch，整存调用公开put，计数/转账仍是原快照事务。旧库支持同一ABI2入口，所以表内A/B用于隔离引擎改动；与此前使用显式事务封装字段覆盖的报告不是完全相同的接口开销。

## 仍弱处的瓶颈

1. **单调用线程小修改：跨线程同步往返仍在。** 每笔写入都要通知单写者并等待内存发布，当前只有一笔在途，无法利用并发自然合组。4 KiB混合更新每秒约2.1万业务调用、约2.1万次进程线程切换（含预热/收尾），约每笔写入两次；本轮CPU使用约0.86核，复用条件变量减少管理成本后，此串行往返没有消失。用户态CRC与缓存/索引查找也仍有成本。
2. **4 KiB整存：校验与实际可靠同步。** CPU采样里crc32本体约21.2%；2秒诊断中完成约6.6万次保存，group_flushes为271。即便100ms未到，1MiB字节阈值仍会提前触发同步；这一执行/刷盘耦合按本次要求保持原样。
3. **转账：两键事务、校验与缓存索引。** CPU采样里crc32本体约14.9%，值缓存哈希查找约8.3%，还存在多键快照验证、两个补丁和冲突重试。只覆盖8字节时，patch_buffer仍使完整结果CRC失效，提交前会重新校验整份值。

下一阶段可研究保持IEEE CRC格式的等长补丁差分校验、复用完整保存已有CRC并组合帧校验，以及进一步精简缓存/索引查找。它们是本轮定位出的后续方向，尚未实现；不能为了速度省略完整性校验或直接替换成不同多项式的CRC32C。

CPU采样来自最新源码的Release＋调试符号构建，999Hz的cpu-clock:u及DWARF栈，每项2秒；覆盖进程预热与校验收尾，不等于精确计时段或等待时间占比。诊断吞吐不混入正式A/B。分析容器临时使用PERFMON，未改宿主sysctl。

容器内存指标包含文件缓存；summary中的cache_mib是驱动输出时持有的缓存量，已包含结束后的验证读取，不能当作精确计时段的数据库堆峰值。当前核心DLL为853,504 B（原844,288 B），strip后SO为826,832 B（原818,640 B），约增加1%，不含绑定/JNI/运行时。
